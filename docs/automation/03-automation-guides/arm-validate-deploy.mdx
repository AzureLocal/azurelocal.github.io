## Overview

After the machines are provisioned (ZTP or an ISO install) and their operating system is configured, the cluster is created by an ARM deployment: Microsoft's quickstart template (`Microsoft.AzureStackHCI/clusters` with `deploymentSettings`), run first in **Validate** mode and then in **Deploy** mode. The toolkit automates that step with `Invoke-AzureLocalArmDeployment.ps1`, which works the same on a jump server and in GitHub Actions, GitLab CI or Azure DevOps.

```text
infrastructure.yml  +  OS configuration report  +  ZTP handoff (optional)
    -> Plan (preconditions) -> Validate -> approval -> Deploy -> report, events, exit code
```

It covers Active Directory or local identity; Storage Spaces Direct, a Fibre Channel SAN, an iSCSI SAN (Active Directory only), or hybrid (deployed as Storage Spaces Direct, the SAN connected afterwards); switchless or switched storage; and 1 to 16 machines. Running it twice is safe.

This page automates the manual routes in [Phase 05: Cluster Deployment](../../implementation/04-cluster-deployment/phase-05-cluster-deployment/index.mdx) (portal and ARM template). The manual runbooks stay the reference for each Azure setting.

## What it does

1. **Reads** the master `infrastructure.yml`, the OS configuration report and, if you have one, the ZTP handoff.
2. **Generates** every parameter of the right Microsoft template for your design and shows which file key fed which parameter.
3. **Checks readiness**, read-only (see [What it checks first](#what-it-checks-first)).
4. **Validates** and waits (10 to 30 minutes), reading Microsoft's step list as it goes.
5. **Waits for approval.** A pipeline has the platform's approval gate between the Validate job and the Deploy job.
6. **Deploys** and waits (2.5 to 3 hours).
7. **Explains a failure**: the failing step with the number the portal shows, the error text, the matching known issue with its cause and remediation, and what may be retried.
8. **Reports**: an event feed (JSON Lines), `report.json`, `summary.md` and an exit code of 0, 1 or 2.

It is **idempotent**. A Validate that already passed with the same parameters isn't run again. A deployment that is running is attached to, not duplicated. A deployment that failed is resubmitted only when you pass `-Resume`, because Microsoft warns that another Validate after a failure can break license sync.

### The SBE package checks

The hardware vendor's Solution Builder Extension (SBE) package is a **requirement**. Download it for your hardware model and the Azure Local version you deploy before you start, and make it available on a share the automation can read (`hardware.sbe.source_path`). You need it to update the cluster, and the gate reads it from the share and checks it before the cluster is created. To install it during the build, switch on the side-load (`hardware.sbe.delivery`); it is off by default.

The gate checks SB-001 to SB-006, and all of them block:

| Check | What it verifies |
|-------|------------------|
| SB-001 | The package source is configured, or declared not applicable with a reason (`hardware.sbe.requirement`, `hardware.sbe.not_applicable_reason`) |
| SB-002 | The share is reachable |
| SB-003 | The three files are present: `SBE_Discovery_<Vendor>.xml`, `SBE_<Vendor>_<Family>_<Version>.xml` and the payload zip |
| SB-004 | The hashes show the files are unmodified |
| SB-005 | The hardware model of every node is listed in the package's own supported models (a 17G Intel package fails on AX-760 nodes; the right one is `16G-45n0c-Intel` 5.0.2609.1611) |
| SB-006 | The version is validated for the target solution version (Dell on 2610: `12.2610.1004.x`) |

The update later reuses the same share: `Add-SolutionUpdate`, then `Start-SolutionUpdate` (see [Import and rediscover updates](https://learn.microsoft.com/en-us/azure/azure-local/update/update-via-powershell-23h2?view=azloc-2610#step-3-import-and-rediscover-updates) on Microsoft Learn). The keys, the vendor differences and the full wording are in [the SBE package prerequisite](../../implementation/04-prerequisites-and-assumptions.mdx#sbe-package).

What is already documented and checked on `main` before Validate:

- The OS configuration run ends with a **verify pass** and a per-node `converged` result in `report.json` (a node is converged only when nothing is left to change). See [How the run works](../../implementation/04-cluster-deployment/phase-03-os-configuration/how-the-run-works.mdx).
- `Invoke-AzureLocalArmDeployment.ps1` re-checks, read-only and in `-Mode Plan`, the conditions listed in [What it checks first](#what-it-checks-first), including `OsConfigurationConverged` (the report says every node converged for this cluster), `OsBuildConsistent`, `DnsAndTime`, `ArcMachinesConnected` and `ArcMachineNaming`.
- The Environment Checker validators are a separate, manual readiness assessment: [Task 05: Environment Checker Readiness](../../implementation/03-onprem-readiness/phase-02-enterprise-readiness/task-05-environment-checker-readiness.mdx). Azure also runs them itself during Validate.

## Run it from a jump server

You need PowerShell 7 on Windows or Linux, the `powershell-yaml`, `Az.Accounts` and `Az.KeyVault` modules, and a sign-in. The script does not sign in.

```powershell
Connect-AzAccount            # or: Connect-AzAccount -Identity   (an Azure VM with a managed identity)

$arm    = './scripts/deploy/04-cluster-deployment/phase-05-cluster-deployment/Invoke-AzureLocalArmDeployment.ps1'
$common = @{ InfrastructureFile = './infrastructure.yml'; OsConfigurationReport = './osconfig-report' }

& $arm @common -Mode Plan     -ReportDirectory ./arm-plan        # reads only; add -Offline to touch no Azure at all
& $arm @common -Mode Validate -ReportDirectory ./arm-validate    # 10 to 30 minutes
& $arm @common -Mode Deploy   -ReportDirectory ./arm-deploy      # 2.5 to 3 hours, only after a Validate of these parameters
```

`-Mode ValidateAndDeploy` does the last two in one run with a gate between them (`-ApprovalMode stop|prompt|none`). The default, `stop`, ends after a good Validate in state `AwaitingApproval` with exit code 0; run `-Mode Deploy` to continue. `-WhatIf` does everything except submit.

| Parameter | Meaning |
|-----------|---------|
| `-InfrastructureFile` | The master file (schema 5). Required |
| `-OsConfigurationReport` | The OS configuration run's `report.json`, a node-level report, or its report directory. Gives the OS names of the network ports (found by MAC), the SAN disks (a LUN number becomes the disk's UniqueId), and proves every node converged |
| `-HandoffFile` | The ZTP handoff: Arc machine resource IDs and the solution build |
| `-Mode` | `Plan` (default), `Validate`, `Deploy`, `ValidateAndDeploy` |
| `-ReportDirectory` | Where the events, report, summary and parameter files go. Not for a repository |
| `-Resume` | Resubmit a failed Deploy (and attach to a running one) |
| `-AcknowledgeKnownIssues` | Known issue ids you accept, for example `arc-device-id-name` |
| `-Settings`, `-SettingsFile` | Run settings as a hashtable or a JSON file; they win over the master file's `deployment` block |
| `-AllowRevalidate` | Validate an instance in a failed deployment state. Microsoft says not to; support-guided recovery only |
| `-RegisterResourceProviders` | Opt in: register the mandatory resource providers that are not registered and wait until they are `Registered` (Validate and Deploy only). Without it the run never changes Azure |
| `-TemplateFile` | A local copy of the quickstart template instead of the download |
| `-Offline` | Plan only: no Azure call at all |

## Run it from a pipeline

Copy the file for your platform. Each runs the same script: **preconditions** (Plan), then **Validate**, then **Deploy** behind the platform's approval, and publishes `report.json`, `summary.md` and the event feed of every job. No client secret is stored anywhere; the files hold placeholders only, and you set the real values as variables of the project.

| Platform | File in the toolkit | Jobs or stages | Approval | Sign-in |
|----------|---------------------|----------------|----------|---------|
| GitHub Actions | `pipelines/github-actions/arm-deployment.yml` (copy to `.github/workflows/`) | `preconditions`, `validate`, `deploy` | The environment of `devops.pipelines.environments.arm_deployment`, with required reviewers | `azure/login`, OIDC |
| GitLab CI | `pipelines/gitlab/stages/arm-deployment.yml` (declares its own stages, include it from a pipeline of its own) | `arm-preconditions`, `arm-validate`, `arm-deploy` | `arm-deploy` is a manual job in the protected environment of `devops.pipelines.environments.arm_deployment` | `id_tokens` and a federated token, or a managed identity |
| Azure DevOps | `pipelines/azure-devops/arm-deployment.yml` | Stages `Preconditions`, `Validate`, `Deploy` | Approvals check on the environment you enter as a run parameter (the value of `devops.pipelines.environments.arm_deployment`) | A service connection with workload identity federation |

The pipeline files name no runner label, agent pool or environment. On GitHub and GitLab they read `AZL_RUNNER_LABEL` and `AZL_ENVIRONMENT_ARM_DEPLOYMENT`, which task 05 of the CI/CD setup sets from `devops.pipelines.runner_label` and `devops.pipelines.environments.arm_deployment` ([Task 05](../01-cicd-infra/phase-01-cicd-setup/task-05-configure-variables.mdx)). On Azure DevOps the pool and the environment are run parameters with no default.

Pipeline inputs: the mode (`Plan`, `Validate`, `ValidateAndDeploy`, `Deploy`), the path of `infrastructure.yml`, the OS configuration report (the artifact of the OS configuration pipeline, or a repository path), the optional ZTP handoff, `resume`, and the known issue ids to acknowledge.

- Use a self-hosted runner that reaches Azure over HTTPS (Linux with PowerShell 7 is enough). The Active Directory check also needs a domain-joined runner with the ActiveDirectory module; on any other runner it is reported as **Skipped**, never as passed.
- The Deploy job re-runs every precondition and checks that **these parameters were validated** (the Validate's ARM deployment is named from a hash of the parameters), so an approval cannot start a Deploy of something that was never validated. The reviewer reads the Validate job's `summary.md`.
- Passwords are read from the Key Vaults named by the `keyvault://` references in the master file. The identity needs `Get` on those secrets.

The OS configuration step has its own pipelines (`pipelines/github/os-configuration.yml`, `pipelines/gitlab/os-configuration.gitlab-ci.yml`, `pipelines/azure-devops/os-configuration.yml`) with an approval before apply: see the pipeline pages for [GitHub Actions](../02-cicd-pipelines/github-actions.mdx), [GitLab CI/CD](../02-cicd-pipelines/gitlab-cicd.mdx) and [Azure DevOps](../02-cicd-pipelines/azure-devops-pipelines.mdx).

## What it checks first

All checks are read-only. Each is `Passed`, `Failed` (stops the run, exit 1), `Warning`, or `Skipped` (with the reason). The report lists all of them. Skip a check on purpose with `deployment.skip_preconditions`; it still appears as Skipped.

| Check | What it looks for | Typical fix |
|-------|-------------------|-------------|
| `AzureContext` | Signed in; the subscription and tenant are the file's | `Set-AzContext`, or fix `azure.subscription_id` |
| `ResourceGroup` | `azure.resource_group` exists | Create it |
| `ResourceProviders` | All 13 resource providers Microsoft requires are Registered. Any one that is not is **Failed**, never a Warning | `Register-AzResourceProvider -ProviderNamespace <name>`, or run with `-RegisterResourceProviders` |
| `Permissions` | May write deployments, clusters, vaults, storage accounts and role assignments at the resource group | Owner, or Contributor plus User Access Administrator |
| `NamesAvailable` | Diagnostic and witness storage account names and the new Key Vault's name are free | Pick another name; a soft-deleted vault keeps its name |
| `KeyVaultSecrets` | Every `keyvault://` reference points at a listed vault and an existing secret (the value is not read) | Create the secret; grant `Get` |
| `ArcMachinesConnected` | Each node's Arc machine exists, is Connected, is in the instance's resource group | Finish ZTP or Arc registration |
| `ArcMachineNaming` | The Arc machine is named after the host. A device-ID name (`<id>-1`) fails the Deploy at step 0.41 on build 2690 | See the known issue below |
| `OsConfigurationConverged` | The OS configuration report says every node converged, for this cluster | Run the OS configuration with `-Mode Apply` |
| `OsBuildConsistent` | Every node runs the same OS build | Install the same build everywhere |
| `SbeConsistent`, `SbeValidatedWithSolution` | The package must be on the share ([SB-001 to SB-006](#the-sbe-package-checks)), but passing an SBE to the ARM deployment is opt-in. With no `hardware.sbe.version` both pass with "deploying without a Solution Builder Extension". With a version the family must be set too, and the SBE must be validated with the solution version the nodes run | Set `hardware.sbe.family`, or remove the version to deploy without an SBE |
| `DnsAndTime` | DNS servers set and valid, NTP set, no pending Dns or Time change in the OS report | Fix `networking.management.dns_servers` and `ntp_servers` |
| `ActiveDirectoryPrepared` | The OU is not at the top of the domain; the LCM user name is 20 characters or fewer; the OU and user exist | Run Microsoft's Active Directory preparation |
| `LocalIdentityPrerequisites` | `identity.local_identity.dns_zone` is set | Set it |
| `NoLeftoverFailedDeployment` | No failed or running deployment that this run would damage | Resume with `-Mode Deploy -Resume`, never Validate again |
| `ValidatedBeforeDeploy` | (Deploy only) Validation succeeded for these parameters | Run Validate |

### The mandatory resource providers

The 13 providers are the list in Microsoft Learn, [Assign required permissions for Azure Local deployment](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deployment-arc-register-server-permissions?view=azloc-2610): `Microsoft.HybridCompute`, `Microsoft.GuestConfiguration`, `Microsoft.HybridConnectivity`, `Microsoft.AzureStackHCI`, `Microsoft.Kubernetes`, `Microsoft.KubernetesConfiguration`, `Microsoft.ExtendedLocation`, `Microsoft.ResourceConnector`, `Microsoft.HybridContainerService`, `Microsoft.Attestation`, `Microsoft.Storage`, `Microsoft.Insights` and `Microsoft.KeyVault`. A provider that is `Registering` still counts as missing until it is `Registered`.

**Registration is opt in.** By default the run reads and never changes Azure. Pass `-RegisterResourceProviders` (or set `deployment.register_resource_providers: true`) to let a Validate or Deploy run register what is missing. It asks once per provider and reads their state every 10 seconds for up to 15 minutes. Plan mode and `-WhatIf` never change Azure. It needs Owner or Contributor on the subscription.

### Passing the Solution Builder Extension to the deployment is opt-in

The SBE package must be downloaded and available on the share (see [the SBE package checks](#the-sbe-package-checks)); what is optional is handing an SBE to the ARM deployment and side-loading it at build time. A deployment without an SBE is a normal deployment. When `hardware.sbe` is absent, or has no `version`, the run passes none of the seven SBE parameters of Microsoft's template (`sbeVersion`, `sbeFamily`, `sbePublisher`, `sbeManifestSource`, `sbeManifestCreationDate`, `partnerProperties`, `partnerCredentiallist`). An SBE is passed only when `hardware.sbe.version` is set. If Azure still names an SBE problem in a run without an SBE (the nodes carry a package in `C:\SBE`), the known issue `sbe-referenced-but-not-configured` says so and offers both ways out.

Two keys (schema 5.6.24) fill `partnerProperties` and `partnerCredentiallist` when an SBE is passed. Leave both out unless the vendor's SBE documentation names a property or a credential; the deployment then sends empty lists.

| Key | What it is |
|-----|------------|
| `hardware.sbe.partner_properties[]` (`name`, `value`) | Properties the hardware vendor's SBE asks for, as name and value pairs (ARM `partnerProperties`). Copy the pairs as the vendor's SBE documentation gives them. Not a secret: a secret goes in `partner_credentials`. |
| `hardware.sbe.partner_credentials[]` (`secret_name`, `secret`) | The secrets the vendor's SBE needs while the deployment runs, for example the login of its download connector (ARM `partnerCredentiallist`). `secret_name` is the name the secret gets in the cluster's own Key Vault (`cluster.key_vault.name`) and the name the SBE looks for. `secret` is required with every entry: a secret reference (`keyvault://`, `env://`, `file://` or `command://`), never the value. |

The toolkit reads each `secret` on this machine, in memory, when it submits the deployment, and sends it as `secretValue`. Microsoft's template writes the value into the cluster's Key Vault. The template declares `partnerCredentiallist` as a plain array, so the value is visible in the deployment's input parameters in Azure. Set it only when the vendor's SBE requires it. The parameter file holds `null` for it (`-SecretMode Placeholder`); `-SecretMode KeyVaultReference` refuses when an entry exists.

## What it builds from the master file

`parameter-sources.md` in the report directory shows, for your scenario, which `infrastructure.yml` key fed each ARM parameter. A required value that is empty ends the run (exit 2) with a message such as:

```text
ARM parameter adouPath (required when scenario.identity is active_directory) needs identity.active_directory.ou_path in infrastructure.yml, and it is empty.
```

All missing keys are listed at once. A design the generator does not support yet (disconnected operations, Azure Government with local identity or a SAN, rack aware with a SAN or local identity, an iSCSI SAN with local identity) stops with exit 2 and says so. An iSCSI SAN with local identity is refused because Microsoft has no template for it.

### SAN values in the master file

For a SAN the generator fills the parameters of Microsoft's template: `create-cluster-san` for Fibre Channel and `create-cluster-san-iscsi` for iSCSI. For iSCSI it builds one object per node with the Arc machine ID, the address, the initiator name and the iSCSI ports, and it sets the CHAP type. These keys feed them (example values are from the master template).

| Key | Example | Used for |
|-----|---------|----------|
| `storage.san.type` | `iscsi` | `fibre_channel` or `iscsi`. Selects the template |
| `storage.san.iscsi.targets[]` | `iqn`, `portals`, `fabric` | The array's iSCSI targets |
| `storage.san.iscsi.networks[].fabric` | `A` | The path: `A` for the ports with the role `iscsi:a`, `B` for `iscsi:b` |
| `storage.san.iscsi.networks[].subnet` | `198.51.100.0/24` | Subnet of the iSCSI network, in CIDR form. Required |
| `storage.san.iscsi.networks[].vlan_id` | `0` | VLAN, 0 to 4094. 0 means untagged. Default 0 |
| `storage.san.iscsi.networks[].next_hop` | `198.51.100.1` | Only when the target portals are in another subnet: the router address on this network |
| `storage.san.iscsi.jumbo_packet` | `9014` | Jumbo packet size of the iSCSI networks, in bytes. Default 1514 |
| `storage.san.iscsi.chap.enabled` | `false` | `true` when the targets require CHAP |
| `storage.san.iscsi.chap.mutual` | `false` | `true`: the initiators also authenticate the targets (ARM chapType `Mutual`). `false`: one-way CHAP (`OneWay`). Default `false` |
| `nodes[].san.initiator_iqn` | an IQN | The initiator name of each node |
| `nodes[].network_adapters[].roles` | `iscsi:a`, `iscsi:b` | The ports that carry iSCSI. Every node needs a port with the role `iscsi:a` or `iscsi:b` |
| `networking.cluster_network_properties.bandwidth_percentage_smb` | `50` | Share of bandwidth reserved for SMB, 1 to 97 percent. Default 50 |
| `networking.cluster_network_properties.jumbo_packet` | `9014` | JumboPacket of the cluster network adapters: 1514, 4088 or 9014. Default 9014 |
| `networking.cluster_network_properties.priority_cluster` | `7` | 802.1p priority of the cluster heartbeat, 0 to 7. Default 7 |
| `networking.cluster_network_properties.priority_smb` | `3` | 802.1p priority of the SMB traffic, 0 to 7. Default 3 |

The CHAP secret stays a Key Vault reference (`storage.san.iscsi.chap.secret`). The four cluster network values are no longer fixed in the generator. Their defaults are the values of Microsoft's template. A Fibre Channel or Storage Spaces Direct file needs none of the new keys.

## Re-running, resuming, waiting

| Found in Azure | Validate | Deploy |
|----------------|----------|--------|
| Nothing | Submits | Refused: validate first |
| Validated with these parameters | Not submitted again | Submits |
| A validation of these parameters running | Attaches and waits | Refused |
| A deployment running | Refused | Attaches and waits |
| A failed deployment | **Refused** (Microsoft: another Validate can break license sync) | Refused, unless `-Resume` |
| A succeeded deployment | Refused | Reports it, submits nothing |

**Resume.** The portal has *Resume deployment*. For the ARM route Microsoft documents a second submission with the same parameters and `deploymentMode` Deploy; `-Resume` does that, under the same deployment name. Whether Azure continues at the failed step or restarts is not documented for the ARM route; the first step events after a resume show where it started. A failure whose known issue says "do not retry" (for example `arc-device-id-name`) blocks the resume until you acknowledge the issue.

**Waiting.** The status is read every 15 s, growing by half each read to 120 s. Validate is given 90 minutes and Deploy 6 hours. At the limit the run ends in `ValidationTimedOut` or `DeploymentTimedOut` with exit 1; Azure keeps working and the next run **attaches** to it. Five failed reads in a row end the wait.

## When it fails

The run names the failing step with the number the portal shows (for example `0.41`), copies the step's error text (secrets removed), and looks it up in `config/known-issues/arm-deployment.json`:

| Id | Meaning | Retry |
|----|---------|-------|
| `arc-device-id-name` | Step *Deploy Arc infrastructure components*, `ParentResourceNotFound`: Arc machines named `<device-id>-1`, looked up by host name (build 2690) | no |
| `arc-device-id-name-step-0-41` | Any failure at step 0.41: rule the above out first | no |
| `unsupported-os-version` | "Unsupported OS version": a build the subscription does not accept, or nodes on different builds | after the fix |
| `registration-5901` | 403 on the target Arc machine soon after the role assignment | once, after a wait |
| `role-assignment-already-exists` | A portal attempt in the same resource group left the role assignment | after the fix |
| `role-assignment-zombie` | Role assignments of deleted resources remain | after the fix |
| `license-sync-after-failed-validate` | A second Validate after a failure | never Validate |
| `ad-prerequisites` | OU, LCM user, GPO or rights (pattern, not yet seen in a run) | after the fix |
| `dns-resolution` | The domain or an Azure endpoint does not resolve (pattern) | after the fix |
| `vmswitch-not-bound` | Stale validation switch data (Learn) | after the fix |

Add an entry when you understand a new failure; the run then explains it the next time.

**You get the whole reason, not a cut-off line.** Azure reports a failed validation step (for example `0.170` *ValidateCluster*) with a long text: the EnvironmentValidator results as JSON, and inside the Test-Cluster result the `[!!Failed!!]` and `[!!Warning!!]` lines with the sentences that say why. The run keeps all of it in `report.json` (`validate.failedSteps[]`: `errors`, `results`, `checks`, and the Test-Cluster report path on the node), in `summary.md`, and in the events. Only the console line is cut, and it always ends with the path of `report.json`. Secrets are removed from every text.

**Steps of an earlier run are not this run's.** The cluster resource keeps the steps of every earlier attempt until a new attempt runs them again. The run ignores a step older than the moment it submitted (by more than the allowed clock skew, `staleSkewMinutes`, 5) or one whose text names another deployment. Ignored steps are listed in `report.json` (`validate.ignoredSteps`), in `summary.md` and in one `StaleStepsIgnored` event; they are never the failing step.

| `<cluster>.parameters.json` | The ARM parameter file. Secrets are null in it |
| `parameter-sources.md` | Which key fed which parameter |

Exit codes: **0** the requested part succeeded (Plan clean; Validate passed; Deploy succeeded; ValidateAndDeploy stopped at the approval gate); **1** a precondition failed, or the validation or deployment failed or timed out; **2** bad input (a file or a required key missing, an unsupported design, no Azure sign-in when one is needed).

---

## What is verified, and what is not

Verified by the toolkit's tests with a fake Azure and a fake clock (no subscription touched): the parameters for AD and local identity, S2D and SAN, switchless and switched, 1, 2, 4 and 16 machines; every precondition with a passing and a failing case; the state machine; the wait including a 6 hour time-out; skip, attach, submit and resume decisions; the full failure text kept in the report; the steps of earlier runs ignored; the known-issue mapping on a fixture that copies a failure at step 0.41 on build 2690; the event feed, report, exit codes and secret scrubbing; and that the three pipeline files parse and carry the approval gate.

**Not verified, because it needs Azure or a machine** (state this until a lab run confirms it): that the real deployment status carries the step numbers and times the code reads; the real ARM states during a Deploy; that a resubmitted Deploy resumes at the failed step; the permissions, name-availability and provider REST calls; the Active Directory lookup; the pipelines on a real runner; and Linux runs of the modules this one imports. The first run on a lab instance is the acceptance test: Plan, Validate, then a Deploy that is allowed to fail.
