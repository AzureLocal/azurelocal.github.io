Task 05: Configure Environment Variables

DOCUMENT CATEGORY: Runbook Step
SCOPE: CI/CD pipeline variable configuration
PURPOSE: Configure environment variables for Azure authentication
MASTER REFERENCE: See platform-specific docs below

Status: Active

Objective​

Configure CI/CD pipeline environment variables for each target Azure subscription.

Prerequisites​

  • Environments created (Task 04)
  • The app registration from Task 01 (azure.automation_identity); with devops.authentication.method: client_secret, its secret in Key Vault, named by the reference in devops.authentication.client_secret

Values from infrastructure.yml​

No value of a deployment is written in a pipeline file. Every value the toolkit's pipelines read (the sign-in, the state, the runner, the approval environments, the infrastructure file and handoff paths, the tool versions and the job timeouts) is a key of infrastructure.yml (schema 5), and this task sets it on the platform. Run it again after you change the file. The script reads the devops (including devops.pipelines, devops.state and devops.runners[]), azure, deployment, key_vaults and landing_zone sections. A key that is not set takes its registry default. Each key, with its type, default and example, is in the variables reference.

Every variable the pipelines read​

On GitHub each is a repository variable (vars.NAME; the sign-in values also per environment), on GitLab a project CI/CD variable (scope *; the sign-in values also per environment), on Azure DevOps an entry of the variable group devops.pipelines.variable_group (one per environment, <name>-<environment>), a run parameter, or (the approval environments) a variable of pipelines/azure-devops/variables/approval-environments.yml.

Each name is registered in the toolkit's registry (tools.cicd_infra, as a pipeline_inputs or pipeline_variables entry with the key as source_key), and the table is $script:AzlPipelineVariable in scripts/common/cicd-infra/AzlCicdInfra.psm1. Nothing else is set by hand: no DOMAIN_ADMIN_PASSWORD, CLUSTER_NAME or CLUSTER_RESOURCE_GROUP, and no AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID or AZURE_AUTH (the pipelines read ARM_* and AZL_AUTH_METHOD).

The runner label and the approval environments of the pipelines​

From schema 5.6.25 the toolkit's pipeline files hold no runner label, agent pool or environment name. These keys give them:

KeyWhat it is
devops.pipelines.runner_labelThe one label by which the pipelines choose the general runner: runs-on on GitHub (after self-hosted and linux) and tags on GitLab. It must be an entry of devops.runners[].labels of the general runner, and a label no other runner of the repository has. Azure DevOps chooses the runner by its pool, devops.runners[].pool, and ignores this key.
devops.pipelines.environments.os_configurationThe environment that gates the Apply job of the OS configuration pipelines.
devops.pipelines.environments.os_configuration_clear_storageThe environment of the second approval in front of a storage wipe (stage ConfirmStorageWipe of the Azure DevOps OS configuration pipeline). Use other approvers than for os_configuration where you can.
devops.pipelines.environments.arm_deploymentThe environment that gates the Deploy job of the ARM deployment pipelines.
devops.pipelines.environments.cicd_infraThe environment that gates the Apply job of the CI/CD infrastructure pipelines (the runners).
devops.pipelines.environments.terraform_deploymentThe environment that gates the Terraform apply and the on-premises Ansible jobs of the Terraform and Ansible sample pipelines.

Each environment value is the name of an entry of devops.environments[] that has approval_required: true. Two pipelines may use the same entry.

The script sets them as GitHub repository variables or GitLab project CI/CD variables: AZL_RUNNER_LABEL and one AZL_ENVIRONMENT_... variable per pipeline. Azure DevOps reads the pool before any variable exists, so there it is a run parameter with no default, and the script prints the value to enter. A label that the general runner does not have, or an environment that devops.environments[] does not list with approval_required: true, stops the task.

On Azure DevOps the approval environments are not run parameters. With a run parameter, whoever queues a run could type the name of an environment with no approval check, and the change would run without an approval. So every Azure DevOps pipeline that changes something reads its environment from a variable of pipelines/azure-devops/variables/approval-environments.yml, a YAML file of the repository, when the pipeline is compiled. The toolkit ships the variables empty. The script cannot write that file. For each variable it lists the value to write there (action Pipeline variable template, status Skipped). Write them once, in a pull request:

Variable in approval-environments.ymlValue the script listsUsed by
AZL_ENVIRONMENT_OS_CONFIGURATIONdevops.pipelines.environments.os_configurationos-configuration.yml, stage Apply
AZL_ENVIRONMENT_OS_CONFIGURATION_CLEAR_STORAGEdevops.pipelines.environments.os_configuration_clear_storageos-configuration.yml, stage ConfirmStorageWipe
AZL_ENVIRONMENT_ARM_DEPLOYMENTdevops.pipelines.environments.arm_deploymentarm-deployment.yml, stage Deploy; pre-cluster-verification.yml, stage VerifyWithChanges
AZL_ENVIRONMENT_CICD_INFRAdevops.pipelines.environments.cicd_infracicd-infra.yml, stage Apply
AZL_ENVIRONMENT_TERRAFORM_DEPLOYMENTdevops.pipelines.environments.terraform_deploymentazure-local-deploy.yml, stages DeployFoundation, ConfigureOnPrem and ConfigureOperations

While a variable is empty, the stages that change something do not exist. A run that would change something fails in the stage ApprovalEnvironmentNotSet (for the storage wipe, ConfirmStorageWipe) and changes nothing. The read-only stages run as before. See Azure DevOps: Approval environments.

Create the variables (or run this task) before the first pipeline run. With AZL_RUNNER_LABEL empty, a job has no label to select a runner by. On GitLab, for the first run of the CI/CD infrastructure stage, before the runners exist, give AZL_RUNNER_LABEL a shared runner tag when you run the pipeline.

On GitLab, a person who starts a pipeline by hand can override a variable in the run form, AZL_ENVIRONMENT_ARM_DEPLOYMENT of the pre-cluster verification job included. Restrict who may set pipeline variables (project Settings > CI/CD > Variables, the minimum role to use pipeline variables) and protect the environment.

The service connection and the variable group (Azure DevOps)​

From schema 5.6.27 the Azure DevOps pipeline files hold no service connection or variable group name either. GitHub and GitLab ignore these keys.

KeyWhat it is
devops.pipelines.service_connectionThe name of the Azure Resource Manager service connection (workload identity federation) that task 05 creates and that the Azure DevOps pipelines sign in through. Task 01 puts the same name in the subject of the federated credential. Example: iic-azure-local.
devops.pipelines.variable_groupThe name of the variable group (Pipelines > Library) task 05 writes the sign-in values (ARM_*) and the state settings (TF_BACKEND_*) to. With entries in devops.environments[] there is one group per environment, named <variable_group>-<environment>. Example: iic-azure-credentials.

On Azure DevOps both keys are required: task 01 and task 05 stop with a message when one is missing. The pipelines take the names as run parameters with no default, and the script prints the values to enter. Before schema 5.6.27 the names were fixed (AzureLocal-ServiceConnection and azure-credentials). To keep what an earlier task 05 created, set the keys to those names.

Configure Repository Variables​

The script sets them. To check or set them by hand:

  1. Navigate to your repository → Settings → Secrets and variables → Actions
  2. On the Variables tab, click New repository variable for each variable of the table Every variable the pipelines read (the workflows read vars.NAME):
VariableValue
ARM_TENANT_IDazure.tenant_id
ARM_SUBSCRIPTION_IDazure.subscription_id
ARM_CLIENT_IDThe app registration client ID
AZL_AUTH_METHODdevops.authentication.method
  1. Only with devops.authentication.method: client_secret: on the Secrets tab, add ARM_CLIENT_SECRET with the value of the Key Vault secret devops.authentication.client_secret names.

Environment-Scoped Values​

The script also sets the sign-in values on each environment:

  1. Go to Settings → Environments → select environment (e.g. azr-prod-us)
  2. Under Environment variables (and Environment secrets for ARM_CLIENT_SECRET), add the values that differ per environment, such as ARM_SUBSCRIPTION_ID

Tip: Repository-level values apply to all environments. Environment values override them per environment.

Configure CI/CD Variables​

  1. Navigate to Settings → CI/CD
  2. Expand Variables
  3. The script adds each variable of the table Every variable the pipelines read with scope *, and the sign-in values also per environment. To add one by hand, click Add variable:
VariableConfiguration
ARM_TENANT_ID, ARM_SUBSCRIPTION_ID, ARM_CLIENT_ID
TypeVariable
Environments*, and the target environment for a value that differs
Flagsnone (identifiers)
Valueazure.tenant_id, azure.subscription_id, the app registration client ID
VariableConfiguration
ARM_CLIENT_SECRET (only with devops.authentication.method: client_secret)
TypeVariable
EnvironmentsSelect target environment
FlagsMasked
ValueThe Key Vault secret devops.authentication.client_secret names

With oidc the jobs sign in with the GitLab ID token ARM_OIDC_TOKEN and the federated credential Task 01 made; there is no secret.

Tip: Scope variables to specific environments to support multi-subscription deployments.

Create Variable Group​

The script creates the group. To create it by hand:

  1. Navigate to Pipelines → Library
  2. Click + Variable group
  3. Name it <variable_group>-<environment>, from devops.pipelines.variable_group (e.g. iic-azure-credentials-azr-prod-us). Without entries in devops.environments[] the name is devops.pipelines.variable_group alone.
  4. Add variables:
VariableValueLock
ARM_TENANT_IDEntra ID tenant ID🔒
ARM_SUBSCRIPTION_IDAzure subscription ID🔒
ARM_CLIENT_IDApp Registration client ID🔒
ARM_CLIENT_SECRETApp Registration client secret (only with devops.authentication.method: client_secret)🔒
TF_BACKEND_RG, TF_BACKEND_SA, TF_BACKEND_CONTAINER, TF_BACKEND_KEYThe Terraform state settings (table above)
AZL_AUTH_METHODdevops.authentication.method
AZL_DEFAULT_BRANCHdevops.repository.default_branch
AZL_TERRAFORM_VERSION, AZL_PYTHON_VERSION, AZL_ANSIBLE_CORE_VERSION, AZL_ANSIBLE_LINT_VERSION, AZL_AZ_POWERSHELL_VERSION, AZL_POWERSHELL_YAML_VERSION, AZL_AZ_KEYVAULT_VERSIONdevops.pipelines.tool_versions.*
AZL_RUNNER_SSH_PUBLIC_KEYdevops.runners[].admin_ssh_public_key of the Linux runner
  1. Click Save

With OIDC (workload identity federation) the script also creates the service connection named by devops.pipelines.service_connection. There is no client secret.

Link to Pipeline​

The toolkit's Azure DevOps pipelines take the group as a run parameter (variableGroup in azure-local-deploy.yml, variable_group in os-configuration.yml), and the service connection as serviceConnection, azureServiceConnection or service_connection. Enter the values the script prints when you run the pipeline. The pipeline file links the group like this:

variables:
  - group: ${{ parameters.variableGroup }}

Write the approval environments​

The approval environments are not in the variable group and are not run parameters. The script lists five values, one for each variable of pipelines/azure-devops/variables/approval-environments.yml:

VariableValue
AZL_ENVIRONMENT_OS_CONFIGURATIONdevops.pipelines.environments.os_configuration
AZL_ENVIRONMENT_OS_CONFIGURATION_CLEAR_STORAGEdevops.pipelines.environments.os_configuration_clear_storage
AZL_ENVIRONMENT_ARM_DEPLOYMENTdevops.pipelines.environments.arm_deployment
AZL_ENVIRONMENT_CICD_INFRAdevops.pipelines.environments.cicd_infra
AZL_ENVIRONMENT_TERRAFORM_DEPLOYMENTdevops.pipelines.environments.terraform_deployment

Write each value in that file, once, in a pull request. The pipelines read the file when they are compiled, so whoever queues a run cannot choose the environment. The file links into each pipeline like this:

variables:
  - template: variables/approval-environments.yml

Verification​

  • All required variables configured per environment
  • Sensitive values are masked/secret
  • Variables scoped to correct environments
  • Test pipeline can authenticate to Azure

Toolkit script

The toolkit script for this task is PowerShell 7. It reads infrastructure.yml through the mandatory -InfrastructureFile parameter and never prompts. It ends with exit code 0, 1 or 2. Run it with -WhatIf first: the script reads what exists and lists what it would do.

Script​

ScriptWhat it does
scripts/deploy/01-cicd-infra/phase-01-cicd-setup/task-05-configure-variables/powershell/Set-CicdVariables.ps1Task 05. Sets every value the toolkit's pipelines read, each from its key of infrastructure.yml: the sign-in, the state, the runner, the approval environments, the paths, the tool versions and the job timeouts. Supports -WhatIf.

Requires: PowerShell 7.

Run​

./Set-CicdVariables.ps1 -InfrastructureFile ./infrastructure.yml -WhatIf

Alternatives​

The procedures in this task use the methods shown in the tabs above. The toolkit is PowerShell 7 only and has no Bash scripts. A few tasks that act on Azure also have an Azure CLI script written in PowerShell. The script status page of the toolkit lists which task has which script.
