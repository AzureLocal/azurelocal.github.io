## Values from infrastructure.yml

**No value of a deployment is written in a pipeline file.** Every value the toolkit's pipelines read (the sign-in, the state, the runner, the approval environments, the infrastructure file and handoff paths, the tool versions and the job timeouts) is a key of `infrastructure.yml` (schema 5), and this task sets it on the platform. Run it again after you change the file. The script reads the `devops` (including `devops.pipelines`, `devops.state` and `devops.runners[]`), `azure`, `deployment`, `key_vaults` and `landing_zone` sections. A key that is not set takes its registry default. Each key, with its type, default and example, is in the [variables reference](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/docs/VARIABLES.md).

### Every variable the pipelines read

On GitHub each is a repository variable (`vars.NAME`; the sign-in values also per environment), on GitLab a project CI/CD variable (scope `*`; the sign-in values also per environment), on Azure DevOps an entry of the variable group `devops.pipelines.variable_group` (one per environment, `<name>-<environment>`), a run parameter, or (the approval environments) a variable of `pipelines/azure-devops/variables/approval-environments.yml`.

| Variable | Key in `infrastructure.yml` | GitHub | GitLab | Azure DevOps |
|---|---|---|---|---|
| `ARM_CLIENT_ID` | `azure.automation_identity.client_id` (else the app registration Task 01 made) | variable | variable | variable group |
| `ARM_TENANT_ID` | `azure.tenant_id` | variable | variable | variable group |
| `ARM_SUBSCRIPTION_ID` | `azure.subscription_id` | variable | variable | variable group |
| `ARM_USE_OIDC` (method `oidc`) or `ARM_CLIENT_SECRET` (method `client_secret`, read from `devops.authentication.client_secret`) | `devops.authentication.method` | variable / secret | variable / masked | variable group (secret) |
| `AZL_AUTH_METHOD` | `devops.authentication.method` (`oidc` or `client_secret`) | variable | variable | variable group |
| `TF_BACKEND_RG`, `TF_BACKEND_SA`, `TF_BACKEND_CONTAINER`, `TF_BACKEND_KEY` | `devops.state.resource_group`, `.storage_account`, `.container`, `.azure_local_key` | variable | variable | variable group |
| `AZL_RUNNER_LABEL` | `devops.pipelines.runner_label` | variable | variable | (the pool, a run parameter) |
| `AZL_RUNNER_OS` | `devops.runners[].os_type` of the general runner | variable | | |
| `AZL_ENVIRONMENT_OS_CONFIGURATION`, `_OS_CONFIGURATION_CLEAR_STORAGE` (Azure DevOps only), `_ARM_DEPLOYMENT`, `_CICD_INFRA`, `_TERRAFORM_DEPLOYMENT` | `devops.pipelines.environments.*` | variable | variable | the variable of the same name in `pipelines/azure-devops/variables/approval-environments.yml` (written once, in a pull request; see below) |
| `AZL_INFRASTRUCTURE_FILE` | `devops.pipelines.infrastructure_file` | variable | variable | (a run parameter) |
| `AZL_HANDOFF_PATH` | `devops.pipelines.handoff_path` | variable | variable | (a run parameter) |
| `AZL_TERRAFORM_VERSION`, `AZL_PYTHON_VERSION`, `AZL_ANSIBLE_CORE_VERSION`, `AZL_ANSIBLE_LINT_VERSION`, `AZL_AZ_POWERSHELL_VERSION`, `AZL_POWERSHELL_YAML_VERSION`, `AZL_AZ_KEYVAULT_VERSION` | `devops.pipelines.tool_versions.terraform`, `.python`, `.ansible_core`, `.ansible_lint`, `.az_powershell`, `.powershell_yaml`, `.az_keyvault` | variable | variable | variable group |
| `AZL_VALIDATE_JOB_TIMEOUT_MINUTES`, `AZL_DEPLOY_JOB_TIMEOUT_MINUTES` | `deployment.validate_timeout_minutes`, `deployment.deploy_timeout_minutes`, each plus 60 minutes | variable | | |
| `AZL_DEFAULT_BRANCH` | `devops.repository.default_branch` | | | variable group |
| `AZL_RUNNER_SSH_PUBLIC_KEY` | `devops.runners[].admin_ssh_public_key` of the Linux runner (the key, or a reference the script reads through the secret resolver) | variable | variable | variable group |

Each name is registered in the toolkit's registry (`tools.cicd_infra`, as a `pipeline_inputs` or `pipeline_variables` entry with the key as `source_key`), and the table is `$script:AzlPipelineVariable` in `scripts/common/cicd-infra/AzlCicdInfra.psm1`. Nothing else is set by hand: no `DOMAIN_ADMIN_PASSWORD`, `CLUSTER_NAME` or `CLUSTER_RESOURCE_GROUP`, and no `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID` or `AZURE_AUTH` (the pipelines read `ARM_*` and `AZL_AUTH_METHOD`).

### The runner label and the approval environments of the pipelines

From schema 5.6.25 the toolkit's pipeline files hold no runner label, agent pool or environment name. These keys give them:

| Key | What it is |
|-----|------------|
| `devops.pipelines.runner_label` | The one label by which the pipelines choose the general runner: `runs-on` on GitHub (after `self-hosted` and `linux`) and `tags` on GitLab. It must be an entry of `devops.runners[].labels` of the general runner, and a label no other runner of the repository has. Azure DevOps chooses the runner by its pool, `devops.runners[].pool`, and ignores this key. |
| `devops.pipelines.environments.os_configuration` | The environment that gates the Apply job of the OS configuration pipelines. |
| `devops.pipelines.environments.os_configuration_clear_storage` | The environment of the second approval in front of a storage wipe (stage `ConfirmStorageWipe` of the Azure DevOps OS configuration pipeline). Use other approvers than for `os_configuration` where you can. |
| `devops.pipelines.environments.arm_deployment` | The environment that gates the Deploy job of the ARM deployment pipelines. |
| `devops.pipelines.environments.cicd_infra` | The environment that gates the Apply job of the CI/CD infrastructure pipelines (the runners). |
| `devops.pipelines.environments.terraform_deployment` | The environment that gates the Terraform apply and the on-premises Ansible jobs of the Terraform and Ansible sample pipelines. |

Each environment value is the name of an entry of `devops.environments[]` that has `approval_required: true`. Two pipelines may use the same entry.

The script sets them as GitHub repository variables or GitLab project CI/CD variables: `AZL_RUNNER_LABEL` and one `AZL_ENVIRONMENT_...` variable per pipeline. Azure DevOps reads the pool before any variable exists, so there it is a run parameter with no default, and the script prints the value to enter. A label that the general runner does not have, or an environment that `devops.environments[]` does not list with `approval_required: true`, stops the task.

**On Azure DevOps the approval environments are not run parameters.** With a run parameter, whoever queues a run could type the name of an environment with no approval check, and the change would run without an approval. So every Azure DevOps pipeline that changes something reads its environment from a variable of `pipelines/azure-devops/variables/approval-environments.yml`, a YAML file of the repository, when the pipeline is compiled. The toolkit ships the variables empty. The script cannot write that file. For each variable it lists the value to write there (action `Pipeline variable template`, status `Skipped`). Write them once, in a pull request:

| Variable in `approval-environments.yml` | Value the script lists | Used by |
|---|---|---|
| `AZL_ENVIRONMENT_OS_CONFIGURATION` | `devops.pipelines.environments.os_configuration` | `os-configuration.yml`, stage `Apply` |
| `AZL_ENVIRONMENT_OS_CONFIGURATION_CLEAR_STORAGE` | `devops.pipelines.environments.os_configuration_clear_storage` | `os-configuration.yml`, stage `ConfirmStorageWipe` |
| `AZL_ENVIRONMENT_ARM_DEPLOYMENT` | `devops.pipelines.environments.arm_deployment` | `arm-deployment.yml`, stage `Deploy`; `pre-cluster-verification.yml`, stage `VerifyWithChanges` |
| `AZL_ENVIRONMENT_CICD_INFRA` | `devops.pipelines.environments.cicd_infra` | `cicd-infra.yml`, stage `Apply` |
| `AZL_ENVIRONMENT_TERRAFORM_DEPLOYMENT` | `devops.pipelines.environments.terraform_deployment` | `azure-local-deploy.yml`, stages `DeployFoundation`, `ConfigureOnPrem` and `ConfigureOperations` |

While a variable is empty, the stages that change something do not exist. A run that would change something fails in the stage `ApprovalEnvironmentNotSet` (for the storage wipe, `ConfirmStorageWipe`) and changes nothing. The read-only stages run as before. See [Azure DevOps: Approval environments](../../02-cicd-pipelines/azure-devops-pipelines.mdx#approval-environments).

Create the variables (or run this task) before the first pipeline run. With `AZL_RUNNER_LABEL` empty, a job has no label to select a runner by. On GitLab, for the first run of the CI/CD infrastructure stage, before the runners exist, give `AZL_RUNNER_LABEL` a shared runner tag when you run the pipeline.

On GitLab, a person who starts a pipeline by hand can override a variable in the run form, `AZL_ENVIRONMENT_ARM_DEPLOYMENT` of the pre-cluster verification job included. Restrict who may set pipeline variables (project **Settings > CI/CD > Variables**, the minimum role to use pipeline variables) and protect the environment.

### The service connection and the variable group (Azure DevOps)

From schema 5.6.27 the Azure DevOps pipeline files hold no service connection or variable group name either. GitHub and GitLab ignore these keys.

| Key | What it is |
|-----|------------|
| `devops.pipelines.service_connection` | The name of the Azure Resource Manager service connection (workload identity federation) that task 05 creates and that the Azure DevOps pipelines sign in through. Task 01 puts the same name in the subject of the federated credential. Example: `iic-azure-local`. |
| `devops.pipelines.variable_group` | The name of the variable group (Pipelines > Library) task 05 writes the sign-in values (`ARM_*`) and the state settings (`TF_BACKEND_*`) to. With entries in `devops.environments[]` there is one group per environment, named `<variable_group>-<environment>`. Example: `iic-azure-credentials`. |

On Azure DevOps both keys are required: task 01 and task 05 stop with a message when one is missing. The pipelines take the names as run parameters with no default, and the script prints the values to enter. Before schema 5.6.27 the names were fixed (`AzureLocal-ServiceConnection` and `azure-credentials`). To keep what an earlier task 05 created, set the keys to those names.

### The paths, the tool versions and the state key

From schema 5.6.28 (registry 5.0.62) the pipeline files hold no infrastructure file path, handoff path, tool version or state file name either. These keys are optional; a key the file leaves out takes its registry default:

| Key | What it is | Default |
|-----|------------|---------|
| `devops.pipelines.infrastructure_file` | The path, in the deployment repository, of the infrastructure file the pipelines pass to the scripts (`-InfrastructureFile`) | `config/infrastructure.yml` |
| `devops.pipelines.handoff_path` | The repository path of the ZTP handoff files (a handoff file or a directory of `*.ztp-handoff.json`) the OS configuration pipelines pass to the script | `ztp-state` |
| `devops.pipelines.tool_versions.terraform` | The Terraform release the pipelines install | `1.16.3` |
| `devops.pipelines.tool_versions.python` | The Python minor version of the Ansible jobs | `3.12` |
| `devops.pipelines.tool_versions.ansible_core` | The ansible-core release the Ansible jobs install with pip | `2.21.5` |
| `devops.pipelines.tool_versions.ansible_lint` | The ansible-lint release the lint jobs install with pip | `26.10.1` |
| `devops.pipelines.tool_versions.az_powershell` | The Az PowerShell module version | `16.3.0` |
| `devops.pipelines.tool_versions.powershell_yaml` | The powershell-yaml module version the pipelines install to read `infrastructure.yml` | `0.4.12` |
| `devops.pipelines.tool_versions.az_keyvault` | The Az.KeyVault module version the pipelines install to read `keyvault://` secrets | `6.6.1` |
| `devops.state.azure_local_key` | Blob name of the state of the `azure-local` Terraform environment (`TF_BACKEND_KEY`) | `azure-local.tfstate` |
| `devops.runners[].admin_ssh_public_key` | The SSH public key of the administrator of a Linux runner (`AZL_RUNNER_SSH_PUBLIC_KEY`): the key itself or a reference | |

The same versions are installed on GitHub, GitLab and Azure DevOps: `hashicorp/setup-terraform`, `actions/setup-python` and `Install-Module` on GitHub, `TerraformInstaller@1`, `UsePythonVersion` and `AzurePowerShell@5` on Azure DevOps, and `pipelines/gitlab/Use-AzlGitLabTool.ps1` on GitLab.

## Required Variables

The sign-in values, set for the repository and for **each** environment:

| Variable | Description | Sensitivity |
|----------|-------------|-------------|
| `ARM_TENANT_ID` | Entra ID tenant ID (`azure.tenant_id`) | Plain (an identifier) |
| `ARM_SUBSCRIPTION_ID` | Azure subscription ID (`azure.subscription_id`) | Plain (an identifier) |
| `ARM_CLIENT_ID` | App registration client ID (`azure.automation_identity`, from Task 01) | Plain (an identifier) |
| `ARM_USE_OIDC` | `true`, only with `devops.authentication.method: oidc` (no secret) | Plain |
| `ARM_CLIENT_SECRET` | Only with `devops.authentication.method: client_secret`: the script reads it from Key Vault (`devops.authentication.client_secret`); never typed in | Secret / masked |

With a state storage account in `devops.state`, the script also sets the Terraform state settings that the Azure DevOps, GitHub and GitLab pipelines pass to `terraform init`:

| Variable | Source | Sensitivity |
|----------|--------|-------------|
| `TF_BACKEND_RG` | `devops.state.resource_group` | Plain |
| `TF_BACKEND_SA` | `devops.state.storage_account` | Plain |
| `TF_BACKEND_CONTAINER` | `devops.state.container` | Plain |
| `TF_BACKEND_KEY` | `devops.state.azure_local_key`, the state file of the `azure-local` environment (the same key `New-IacVariableFiles.ps1` writes to `backend.hcl`) | Plain |

## Procedure

<TabItem value="github" label="GitHub" default>

### Configure Repository Variables

The script sets them. To check or set them by hand:

1. Navigate to your repository → **Settings** → **Secrets and variables** → **Actions**
2. On the **Variables** tab, click **New repository variable** for each variable of the table [Every variable the pipelines read](#every-variable-the-pipelines-read) (the workflows read `vars.NAME`):

| Variable | Value |
|-------------|-------|
| `ARM_TENANT_ID` | `azure.tenant_id` |
| `ARM_SUBSCRIPTION_ID` | `azure.subscription_id` |
| `ARM_CLIENT_ID` | The app registration client ID |
| `AZL_AUTH_METHOD` | `devops.authentication.method` |

3. Only with `devops.authentication.method: client_secret`: on the **Secrets** tab, add `ARM_CLIENT_SECRET` with the value of the Key Vault secret `devops.authentication.client_secret` names.

### Environment-Scoped Values

The script also sets the sign-in values on each environment:

1. Go to **Settings** → **Environments** → select environment (e.g. `azr-prod-us`)
2. Under **Environment variables** (and **Environment secrets** for `ARM_CLIENT_SECRET`), add the values that differ per environment, such as `ARM_SUBSCRIPTION_ID`

> **Tip:** Repository-level values apply to all environments. Environment values override them per environment.

</TabItem>
<TabItem value="gitlab" label="GitLab">

### Configure CI/CD Variables

1. Navigate to **Settings** → **CI/CD**
2. Expand **Variables**
3. The script adds each variable of the table [Every variable the pipelines read](#every-variable-the-pipelines-read) with scope `*`, and the sign-in values also per environment. To add one by hand, click **Add variable**:

| Variable | Configuration |
|----------|---------------|
| **ARM_TENANT_ID**, **ARM_SUBSCRIPTION_ID**, **ARM_CLIENT_ID** | |
| Type | `Variable` |
| Environments | `*`, and the target environment for a value that differs |
| Flags | none (identifiers) |
| Value | `azure.tenant_id`, `azure.subscription_id`, the app registration client ID |

| Variable | Configuration |
|----------|---------------|
| **ARM_CLIENT_SECRET** (only with `devops.authentication.method: client_secret`) | |
| Type | `Variable` |
| Environments | Select target environment |
| Flags | `Masked` |
| Value | The Key Vault secret `devops.authentication.client_secret` names |

With `oidc` the jobs sign in with the GitLab ID token `ARM_OIDC_TOKEN` and the federated credential Task 01 made; there is no secret.

> **Tip:** Scope variables to specific environments to support multi-subscription deployments.

</TabItem>
<TabItem value="azdo" label="Azure DevOps">

### Create Variable Group

The script creates the group. To create it by hand:

1. Navigate to **Pipelines** → **Library**
2. Click **+ Variable group**
3. Name it `<variable_group>-<environment>`, from `devops.pipelines.variable_group` (e.g. `iic-azure-credentials-azr-prod-us`). Without entries in `devops.environments[]` the name is `devops.pipelines.variable_group` alone.
4. Add variables:

| Variable | Value | Lock |
|----------|-------|------|
| `ARM_TENANT_ID` | Entra ID tenant ID | 🔒 |
| `ARM_SUBSCRIPTION_ID` | Azure subscription ID | 🔒 |
| `ARM_CLIENT_ID` | App Registration client ID | 🔒 |
| `ARM_CLIENT_SECRET` | App Registration client secret (only with `devops.authentication.method: client_secret`) | 🔒 |
| `TF_BACKEND_RG`, `TF_BACKEND_SA`, `TF_BACKEND_CONTAINER`, `TF_BACKEND_KEY` | The Terraform state settings (table above) | |
| `AZL_AUTH_METHOD` | `devops.authentication.method` | |
| `AZL_DEFAULT_BRANCH` | `devops.repository.default_branch` | |
| `AZL_TERRAFORM_VERSION`, `AZL_PYTHON_VERSION`, `AZL_ANSIBLE_CORE_VERSION`, `AZL_ANSIBLE_LINT_VERSION`, `AZL_AZ_POWERSHELL_VERSION`, `AZL_POWERSHELL_YAML_VERSION`, `AZL_AZ_KEYVAULT_VERSION` | `devops.pipelines.tool_versions.*` | |
| `AZL_RUNNER_SSH_PUBLIC_KEY` | `devops.runners[].admin_ssh_public_key` of the Linux runner | |

5. Click **Save**

With OIDC (workload identity federation) the script also creates the service connection named by `devops.pipelines.service_connection`. There is no client secret.

### Link to Pipeline

The toolkit's Azure DevOps pipelines take the group as a run parameter (`variableGroup` in `azure-local-deploy.yml`, `variable_group` in `os-configuration.yml`), and the service connection as `serviceConnection`, `azureServiceConnection` or `service_connection`. Enter the values the script prints when you run the pipeline. The pipeline file links the group like this:

```yaml
variables:
  - group: ${{ parameters.variableGroup }}
```

### Write the approval environments

The approval environments are not in the variable group and are not run parameters. The script lists five values, one for each variable of `pipelines/azure-devops/variables/approval-environments.yml`:

| Variable | Value |
|----------|-------|
| `AZL_ENVIRONMENT_OS_CONFIGURATION` | `devops.pipelines.environments.os_configuration` |
| `AZL_ENVIRONMENT_OS_CONFIGURATION_CLEAR_STORAGE` | `devops.pipelines.environments.os_configuration_clear_storage` |
| `AZL_ENVIRONMENT_ARM_DEPLOYMENT` | `devops.pipelines.environments.arm_deployment` |
| `AZL_ENVIRONMENT_CICD_INFRA` | `devops.pipelines.environments.cicd_infra` |
| `AZL_ENVIRONMENT_TERRAFORM_DEPLOYMENT` | `devops.pipelines.environments.terraform_deployment` |

Write each value in that file, once, in a pull request. The pipelines read the file when they are compiled, so whoever queues a run cannot choose the environment. The file links into each pipeline like this:

```yaml
variables:
  - template: variables/approval-environments.yml
```
