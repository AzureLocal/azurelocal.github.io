## Deployment Paths

| Path | Azure Resources | On-Premises / Guest Configuration | Best For |
|------|:-:|:-:|---|
| **Terraform + PowerShell** | Terraform | PowerShell scripts | Teams with existing PowerShell operational workflows |
| **Terraform + Ansible** | Terraform | Ansible playbooks | Teams preferring declarative configuration management |
| **Ansible Only** | `azure.azcollection` | Ansible playbooks | Teams standardizing on Ansible across cloud and on-premises |
| **PowerShell scripts from one `infrastructure.yml`** | ARM Validate and Deploy script | OS configuration script | Teams that provision with azurelocal-ztp (or an ISO), then configure and deploy from a jump server or a pipeline: [OS configuration](../implementation/04-cluster-deployment/phase-03-os-configuration/automated-os-configuration.mdx), then [ARM Validate and Deploy](./03-automation-guides/arm-validate-deploy.mdx) |

## Why the Guide Is Split into Sections

- **CI/CD Infrastructure** covers the platform you must build first: source control project, environments, variables, and runners.
- **CI/CD Pipelines** covers the delivery engine you choose to run on that platform: GitLab, GitHub Actions, or Azure DevOps.
- **Automation Guides** covers the technical assets those pipelines call: Terraform, Ansible, Bicep, and PowerShell.

This separation keeps platform setup, delivery orchestration, and tool implementation from being mixed together on the same level of the sidebar.

## Architecture

:::info One input model
Every tool reads the **master `infrastructure.yml`** (schema 5, current version 5.6.21): the toolkit scripts, azurelocal-ztp, azurelocal-sonar, OS configuration, ARM Validate and Deploy, Terraform and Ansible. The file, its schema, its templates and its variables reference are generated from the toolkit's master registry (`config/variables/schema/master-registry.yaml`), and a new variable is added to the registry first. Secrets are never in the file: a secret key holds only a reference (`keyvault://<vault>/<secret>`, `env://<VARIABLE>`, `file://<name>` or `command://<name>`).
:::

```
┌─────────────────────────────────────────────────────────────────────┐
│                         infrastructure.yml                          │

└────────────┬───────────────────┬──────────────────┬─────────────────┘
             │                   │                  │
     New-IacVariableFiles.ps1  (same script)   Import-AzlInfrastructure
             │                   │                  │
             ▼                   ▼                  ▼
  terraform.tfvars.json    inventory/hosts.yml,   PowerShell scripts,
  and backend.hcl          group_vars, host_vars  ZTP, Sonar, ARM

```

## Variable System

One master file feeds every tool. The Terraform and Ansible variable files are written from it:

```powershell
./config/variables/scripts/New-IacVariableFiles.ps1 -InfrastructureFile ./infrastructure.yml -OutputDirectory D:\work\iac -WhatIf
```

`New-IacVariableFiles.ps1` writes `terraform.tfvars.json` and `backend.hcl` for each Terraform environment and `inventory/hosts.yml`, `group_vars/all.yml` and `host_vars/<node>.yml` for Ansible. Every variable of the code says in the registry which key it comes from. A secret is never written to a file. See [Variable Management](https://azurelocal.cloud/standards/variables).

## Repository

All automation code lives in the [azurelocal-toolkit](https://github.com/AzureLocal/azurelocal-toolkit) repository:

| Directory | Contents |
|---|---|
| `src/terraform/` | Terraform modules and root environment |
| `src/ansible/` | Ansible roles, playbooks, and inventory |
| `pipelines/` | CI/CD pipeline definitions: Terraform and Ansible deploy, CI/CD infrastructure, OS configuration, and ARM Validate and Deploy |
| `scripts/deploy/` | PowerShell deployment scripts |
| `config/variables/` | Central variable system: the master registry, the `infrastructure.yml` schema, templates and the generated variables reference |
| `docs/` | Operator guides for OS configuration and ARM Validate and Deploy, with their design and audit |
