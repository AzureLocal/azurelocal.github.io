ARM Validate and Deploy automation

DOCUMENT CATEGORY: Reference SCOPE: Automating the cluster ARM Validate and Deploy step (implementation Phase 05) PURPOSE: Run Microsoft's quickstart template through Validate, approval and Deploy with one command, on a jump server or in a pipeline MASTER REFERENCE: azurelocal-toolkit: ARM Validate and Deploy run guide

Status: Active Validated against: the toolkit's docs/arm-deployment-guide.md on main, and Microsoft Learn view azloc-2610

Overview​

After the machines are provisioned (ZTP or an ISO install) and their operating system is configured, the cluster is created by an ARM deployment: Microsoft's quickstart template (Microsoft.AzureStackHCI/clusters with deploymentSettings), run first in Validate mode and then in Deploy mode. The toolkit automates that step with Invoke-AzureLocalArmDeployment.ps1, which works the same on a jump server and in GitHub Actions, GitLab CI or Azure DevOps.

infrastructure.yml  +  OS configuration report  +  ZTP handoff (optional)
    -> Plan (preconditions) -> Validate -> approval -> Deploy -> report, events, exit code

It covers Active Directory or local identity; Storage Spaces Direct, a Fibre Channel SAN, or hybrid (deployed as Storage Spaces Direct, the SAN connected afterwards); switchless or switched storage; and 1 to 16 machines. Running it twice is safe.

This page automates the manual routes in Phase 05: Cluster Deployment (portal and ARM template). The manual runbooks stay the reference for each Azure setting.

Where it sits in the flow​

OrderStagePage
1Provisioning: azurelocal-ztp (ends at the Handoff) or an ISO installSimplified provisioning automation
2OS configuration of every node (plan, approval, apply, verify; writes report.json)Automated OS configuration
3Pre-cluster verification gateBelow
4ARM Validate, approval, ARM DeployThis page
5Post-deployment tasksPhase 06

What it does​

  1. Reads the master infrastructure.yml, the OS configuration report and, if you have one, the ZTP handoff.
  2. Generates every parameter of the right Microsoft template for your design and shows which file key fed which parameter.
  3. Checks readiness, read-only (see What it checks first).
  4. Validates and waits (10 to 30 minutes), reading Microsoft's step list as it goes.
  5. Waits for approval. A pipeline has the platform's approval gate between the Validate job and the Deploy job.
  6. Deploys and waits (2.5 to 3 hours).
  7. Explains a failure: the failing step with the number the portal shows, the error text, the matching known issue with its cause and remediation, and what may be retried.
  8. Reports: an event feed (JSON Lines), report.json, summary.md and an exit code of 0, 1 or 2.

It is idempotent. A Validate that already passed with the same parameters isn't run again. A deployment that is running is attached to, not duplicated. A deployment that failed is resubmitted only when you pass -Resume, because Microsoft warns that another Validate after a failure can break license sync.

Pre-cluster verification gate​

The toolkit defines a pre-cluster verification gate: a stage that runs after OS configuration and before the cluster ARM Validate.

Gate details are pending in the toolkit

The gate's own run guide, docs/pre-cluster-verification.md in the azurelocal-toolkit repository, had not landed on the toolkit's main branch when this page was written (2026-11-08), and docs/arm-deployment-guide.md does not describe it. To avoid inventing behaviour, this page does not list the gate's other checks, parameters, outputs or exit codes (the SBE package checks below are the exception). Take them from that document once it is on main, and update this section in the same change. Open item for the documentation owner.

The SBE package checks​

The hardware vendor's Solution Builder Extension (SBE) package is a requirement. Download it for your hardware model and the Azure Local version you deploy before you start, and make it available on a share the automation can read (hardware.sbe.source_path). You need it to update the cluster, and the gate reads it from the share and checks it before the cluster is created. To install it during the build, switch on the side-load (hardware.sbe.delivery); it is off by default.

The gate checks SB-001 to SB-006, and all of them block:

CheckWhat it verifies
SB-001The package source is configured, or declared not applicable with a reason (hardware.sbe.requirement, hardware.sbe.not_applicable_reason)
SB-002The share is reachable
SB-003The three files are present: SBE_Discovery_<Vendor>.xml, SBE_<Vendor>_<Family>_<Version>.xml and the payload zip
SB-004The hashes show the files are unmodified
SB-005The hardware model of every node is listed in the package's own supported models (a 17G Intel package fails on AX-760 nodes; the right one is 16G-45n0c-Intel 5.0.2609.1611)
SB-006The version is validated for the target solution version (Dell on 2610: 12.2610.1004.x)

The update later reuses the same share: Add-SolutionUpdate, then Start-SolutionUpdate (see Import and rediscover updates on Microsoft Learn). The keys, the vendor differences and the full wording are in the SBE package prerequisite.

What is already documented and checked on main before Validate:

  • The OS configuration run ends with a verify pass and a per-node converged result in report.json (a node is converged only when nothing is left to change). See How the run works.
  • Invoke-AzureLocalArmDeployment.ps1 re-checks, read-only and in -Mode Plan, the conditions listed in What it checks first, including OsConfigurationConverged (the report says every node converged for this cluster), OsBuildConsistent, DnsAndTime, ArcMachinesConnected and ArcMachineNaming.
  • The Environment Checker validators are a separate, manual readiness assessment: Task 05: Environment Checker Readiness. Azure also runs them itself during Validate.

Run it from a jump server​

You need PowerShell 7 on Windows or Linux, the powershell-yaml, Az.Accounts and Az.KeyVault modules, and a sign-in. The script does not sign in.

Connect-AzAccount            # or: Connect-AzAccount -Identity   (an Azure VM with a managed identity)

$arm    = './scripts/deploy/04-cluster-deployment/phase-05-cluster-deployment/Invoke-AzureLocalArmDeployment.ps1'
$common = @{ InfrastructureFile = './infrastructure.yml'; OsConfigurationReport = './osconfig-report' }

& $arm @common -Mode Plan     -ReportDirectory ./arm-plan        # reads only; add -Offline to touch no Azure at all
& $arm @common -Mode Validate -ReportDirectory ./arm-validate    # 10 to 30 minutes
& $arm @common -Mode Deploy   -ReportDirectory ./arm-deploy      # 2.5 to 3 hours, only after a Validate of these parameters

-Mode ValidateAndDeploy does the last two in one run with a gate between them (-ApprovalMode stop|prompt|none). The default, stop, ends after a good Validate in state AwaitingApproval with exit code 0; run -Mode Deploy to continue. -WhatIf does everything except submit.

ParameterMeaning
-InfrastructureFileThe master file (schema 5). Required
-OsConfigurationReportThe OS configuration run's report.json, a node-level report, or its report directory. Gives the OS names of the network ports (found by MAC), the SAN disks (a LUN number becomes the disk's UniqueId), and proves every node converged
-HandoffFileThe ZTP handoff: Arc machine resource IDs and the solution build
-ModePlan (default), Validate, Deploy, ValidateAndDeploy
-ReportDirectoryWhere the events, report, summary and parameter files go. Not for a repository
-ResumeResubmit a failed Deploy (and attach to a running one)
-AcknowledgeKnownIssuesKnown issue ids you accept, for example arc-device-id-name
-Settings, -ConfigPathRun settings as a hashtable or JSON file; they win over the master file's deployment block
-AllowRevalidateValidate an instance in a failed deployment state. Microsoft says not to; support-guided recovery only
-RegisterResourceProvidersOpt in: register the mandatory resource providers that are not registered and wait until they are Registered (Validate and Deploy only). Without it the run never changes Azure
-TemplateFileA local copy of the quickstart template instead of the download
-OfflinePlan only: no Azure call at all

Run it from a pipeline​

Copy the file for your platform. Each runs the same script: preconditions (Plan), then Validate, then Deploy behind the platform's approval, and publishes report.json, summary.md and the event feed of every job. No client secret is stored anywhere; the files hold placeholders only, and you set the real values as variables of the project.

PlatformFile in the toolkitJobs or stagesApprovalSign-in
GitHub Actionspipelines/github-actions/arm-deployment.yml (copy to .github/workflows/)preconditions, validate, deployEnvironment azure-local-deploy with required reviewersazure/login, OIDC
GitLab CIpipelines/gitlab/stages/arm-deployment.yml (declares its own stages, include it from a pipeline of its own)arm-preconditions, arm-validate, arm-deployarm-deploy is a manual job in the protected environment azure-local-deployid_tokens and a federated token, or a managed identity
Azure DevOpspipelines/azure-devops/arm-deployment.ymlStages Preconditions, Validate, DeployApprovals check on the environment azure-local-deployA service connection with workload identity federation

Pipeline inputs: the mode (Plan, Validate, ValidateAndDeploy, Deploy), the path of infrastructure.yml, the OS configuration report (the artifact of the OS configuration pipeline, or a repository path), the optional ZTP handoff, resume, and the known issue ids to acknowledge.

  • Use a self-hosted runner that reaches Azure over HTTPS (Linux with PowerShell 7 is enough). The Active Directory check also needs a domain-joined runner with the ActiveDirectory module; on any other runner it is reported as Skipped, never as passed.
  • The Deploy job re-runs every precondition and checks that these parameters were validated (the Validate's ARM deployment is named from a hash of the parameters), so an approval cannot start a Deploy of something that was never validated. The reviewer reads the Validate job's summary.md.
  • Passwords are read from the Key Vaults named by the keyvault:// references in the master file. The identity needs Get on those secrets.

The OS configuration step has its own pipelines (pipelines/github/os-configuration.yml, pipelines/gitlab/os-configuration.gitlab-ci.yml, pipelines/azure-devops/os-configuration.yml) with an approval before apply: see the pipeline pages for GitHub Actions, GitLab CI/CD and Azure DevOps.

What it checks first​

All checks are read-only. Each is Passed, Failed (stops the run, exit 1), Warning, or Skipped (with the reason). The report lists all of them. Skip a check on purpose with deployment.skip_preconditions; it still appears as Skipped.

The mandatory resource providers​

The 13 providers are the list in Microsoft Learn, Assign required permissions for Azure Local deployment: Microsoft.HybridCompute, Microsoft.GuestConfiguration, Microsoft.HybridConnectivity, Microsoft.AzureStackHCI, Microsoft.Kubernetes, Microsoft.KubernetesConfiguration, Microsoft.ExtendedLocation, Microsoft.ResourceConnector, Microsoft.HybridContainerService, Microsoft.Attestation, Microsoft.Storage, Microsoft.Insights and Microsoft.KeyVault. A provider that is Registering still counts as missing until it is Registered.

Registration is opt in. By default the run reads and never changes Azure. Pass -RegisterResourceProviders (or set deployment.register_resource_providers: true) to let a Validate or Deploy run register what is missing. It asks once per provider and reads their state every 10 seconds for up to 15 minutes. Plan mode and -WhatIf never change Azure. It needs Owner or Contributor on the subscription.

Passing the Solution Builder Extension to the deployment is opt-in​

The SBE package must be downloaded and available on the share (see the SBE package checks); what is optional is handing an SBE to the ARM deployment and side-loading it at build time. A deployment without an SBE is a normal deployment. When hardware.sbe is absent, or has no version, the run passes none of the seven SBE parameters of Microsoft's template (sbeVersion, sbeFamily, sbePublisher, sbeManifestSource, sbeManifestCreationDate, partnerProperties, partnerCredentiallist). An SBE is passed only when hardware.sbe.version is set. If Azure still names an SBE problem in a run without an SBE (the nodes carry a package in C:\SBE), the known issue sbe-referenced-but-not-configured says so and offers both ways out.

What it builds from the master file​

parameter-sources.md in the report directory shows, for your scenario, which infrastructure.yml key fed each ARM parameter. A required value that is empty ends the run (exit 2) with a message such as:

ARM parameter adouPath (required when scenario.identity is active_directory) needs identity.active_directory.ou_path in infrastructure.yml, and it is empty.

All missing keys are listed at once. A design the generator does not support yet (iSCSI SAN, disconnected operations, Azure Government with local identity or a SAN, rack aware with a SAN or local identity) stops with exit 2 and says so.

Re-running, resuming, waiting​

Found in AzureValidateDeploy
NothingSubmitsRefused: validate first
Validated with these parametersNot submitted againSubmits
A validation of these parameters runningAttaches and waitsRefused
A deployment runningRefusedAttaches and waits
A failed deploymentRefused (Microsoft: another Validate can break license sync)Refused, unless -Resume
A succeeded deploymentRefusedReports it, submits nothing

Resume. The portal has Resume deployment. For the ARM route Microsoft documents a second submission with the same parameters and deploymentMode Deploy; -Resume does that, under the same deployment name. Whether Azure continues at the failed step or restarts is not documented for the ARM route; the first step events after a resume show where it started. A failure whose known issue says "do not retry" (for example arc-device-id-name) blocks the resume until you acknowledge the issue.

Waiting. The status is read every 15 s, growing by half each read to 120 s. Validate is given 90 minutes and Deploy 6 hours. At the limit the run ends in ValidationTimedOut or DeploymentTimedOut with exit 1; Azure keeps working and the next run attaches to it. Five failed reads in a row end the wait.

When it fails​

The run names the failing step with the number the portal shows (for example 0.41), copies the step's error text (secrets removed), and looks it up in config/known-issues/arm-deployment.json:

IdMeaningRetry
arc-device-id-nameStep Deploy Arc infrastructure components, ParentResourceNotFound: Arc machines named <device-id>-1, looked up by host name (build 2690)no
arc-device-id-name-step-0-41Any failure at step 0.41: rule the above out firstno
unsupported-os-version"Unsupported OS version": a build the subscription does not accept, or nodes on different buildsafter the fix
registration-5901403 on the target Arc machine soon after the role assignmentonce, after a wait
role-assignment-already-existsA portal attempt in the same resource group left the role assignmentafter the fix
role-assignment-zombieRole assignments of deleted resources remainafter the fix
license-sync-after-failed-validateA second Validate after a failurenever Validate
ad-prerequisitesOU, LCM user, GPO or rights (pattern, not yet seen in a run)after the fix
dns-resolutionThe domain or an Azure endpoint does not resolve (pattern)after the fix
vmswitch-not-boundStale validation switch data (Learn)after the fix

Add an entry when you understand a new failure; the run then explains it the next time.

You get the whole reason, not a cut-off line. Azure reports a failed validation step (for example 0.170 ValidateCluster) with a long text: the EnvironmentValidator results as JSON, and inside the Test-Cluster result the [!!Failed!!] and [!!Warning!!] lines with the sentences that say why. The run keeps all of it in report.json (validate.failedSteps[]: errors, results, checks, and the Test-Cluster report path on the node), in summary.md, and in the events. Only the console line is cut, and it always ends with the path of report.json. Secrets are removed from every text.

Steps of an earlier run are not this run's. The cluster resource keeps the steps of every earlier attempt until a new attempt runs them again. The run ignores a step older than the moment it submitted (by more than the allowed clock skew, staleSkewMinutes, 5) or one whose text names another deployment. Ignored steps are listed in report.json (validate.ignoredSteps), in summary.md and in one StaleStepsIgnored event; they are never the failing step.

What you get​

FileFor
arm-deployment-events.jsonlOne JSON line per event (timestamp, node, stage, step, state, evidence, level, nextAction plus data). Sonar can follow it
report.jsonResult, state history, every precondition, validation and deployment sections, failing steps, known issue, approval
summary.mdThe same for a person; the job summary in a pipeline
<cluster>.parameters.jsonThe ARM parameter file. Secrets are null in it
parameter-sources.mdWhich key fed which parameter

Exit codes: 0 the requested part succeeded (Plan clean; Validate passed; Deploy succeeded; ValidateAndDeploy stopped at the approval gate); 1 a precondition failed, or the validation or deployment failed or timed out; 2 bad input (a file or a required key missing, an unsupported design, no Azure sign-in when one is needed).

What is verified, and what is not​

Verified by the toolkit's tests with a fake Azure and a fake clock (no subscription touched): the parameters for AD and local identity, S2D and SAN, switchless and switched, 1, 2, 4 and 16 machines; every precondition with a passing and a failing case; the state machine; the wait including a 6 hour time-out; skip, attach, submit and resume decisions; the full failure text kept in the report; the steps of earlier runs ignored; the known-issue mapping on a fixture that copies a failure at step 0.41 on build 2690; the event feed, report, exit codes and secret scrubbing; and that the three pipeline files parse and carry the approval gate.

Not verified, because it needs Azure or a machine (state this until a lab run confirms it): that the real deployment status carries the step numbers and times the code reads; the real ARM states during a Deploy; that a resubmitted Deploy resumes at the failed step; the permissions, name-availability and provider REST calls; the Active Directory lookup; the pipelines on a real runner; and Linux runs of the modules this one imports. The first run on a lab instance is the acceptance test: Plan, Validate, then a Deploy that is allowed to fail.
