# Task 04: Enable Security Logging

[![Runbook](https://img.shields.io/badge/Type-Runbook-blue?style=flat-square)](./index.mdx)
[![Azure](https://img.shields.io/badge/Platform-Azure_Local-0078D4?style=flat-square&logo=microsoftazure)](https://learn.microsoft.com/en-us/azure/azure-local/)

> **DOCUMENT CATEGORY**: Runbook   
> **SCOPE**: Security event collection   
> **PURPOSE**: Configure Data Collection Rules for security logs   
> **MASTER REFERENCE**: [Microsoft Learn - DCR](https://learn.microsoft.com/en-us/azure/azure-monitor/essentials/data-collection-rule-overview) and [Collect Windows events](https://learn.microsoft.com/azure/azure-monitor/vm/data-collection-windows-events#configure-windows-event-data-source)

**Status**: Active

Security logging provides visibility into security events across your Azure Local infrastructure. This step configures a Data Collection Rule (DCR) that collects the Windows Security, System and Application event logs from the Arc-enabled machines and sends them to the **Event** table of a Log Analytics workspace.

:::info Azure Monitor Agent
Azure Monitor Agent (AMA) is the recommended agent for log collection, replacing the legacy Log Analytics agent (MMA). DCRs define what data to collect and where to send it.
:::

:::note The Event table, not SecurityEvent
Learn: when you select the **Security** log in a data collection rule, the events go to the [Event](https://learn.microsoft.com/azure/azure-monitor/reference/tables/event) table with the events of the other logs ([Collect Windows events from virtual machine with Azure Monitor](https://learn.microsoft.com/azure/azure-monitor/vm/data-collection-windows-events#configure-windows-event-data-source)). Learn names a different route to the `SecurityEvent` table: the *Windows Security Events via AMA* connector of Microsoft Sentinel, which uses the same agent and collects the same events but sends them to `SecurityEvent`. Sentinel is a separate product that this task does not set up. Query the Security log with `Event | where EventLog == "Security"`.
:::

## Overview

| Log Type | Source | Purpose |
|----------|--------|---------|
| **Windows event logs** (Security, System, Application) | Windows Event Log | Authentication, authorization, policy changes, system and application errors |
| **Syslog** | Linux systems | System and security events |
| **Performance Counters** | OS metrics | Resource utilization and anomaly detection |
| **Custom Logs** | Application logs | Application-specific security events |

## Prerequisites

- Log Analytics workspace created in Stage 06
- Azure Monitor Agent deployed (or will deploy via DCR)
- Arc-enabled servers registered (or will be during cluster deployment)

## Values from infrastructure.yml

The values for this task come from `infrastructure.yml` (schema 5). Every key, with its type, default and example, is in the [variables reference](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/docs/VARIABLES.md).

## What the rule collects

A plain data collection rule has no Minimal, Common or All tiers: those event sets belong to the Microsoft Sentinel connector ([Windows security event sets that can be sent to Microsoft Sentinel](https://learn.microsoft.com/azure/sentinel/windows-security-event-id-reference)). A rule that you create here chooses the logs and, for each, what it collects:

| Log | Choice in the portal | Key in `infrastructure.yml` |
|-----|----------------------|-------------------------------|
| **Security** | Audit success and Audit failure, or Audit failure only | `operations.security_logging.security_audit`: `success_and_failure` (the default) or `failure` |
| **System** and **Application** | The levels Critical, Error, Warning, Information, Verbose | `operations.security_logging.event_levels`: any of `critical`, `error`, `warning`, `information`, `verbose` (the default is `critical`, `error`, `warning`) |

Learn recommends at least Critical, Error and Warning for System and Application, and Information when you want trends. Verbose events are rarely useful. Every node is billed for the data its events add to the workspace, so collect only what you need. For finer filtering by event ID, use a custom rule with XPath queries.

### Create Data Collection Rule for Security Events

1. **Navigate to Data Collection Rules**
 - In Azure Portal, search for **Data collection rules**
 - Click **+ Create**

2. **Configure Basics**
 - **Rule Name**: `dcr-security-events-prod-eus2`
 - **Subscription**: Select your subscription
 - **Resource Group**: `rg-management-prod-eastus2`
 - **Region**: Same as Log Analytics workspace
 - **Platform Type**: Windows (or All for both Windows and Linux)

3. **Add Resources (Optional)**
 - Click **+ Add resources**
 - Select Arc-enabled servers (if already registered)
 - Or leave empty to assign later during cluster deployment

4. **Configure Data Sources**

 **Windows Security Events:**
 - Click **+ Add data source**
 - **Data source type**: Windows Event Logs
 - **Configure**: Select **Security** under Windows event logs
 - Click **Add data source**

 **Windows Event Logs:**
 - Click **+ Add data source**
 - **Data source type**: Windows Event Logs
 - Check: **System**, **Application**
 - Configure XPath queries for specific events (optional)

5. **Configure Destination**
 - Click **+ Add destination**
 - **Destination type**: Azure Monitor Logs
 - **Subscription**: Select your subscription
 - **Destination**: Select your Log Analytics workspace

6. **Review and Create**
 - Click **Review + create**
 - Click **Create**

### Create Syslog Collection Rule (Linux)

1. **Create New DCR for Linux**
 - **Rule Name**: `dcr-syslog-security-prod-eus2`
 - **Platform Type**: Linux

2. **Add Syslog Data Source**
 - Click **+ Add data source**
 - **Data source type**: Linux Syslog
 - Configure facilities:
 - `auth` - LOG_WARNING and above
 - `authpriv` - LOG_WARNING and above
 - `syslog` - LOG_WARNING and above
 - `daemon` - LOG_ERR and above

3. **Add Destination**
 - Select your Log Analytics workspace
 - Click **Create**

### PowerShell

> **When to use**: Create the rule and associate it with the Arc machine of every node, from a management host. The script is idempotent. The earlier `Set-SecurityLogging.ps1` is removed: Microsoft Learn documents no supported way to change the audit policies of Azure Local with a script. The audit policy itself belongs to the security baseline on the nodes, which is changed with `Set-AzsSecurity` (see [Task 03: Configure security baselines](./task-03-configure-security-baselines.mdx)).

#### Script

| Script | What it does |
|---|---|
| `scripts/deploy/05-operational-foundations/phase-04-security-governance/task-04-enable-security-logging/powershell/Invoke-SecurityLogging-Orchestrated.ps1` | Creates the data collection rule `operations.security_logging.data_collection_rule` (a `windowsEventLogs` data source on the `Microsoft-Event` stream, sent to the Log Analytics workspace of `operations.monitoring`, so into the Event table) and one association with the Arc machine of every node, named `<machine>-<rule>`. First it checks, read only, that `operations.monitoring.enabled` is true, that the workspace exists and that the Azure Monitor Agent extension is on the instance. A rule that exists is checked and never changed: when it sends to another workspace or collects other queries than the file says, the run fails and no node is associated. Supports `-WhatIf`. |

Parameters: `-InfrastructureFile` (required) and `-LogPath`. With `operations.security_logging.enabled` false or absent the script does nothing and exits 0. It does not sign in: run `Connect-AzAccount -Tenant <azure.tenant_id>` first. You need Monitoring Contributor on the workspace resource group and on the Arc machines, and Log Analytics Contributor on the workspace. Exit 0: the rule and every association are in place (created now, already there, planned under `-WhatIf`, or not asked for). Exit 1: an Azure call or a precondition failed. Exit 2: a value in the file is missing or not usable; nothing is sent to Azure.

The keys it reads: `operations.security_logging.enabled`, `data_collection_rule`, `security_audit` and `event_levels`, with `operations.monitoring.log_analytics_workspace` and `workspace_resource_group`.

#### Run

```powershell
Connect-AzAccount -Tenant <azure.tenant_id>

./Invoke-SecurityLogging-Orchestrated.ps1 -InfrastructureFile ./infrastructure.yml -WhatIf
./Invoke-SecurityLogging-Orchestrated.ps1 -InfrastructureFile ./infrastructure.yml
```

## Validation

```powershell
# Verify DCR exists
$dcr = Get-AzDataCollectionRule -ResourceGroupName $resourceGroup -Name $dcrName

if ($dcr) {
 Write-Host "✅ DCR exists: $($dcr.Name)" -ForegroundColor Green
 Write-Host " Location: $($dcr.Location)"
 Write-Host " Data Sources: $($dcr.DataSource.WindowsEventLog.Count) Windows Event Logs"
} else {
 Write-Host "❌ DCR not found" -ForegroundColor Red
}

# Query Log Analytics for security events (after data starts flowing)
# The Security log lands in the Event table (Learn), not in SecurityEvent
$query = @"
Event
| where TimeGenerated > ago(1h) and EventLog == "Security"
| summarize count() by EventID
| order by count_ desc
| take 10
"@

Write-Host "`nQuerying for security events..." -ForegroundColor Cyan
# Note: Events may take 5-10 minutes to appear after DCR association
```

## Assigning DCR to Arc-Enabled Servers

Once Arc-enabled servers are registered during cluster deployment, associate them with the DCR:

```powershell
# Get DCR resource ID
$dcrId = (Get-AzDataCollectionRule -ResourceGroupName $resourceGroup -Name $dcrName).Id

# Associate with Arc-enabled server
$arcServerResourceId = "/subscriptions/$subscriptionId/resourceGroups/rg-azurelocal-prod-eastus2/providers/Microsoft.HybridCompute/machines/azl-node-01"

New-AzDataCollectionRuleAssociation `
 -TargetResourceId $arcServerResourceId `
 -AssociationName "dcr-association-node01" `
 -RuleId $dcrId
```

## Troubleshooting

| Issue | Cause | Resolution |
|-------|-------|------------|
| DCR creation fails with `WorkspaceId invalid` | Log Analytics workspace not found or wrong region | Verify workspace exists with `Get-AzOperationalInsightsWorkspace`; ensure DCR and workspace are in the same region |
| Security events not appearing in Log Analytics | AMA not installed or DCR association missing, or the query reads `SecurityEvent` (the rule here writes to `Event`; `SecurityEvent` is the table of the Microsoft Sentinel connector) | Verify AMA extension: `az connectedmachine extension list`; check DCR association: `Get-AzDataCollectionRuleAssociation` |
| Partial event collection (some event types missing) | DCR XPath queries don't cover required event channels | Update DCR data sources to include all required Windows event channels (Security, System, Application) |
