This document provides detailed provisioning instructions with **tabbed execution options** for each step. Choose the option that best fits your environment and expertise.

## Understanding the Execution Options

Each task page uses tabs so you can switch between methods without scrolling. Not every task supports all options. Only genuinely applicable methods are shown.

| Option | Best For | You Will Need |
|--------|----------|---------------|
| **Manual** (Azure Portal, on-site, vendor UI) | Learning, single deployments, visual preference, physical tasks | Web browser / physical access / vendor UI |
| **Toolkit script** (PowerShell 7) | Repeatable runs from a management workstation or a pipeline | PowerShell 7, the toolkit, and your `infrastructure.yml` |

> **Looking for full automation (IaC/CI/CD)?**
>
> The fully automated deployment instructions (Terraform, Bicep, Ansible, CI/CD pipelines) are documented separately in the [Automation section](../automation/). Use that guide for pipeline-driven, repeatable deployments.

## Configuration File: infrastructure.yml

The toolkit scripts read one file: `infrastructure.yml` (schema 5). It is the only file you fill in for an environment. The master registry (`config/variables/schema/master-registry.yaml`) defines every key. Before you start:

1. **Start from a template.** Copy `config/variables/templates/infrastructure.master.yml` (every key), a scenario template, or the nearest worked example in `config/variables/examples/`. For one tool only, use its template in `config/variables/templates/tools/`.
2. **Edit the values** to match your environment: the Azure tenant and subscription, the resource groups, the networks, the nodes.
3. **Never put a secret in the file.** A secret is a reference: `keyvault://<vault>/<secret>` (the default), `env://<VARIABLE>`, `file://<name>` or `command://<name>`. One resolver reads every reference. No script names a vault.

```yaml
# A reference, not a value
identity:
  local_admin:
    username: "iic-admin"
    password: "keyvault://kv-iic-mgmt-01/local-admin-password"
```

4. **Check the file.** `./scripts/common/infrastructure/Test-InfrastructureFile.ps1 -Path ./infrastructure.yml` lists every problem at once.

> **Configuration reference**: see [Variable Management](https://azurelocal.cloud/standards/variables) for how the variables work, and the [variables reference](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/docs/VARIABLES.md) for every key.

## Execution Workflow

1. **Review the stage details.** Understand the objectives and tasks.
2. **Select your tab** for each step (Manual or Toolkit script).
3. **Complete the step** following that tab's procedure.
4. **Validate** using the verification steps provided.
5. **Proceed to the next step.**

You can **mix options** throughout the runbook (for example, use the portal for some steps and scripts for others). Your tab selection persists across pages.

## Script Language Support

The toolkit is **PowerShell 7 only**. It has no Bash scripts. Scripts that act on Azure use the Azure PowerShell modules (`Az.*`). A few tasks also have an Azure CLI script, written in PowerShell.

| Kind | Naming pattern | Example |
|------|----------------|---------|
| PowerShell + Az modules | `Verb-Noun.ps1` | `Deploy-KeyVaults.ps1` |
| PowerShell + Azure CLI | `az-<verb>-<noun>.ps1` or `<Verb-Noun>.azcli.ps1` | `Register-ResourceProviders.azcli.ps1` |
| Orchestrated (remote) | `Invoke-<Task>-Orchestrated.ps1` | `Invoke-SSHConnectivity-Orchestrated.ps1` |

Every script takes the file as `-InfrastructureFile` (mandatory). No script takes `-ConfigPath` or `-ConfigFile`, and no script prompts.

Every script takes its values from `infrastructure.yml`. A test fails the build when a script carries a value that a deployment chooses (an address, a name, an ID, a region). The [script status](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/docs/script-status.md) page of the toolkit says, for every task folder, whether it has a real script or a placeholder.
