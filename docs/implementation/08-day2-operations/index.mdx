## The monthly update, in order

A cluster stays supported only within the N-6 released build window (with 2611 the latest, 2605 is the oldest supported build), and Microsoft ships cumulative and security updates monthly, so a cluster takes an update about once a month ([About updates](https://learn.microsoft.com/en-us/azure/azure-local/update/about-updates-23h2?view=azloc-2611#lifecycle-cadence)). The steps are always the same ([Update management and SBE](../../operations/update-management-and-sbe.mdx) has the background):

1. **Check.** [Task 01](./task-01-check-for-updates.mdx). The verdict says what is offered: `UpdateAvailable`, `AdditionalContentRequired`, `UpdateRunning`, `UpToDate` or `AttentionNeeded`.
2. **Import the SBE files, only when an update is in the state `AdditionalContentRequired`.** [Phase 06, Task 11: SBE update import](../04-cluster-deployment/phase-06-post-deployment/task-11-sbe-update-import.mdx) lists the files on the share and prints the import commands. Then check again (step 1) until the update is `Ready`.
3. **Prepare (recommended).** [Task 02](./task-02-start-solution-update.mdx) with `-Mode OnDemand -PrepareOnly` downloads the update and runs the readiness checks before the maintenance window. The update becomes `ReadyToInstall`.
4. **Start.** [Task 02](./task-02-start-solution-update.mdx) with `-Mode OnDemand`, inside the maintenance window. The script returns at once; the update takes hours and the machines restart.
5. **Follow.** Run [Task 01](./task-01-check-for-updates.mdx) again, or watch Update Manager in the Azure portal. Sonar watches the progress as well.
6. **Verify.** The update is `Installed` and `Get-SolutionUpdateEnvironment` shows the new `CurrentVersion`. Run the checks of [Part 7](../07-validation-handover/index.mdx) again.

The first update after a deployment is the same path. Set `operations.updates.install_after_deployment: true` to let [Task 02](./task-02-start-solution-update.mdx) start it in the default mode `AfterDeployment`.

## Check after the deployment, and on a schedule

A freshly deployed cluster does not show its first update on its own until later: the update service finds updates by itself, and the update agent checks once a day (Microsoft Learn: Use Azure Update Manager to update Azure Local). So the toolkit always checks:

- **Right after the deployment**, once: `Get-AvailableSolutionUpdate.ps1 -WaitMinutes 120` waits for the first update to be offered.
- **On a schedule**, for example daily: `Get-AvailableSolutionUpdate.azcli.ps1 -OutputPath <file>` needs no access to a node, so a pipeline agent or an administrator's workstation can run it. Exit code `1` means the cluster needs attention (a failed update, a health state of `Failure`, `Error` or `Warning`, or an update service that has not checked for 48 hours): use it as the alert. The JSON file holds the verdict and every update for a monitor.

Both scripts only read. Neither installs an update.

## Prerequisites

- [ ] The cluster is deployed ([Part 4](../04-cluster-deployment/index.mdx)) and registered in Azure
- [ ] `infrastructure.yml` is the file the deployment used (`cluster.name`; `azure.*` for the Azure CLI scripts)
- [ ] The account that runs the PowerShell scripts is the deployment user (Learn: sign in with the deployment user account), or `-Credential` names it
- [ ] For the Azure CLI script: `az login --tenant <azure.tenant_id>` was run, with at least read access to the cluster resource
