# Variable Management Standard

[![Standard](https://img.shields.io/badge/Type-Standard-green?style=flat-square)](./index.mdx)
[![Azure](https://img.shields.io/badge/Platform-Azure_Local-0078D4?style=flat-square&logo=microsoftazure)](https://learn.microsoft.com/en-us/azure/azure-local/)

> **DOCUMENT CATEGORY**: Standard
> **SCOPE**: The Azure Local toolkit and the tools that read its variables
> **PURPOSE**: The variable management pattern: registry first, one infrastructure file, secrets as references
> **MASTER REFERENCE**: [Variable Management](https://azurelocal.cloud/standards/variables)

**Status**: Active

## Overview

The registry `config/variables/schema/master-registry.yaml` is the only master of every variable. One `infrastructure.yml` (schema 5, current version 5.6.21) feeds every tool. The generator writes one master template and one template per tool from the registry. Scripts, schemas, templates and documents conform to the registry. This page is the short version. The full standard is [Variable Management](https://azurelocal.cloud/standards/variables).

**Core principle:** one master, one file per environment, one template per tool.

| Artifact | Location | Purpose |
|----------|----------|---------|
| Registry | `config/variables/schema/master-registry.yaml` | The master of every variable. Edit this |
| Environment file | `infrastructure.yml` (in a private environment repository) | Your values for one Azure Local instance |
| Schema | `config/variables/schema/infrastructure.schema.json` | Generated. Validates the environment file |
| Master template | `config/variables/templates/infrastructure.master.yml` | Generated. Every variable, with comments |
| Tool templates | `config/variables/templates/tools/<tool>.yml` | Generated. Only the keys one tool reads |
| Examples | `config/variables/examples/` | Worked files with example-company values, tested against the schema |
| Reference doc | [`config/variables/docs/VARIABLES.md`](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/docs/VARIABLES.md) | Generated. Every key with type, default, example and who reads it |

Never edit a generated file. A test regenerates them and fails when one is stale.

## Naming Conventions

| Scope | Convention | Example |
|-------|-----------|---------|
| Keys, at every level | `snake_case` | `subscription_id`, `cluster_name` |
| Enum values | `snake_case` | `active_directory`, `rack_aware` |
| Booleans | Descriptive name | `enable_real_time: true` |
| Secrets | A reference | `keyvault://kv-iic-mgmt-01/admin-password` |
| Your own keys | Under `extensions` | `extensions.iic-notes` |

## Secret Management

Secrets are never values in `infrastructure.yml`. A key that needs a secret holds one of four reference forms:

| Form | Provider |
|------|----------|
| `keyvault://<vault>/<secret>` | Azure Key Vault (the default). List the vault under `key_vaults` |
| `env://<VARIABLE>` | Environment variable |
| `file://<name>` | File in `secrets.file.directory` |
| `command://<name>` | Custom command in `secrets.command` |

One resolver, `scripts/common/secrets/AzlSecret.psm1`, reads every reference. No script names a vault. The secret value is passed on in memory and is never written to disk, a log or a report. See [Secret references and providers](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/docs/secret-references.md).

## Validation

The file is validated by the schema and by the rules of `Test-InfrastructureFile.ps1`:

```powershell
./scripts/common/infrastructure/Test-InfrastructureFile.ps1 -Path ./infrastructure.yml
```

The registry and everything generated from it are checked by tests (`Invoke-Pester ./tests/variables, ./tests/infrastructure`) and by the `-Check` switch of each generator. An enforcement test stops a script from carrying a hard-coded value. Every script parameter is registered by a generator.

## Adding a Variable

1. Add the entry to the registry first (type, description, default, example, `used_by`, `since`).
2. Run `./config/variables/scripts/New-InfrastructureArtifacts.ps1`, and `New-ScriptParameterRegistry.ps1` when a script parameter changed.
3. Then change the script, the example and the page that explains it.

A variable that exists only in a script, a file, a hand-edited schema or a document is drift, and the tests fail on it.
