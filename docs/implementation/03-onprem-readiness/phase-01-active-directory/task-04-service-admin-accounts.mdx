## Overview

Create supplemental break-glass admin accounts and optional gMSA scaffold for enterprise environments.

### What This Accomplishes

- Break-glass administrative accounts for emergency access
- Group Managed Service Accounts (gMSA) for secure service authentication
- Secure password management and storage
- Account configuration following security best practices

:::info

The active directory information in these documents should have been decided in the [planning phase](../../../planning/) and discovery phases. These are just examples. Please update your scripts with the right OU information, right security groups, DNS, etc.

:::

## Prerequisites

- OU structure created (Step 1)
- Domain admin access for account creation
- Secure password storage solution (vault)
- Only for the optional gMSA scaffold: a KDS root key that has replicated to all domain controllers (see below)

### KDS root key (optional gMSA scaffold only)

The break-glass account does not need a KDS root key. The Microsoft Learn 2610 Azure Local AD-preparation and custom-AD articles do not mention a gMSA or a KDS root key, so this runbook set treats the gMSA scaffold as optional. If you create the gMSA, a KDS root key must exist first (one per forest). Check with `Get-KdsRootKey`, and create one only if none exists.

| Environment | Command | Wait |
|-------------|---------|------|
| Production or any lab with more than one domain controller | `Add-KdsRootKey -EffectiveImmediately` | Wait 10 hours so the key replicates to all domain controllers before creating the gMSA |
| Single domain controller test environment only | `Add-KdsRootKey -EffectiveTime (Get-Date).AddHours(-10)` | None. Microsoft documents this backdating technique for single-DC tests only and says not to use it in production |

Source: [Create a Key Distribution Service (KDS) root key](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-managed-service-accounts/group-managed-service-accounts/create-the-key-distribution-services-kds-root-key). Do not create more than one root key per forest.

:::note Legacy gMSA wording in the Environment Checker article
The Learn 2610 Environment Checker article still describes the Active Directory validator as checking that the preparation tool created gMSAs. The 2610 AD-preparation article documents only `New-HciAdObjectsPreCreation -AzureStackLCMUserCredential ... -AsHciOUName ...` from the `AsHciADArtifactsPreCreationTool` module (install version 2402 and uninstall earlier versions first). This repo follows the AD-preparation article; treat the gMSA wording as legacy and rely on the validator result in your environment.
:::

## Account Creation

Lifecycle Manager (LCM) user created in Step 1. Add break‑glass admin and optional gMSA scaffold.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Active Directory Users and Computers" default>

1. In **Active Directory Users and Computers**, inside instance OU create user: `adm-AzureLocal-BreakGlass-<clusterId>`.
2. Set: Password never expires; User cannot change password; store password securely (vault).
3. (Optional gMSA) After a KDS root key exists and has replicated (see the KDS table above), create gMSA via AD Administrative Center (if supported) targeting computer principals later.

## Notes

- LCM user is created in Step 1; this step adds supplemental accounts
- Break-glass accounts should have passwords stored securely in a vault
- gMSA requires a KDS root key and replication to complete first (10 hours in production). KDS root key guidance lives here, not in Task 01
- Use unique cluster IDs to avoid naming conflicts

## Troubleshooting

### Common Issues

**Account Creation Fails**: Check OU permissions and naming policies.

**gMSA Creation Fails**: Ensure a KDS root key exists and has replicated to all domain controllers. With `-EffectiveImmediately` wait 10 hours in production; use the `-10` hours backdating only on a single-DC test domain.

**Password Storage**: Verify vault access and security policies.
