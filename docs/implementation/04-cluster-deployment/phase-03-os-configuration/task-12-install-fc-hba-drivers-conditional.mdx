## Overview

Azure Local disaggregated deployments connect each node to a SAN with Fibre Channel Host Bus Adapters (HBAs) or with dedicated iSCSI network adapters. For Fibre Channel, the HBA drivers must be installed and the WWPNs collected so the SAN administrator can zone the fabric and unmask the LUNs. This task installs the vendor-provided drivers and records each node's WWPN.

---

## Zoning timing: disaggregated versus hybrid

The timing is **opposite** for the two designs. Do not apply one rule to both.

| Design | When to zone the FC HBA WWNs | What Microsoft Learn says |
|---|---|---|
| **Disaggregated (SAN only)** | **Before** Arc registration (Phase 04), so the LUNs are visible to the nodes. | "Retrieve the HBA Address (WWPN)... get the LUNs unmasked to the HBAs... Confirm you can see the LUNs before you proceed with Arc registration." "Don't initialize the drives, as the deployment expects the drive type to be RAW." |
| **Hybrid (S2D + SAN)** | **After** the Azure Local deployment completes. | "To avoid deployment confusion for FC LUNs, don't zone in FC HBA World Wide Names (WWNs) until after the Azure Local deployment." |

Learn's disaggregated page requires that the LUNs are unmasked and visible before Arc registration. It does not describe the fabric zoning step itself; on Fibre Channel the LUNs can only become visible once the zones exist, so zoning is part of getting them visible. Needed LUNs at this point: the infrastructure LUN (250 GB or larger) and the performance history LUN (20 GB or larger). Learn states that workload LUNs are configured after deployment.

## Execution Options

<Tabs groupId="deployment-method">
<TabItem value="direct" label="Direct (On Node)" default>

Run on each node individually via console, RDP, or PSRemoting.

**Toolkit script:** none for this step. Fibre Channel HBA drivers are not installed by the toolkit. The run checks the result: its **SanVerify** step collects the node WWPNs and checks that every listed WWPN is seen.

```powershell
# Task 12 - Install FC HBA Drivers (run on each node)
# Consult your HBA vendor documentation for the correct .inf driver path

# Stage 1: Install driver via PnP
# Replace <path-to-driver.inf> with the vendor-provided INF file path
PNPUTIL /add-driver "<path-to-driver.inf>" /install

# Stage 2: Confirm HBA ports are detected
Get-InitiatorPort | Select-Object NodeAddress, PortAddress, ConnectionType |
    Where-Object { $_.ConnectionType -eq 'Fibre Channel' } |
    Format-Table -AutoSize

# Stage 3: Record WWPNs for each node (save to infrastructure.yml)
# PortAddress field contains the WWPN in XX:XX:XX:XX:XX:XX:XX:XX format
Get-InitiatorPort | Where-Object { $_.ConnectionType -eq 'Fibre Channel' } |
    Select-Object @{N='Node';E={$env:COMPUTERNAME}}, NodeAddress, PortAddress |
    Export-Csv -Path "C:\Temp\wwpn-$env:COMPUTERNAME.csv" -NoTypeInformation
```

</TabItem>
<TabItem value="orchestrated" label="Orchestrated Script">

Run from the management server against all nodes.

**Toolkit script:** none for this step. Fibre Channel HBA drivers are not installed by the toolkit. The run checks the result: its **SanVerify** step collects the node WWPNs and checks that every listed WWPN is seen.

```powershell
# Task 12 - Install FC HBA Drivers (orchestrated)

# The management addresses of the nodes: the management port of each entry of nodes[] in infrastructure.yml
$ServerList = @('<node-1-management-ip>', '<node-2-management-ip>')

# Collect WWPNs from all nodes
Invoke-Command -ComputerName $ServerList -ScriptBlock {
    Get-InitiatorPort | Where-Object { $_.ConnectionType -eq 'Fibre Channel' } |
        Select-Object @{N='Node';E={$env:COMPUTERNAME}}, NodeAddress, PortAddress
} | Sort-Object Node | Format-Table -AutoSize
```

> **Note:** Driver installation requires staging the vendor INF to each node before running. Consult your HBA vendor documentation for the driver package appropriate to the installed HBA model.

</TabItem>
</Tabs>

## Validation

```powershell
# Confirm HBA ports are online and WWPNs visible
$ServerList = @("<node1-ip>", "<node2-ip>")
Invoke-Command -ComputerName $ServerList -ScriptBlock {
    Get-InitiatorPort | Where-Object { $_.ConnectionType -eq 'Fibre Channel' } |
        Select-Object @{N='Node';E={$env:COMPUTERNAME}}, PortAddress, ConnectionType, OperationalStatus
} | Sort-Object Node | Format-Table -AutoSize
```

**Expected:** Each node shows 1–4 FC initiator ports depending on HBA count. `OperationalStatus` should be `Online` once fabric-connected.

:::note Provide WWPNs to the FC fabric and SAN administrators (disaggregated)
For a **disaggregated** design, give the collected WWPNs to the SAN administrator so the LUNs are unmasked to the HBAs, and to the fabric administrator for zoning. The array's target port WWPNs are needed to complete the zones. Do this **before** Arc registration (Phase 04), then confirm the LUNs in [Task 14](./task-14-verify-san-lun-presentation-conditional.mdx).

For a **hybrid** design (S2D + SAN), keep the WWPNs on file but **do not zone** them until after the Azure Local deployment.
:::

## iSCSI adapters (disaggregated, iSCSI SAN)

Learn: "Azure Local only supports dedicated adapters for iSCSI." The steps depend on the version you deploy.

:::warning Azure Local 2610: do not enable iSCSI on the machines before deployment
"Starting with Azure Local version 2610, for connected and disconnected deployments, don't manually enable iSCSI on the machines before deployment. The deployment wizard now includes iSCSI configuration as part of the deployment process. For earlier versions, follow the steps in this section to enable iSCSI manually." (Learn, [Connect to SAN](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deployment-install-os-disaggregated?view=azloc-2610#connect-to-san)). In the 2610 portal wizard you turn on **iSCSI Configuration**, then enter the authentication type and the iSCSI network details ([Deploy Azure Local using the Azure portal for disaggregated deployments](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deploy-via-portal-disaggregated?view=azloc-2610#specify-configuration-settings)).
:::

| Version you deploy | What to do in this task |
|---|---|
| **2610** (connected or disconnected) | Install the OEM drivers for the dedicated iSCSI network adapters (**not** the inbox drivers). Learn says not to manually enable iSCSI on the machines before deployment because the wizard now configures it, so this runbook does not run the manual iSCSI steps (addresses, `MSiSCSI`, auto-claim, target connections) on 2610. Enter the iSCSI network details in the wizard instead; Learn does not spell out each manual step as unsupported, so confirm anything beyond the drivers with your OEM. |
| **2604 to 2609** | Follow Learn's manual iSCSI steps on every node: install the OEM adapter drivers (not inbox), assign each adapter an IP address and disable DNS client registration, validate connectivity with `ping -S`, add static routes only if routing is required, set `MSiSCSI` to start automatically, run `Enable-MSDSMAutomaticClaim -BusType iSCSI`, add the target portal for each path, collect the IQNs (the `NodeAddress` of the iSCSI initiator ports from `Get-InitiatorPort`) for LUN masking\| Where-Object ConnectionType -eq 'iSCSI').NodeAddress`) for LUN masking, connect each target with `-IsPersistent $true -IsMultipathEnabled $true`, then confirm the LUNs with `Get-PhysicalDisk`. |

Check that the iSCSI adapters are not on an inbox driver (Learn: an adapter uses an inbox driver if `DriverProvider` is `Microsoft`):

```powershell
Get-NetAdapter -Name "<AdapterName>" | Select-Object Name, DriverProvider, DriverVersion, DriverDate
```

For hybrid (S2D + SAN) with iSCSI, Learn requires dedicated physical ports for iSCSI (vNICs are not supported) and a node with identical NIC configurations; see [Connect an external storage array to Azure Local](https://learn.microsoft.com/en-us/azure/azure-local/deploy/enable-external-storage?view=azloc-2610).

## Rolling Reboot (if required)

Driver installation may require a node restart. In a cluster, reboot one node at a time to maintain availability:

```powershell
# Drain and reboot one node at a time
Suspend-ClusterNode -Name "<NodeName>" -Drain
# Wait for roles to migrate
Restart-Computer -ComputerName "<node-ip>" -Force
# Wait for node to rejoin
Resume-ClusterNode -Name "<NodeName>"
```

For initial pre-cluster deployment (Phase 03), simply reboot each node and confirm the OS comes back online.
