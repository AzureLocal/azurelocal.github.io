## Overview

Configure the primary and secondary DNS server addresses on the management network adapter
of each Azure Local node. DNS must be set before Active Directory operations, Azure Arc
registration, and any hostname resolution required later in the deployment.

:::warning Run AFTER Task 04
Task 04 (disable DHCP) must be complete. Setting DNS before DHCP is disabled has no harmful
effect, but the standard sequence is Tasks 03 → 04 → 05.
:::

:::danger DNS decisions are permanent
Once the deployment completes, it isn't supported to change the DNS server IPs, and the addresses can't be updated across the Azure Local platform stack. Get them right now. Per Learn (Azure Local 2610, *Network considerations for cloud deployments*, DNS server considerations):

1. The DNS servers must be the **same on every node** of the instance.
2. The DNS servers of the **infrastructure IP address range** (set in the deployment wizard or template) must be the same ones the nodes use. The Azure Resource Bridge control plane VM and the AKS control plane use those servers.
3. At least one configured DNS server must run **outside** the Azure Local instance. Running *all* of them as VMs on the instance that depends on them isn't supported, because name resolution is needed during boot, shutdown, restart and recovery.
4. Every configured DNS server must resolve the on-premises domains the infrastructure needs. Public DNS servers such as 8.8.8.8 aren't supported as the configured servers.
5. For Active Directory deployments the DNS server must resolve the Active Directory domain and the public internet endpoints.
6. The DNS server IPs must not fall in the Azure Resource Bridge ranges (`10.96.0.0/24` for deployments created from 2610, `10.96.0.0/12` for earlier deployments, and `10.244.0.0/16` for all). Use the wider `10.96.0.0/12` as the planning rule unless you are sure the instance is new on 2610. If AKS uses these DNS servers, also avoid its service and pod ranges.
7. Learn recommends assigning only one management IP for the default gateway and for the configured DNS servers across the physical network adapters of the node, so it doesn't change once the management intent is created. Network validation fails when it finds more than one physical adapter with a default gateway.
8. In an ARM template, write multiple DNS servers as quoted strings separated by commas, for example `"dnsServers": ["10.250.16.124", "10.250.17.232"]`.
:::

**What the scripts do:**

1. Hard-fail on any `REPLACE` placeholder value remaining in `#region CONFIGURATION`
2. Find the management adapter by **exact name** — exit and list adapters if not found
3. Check idempotency — exit clean if DNS is already set to the target values
4. Call `Set-DnsClientServerAddress` with the two explicit DNS IPs
5. Read back and validate the DNS configuration

## Execution Options

<Tabs groupId="deployment-method">
<TabItem value="sconfig" label="SConfig Utility" default>

Configure DNS interactively on each node via console, KVM, or RDP.

:::note Use the Direct Script tab when running multiple nodes
SConfig requires repeating these steps on every node individually. For multi-node deployments,
the Direct or Orchestrated tab is faster and less error-prone.
:::

**Steps — for each node:**

1. Open **SConfig** (if not already running, type `sconfig` in PowerShell)
2. Select option **`8`** — Network settings
3. Select the **management adapter** (the one configured with a static IP in Task 03)
4. Select option **`2`** — Set DNS Servers
5. Enter the **Primary DNS IP** from `infrastructure.yml` → `networking.management.dns_servers`
6. Enter the **Secondary DNS IP** from `infrastructure.yml` → `networking.management.dns_servers`
7. Press Enter to confirm

**Verify in SConfig:**

After setting DNS, return to the Network settings menu and confirm the DNS servers shown
match the values from `infrastructure.yml`.

**Alternatively, verify in PowerShell:**

```powershell
# Run on the node after SConfig configuration
Get-DnsClientServerAddress -AddressFamily IPv4 |
 Where-Object { $_.ServerAddresses.Count -gt 0 } |
 Select-Object InterfaceAlias, ServerAddresses |
 Format-Table -AutoSize
```

## Validation

Verify DNS server configuration on each node:

```powershell
# Run on each node (or via PSRemoting)
Get-DnsClientServerAddress -AddressFamily IPv4 |
 Where-Object { $_.ServerAddresses.Count -gt 0 } |
 Select-Object InterfaceAlias, ServerAddresses |
 Format-Table -AutoSize
```

**Validation checklist:**

| Check | Expected | Status |
|-------|----------|--------|
| Primary DNS on management NIC | `networking.management.dns_servers` from `infrastructure.yml` | ☐ |
| Secondary DNS on management NIC | `networking.management.dns_servers` from `infrastructure.yml` | ☐ |
| No other DNS entries on management NIC | Only 2 servers listed | ☐ |

:::note DNS resolution test
Task 06 performs a full DNS resolution validation. Basic resolution testing at this stage
is optional — proceed to Task 06 for a comprehensive verification.
:::

## Troubleshooting

| Issue | Root Cause | Remediation |
|-------|------------|-------------|
| Script hard-fails on startup | `REPLACE` placeholder values remain | Edit `#region CONFIGURATION` with real values from `infrastructure.yml` |
| `Adapter not found` error | NIC name in config doesn't match | Run `Get-NetAdapter` on the node; update `nodes[].network_adapters[].name` in `infrastructure.yml` |
| DNS validation fails (post-set mismatch) | Transient WMI delay | Wait 5 seconds and re-run the validation query manually |
| DNS not resolving names (verified in Task 06) | DNS servers unreachable | Verify DNS server IPs are reachable from node; check routing and firewall |
| Orchestrated script: `cluster.management_nic_name not found` | Key missing from `infrastructure.yml` | Add `nodes[].network_adapters[].name` to the `cluster:` block in yml |
| Orchestrated script: `dns.primary not found` | Key missing from `infrastructure.yml` | Add `networking.management.dns_servers` to the `dns:` block in yml |
| Node unreachable via PSRemoting | WinRM not configured or firewall blocking | Verify Task 01 (WinRM) completed; check firewall rules |
