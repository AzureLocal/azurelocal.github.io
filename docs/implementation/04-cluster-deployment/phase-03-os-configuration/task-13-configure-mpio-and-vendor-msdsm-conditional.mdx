## Overview

Windows Multipath I/O (MPIO) aggregates multiple physical paths to a SAN LUN into a single logical disk, providing both redundancy and load distribution. Azure Local uses the inbox Microsoft Device Specific Module (MSDSM); there is no vendor DSM package to stage. For each array, the vendor and product IDs have to be **registered** with MSDSM, and the array's disks have to be **claimed** by MPIO. Without that, Windows presents each path as a separate disk.

:::info MPIO is enabled by default from Azure Local 2604
Learn: "Azure Local 2604 and later versions enable Multipath I/O (MPIO) by default. Verify that MPIO is enabled on all nodes. If MPIO isn't enabled, which can happen in earlier versions, you need to reboot." You no longer install the feature and restart as a routine step. Verify it, and enable it only if it is off.
:::

:::warning Registering the vendor IDs is not always enough: claim the disks too
Learn's step is registering the vendor with MSDSM (`New-MSDSMSupportedHW`). On a real Pure FlashArray lab, registering alone left **8 separate disks for 2 LUNs** (4 paths each, not merged). Claiming the array's devices with `mpclaim -n -i -d` and restarting merged them into 2 multi-path disks. Treat the claim as part of the procedure. This claim step is **lab-verified on Pure FlashArray only**; Learn documents `mpclaim` only for Hitachi VSP (`mpclaim -r -i -d "HITACHI OPEN-V"`). For other arrays, apply the same claim and confirm with `mpclaim -s -d`.
:::

## Step 1: Verify the MPIO Windows Feature

<Tabs groupId="deployment-method">
<TabItem value="direct" label="Direct (On Node)" default>

Run on each node individually via console, KVM, or RDP.

**Toolkit script:** none for this step. The run does this in its **Mpio** step: the MultipathIO feature, the array's MSDSM hardware ID, the MPIO claim and the load balance policy. It needs `storage.san.array.vendor` and `storage.san.array.model`.

```powershell
# Task 13 - Step 1: Verify MPIO (run on each node)
Get-WindowsOptionalFeature -Online -FeatureName MultipathIO |
    Select-Object FeatureName, State, RestartNeeded

# Only if State is not Enabled (possible on builds before 2604):
# Enable-WindowsOptionalFeature -Online -FeatureName MultipathIO
```

:::warning Restart only if required
If you had to enable MPIO, or `RestartNeeded` is `True`, restart the node (rolling, one at a time once clustered) before proceeding to Step 2. If MPIO was already enabled, no restart is needed here.
:::

</TabItem>
<TabItem value="orchestrated" label="Orchestrated Script">

Run from the management server against all nodes.

**Toolkit script:** none for this step. The run does this in its **Mpio** step: the MultipathIO feature, the array's MSDSM hardware ID, the MPIO claim and the load balance policy. It needs `storage.san.array.vendor` and `storage.san.array.model`.

```powershell
# Task 13 - Step 1: Verify MPIO (orchestrated)

# The management addresses of the nodes: the management port of each entry of nodes[] in infrastructure.yml
$ServerList = @('<node-1-management-ip>', '<node-2-management-ip>')

# Report the state on every node. 2604 and later enable MPIO by default.
Invoke-Command -ComputerName $ServerList -ScriptBlock {
    Get-WindowsOptionalFeature -Online -FeatureName MultipathIO |
        Select-Object @{N='Node';E={$env:COMPUTERNAME}}, FeatureName, State, RestartNeeded
} | Sort-Object Node | Format-Table -AutoSize

# Only for a node where State is not Enabled: enable it, then restart that node.
# Invoke-Command -ComputerName <node-ip> -ScriptBlock { Enable-WindowsOptionalFeature -Online -FeatureName MultipathIO -NoRestart }
# Restart-Computer -ComputerName <node-ip> -Force
```

:::warning Restart only if required
Restart a node only if you enabled MPIO on it or `RestartNeeded` is `True`. Wait for the node to return online before proceeding to Step 2.
:::

## Step 2: Register the Vendor with MSDSM, Claim the Disks and Set the Policy

Run on **each node**. Select the tab for your array vendor. Learn's vendor IDs:

| Vendor | VendorId | ProductId | Learn command |
|---|---|---|---|
| Dell PowerStore | `DellEMC` | `PowerStore` | `New-MSDSMSupportedHW -VendorId "DellEMC" -ProductId "PowerStore"` |
| Everpure FlashArray (formerly Pure Storage) | `PURE` | `FlashArray` | `New-MSDSMSupportedHW -VendorId "PURE" -ProductId "FlashArray"` |
| Hitachi VSP | use `mpclaim` | `OPEN-V` | `mpclaim -r -i -d "HITACHI OPEN-V"` |
| HPE Alletra / 3PAR | `3PARdata` | `VV` | `New-MSDSMSupportedHW -VendorId "3PARdata" -ProductId "VV"` |
| NetApp ONTAP | `NETAPP` | `LUN C-Mode` | `New-MSDSMSupportedHW -VendorId "NETAPP" -ProductId "LUN C-Mode"` |
| Lenovo ThinkSystem DS / DM / DG | Learn lists the series as supported but gives no IDs | Learn gives no IDs | Get the IDs from Lenovo's Windows MPIO guide and confirm them in the output of `Get-Disk` and `mpclaim -s -d` |

:::note How to claim with mpclaim
`mpclaim -n -i -d "<device string>"` adds the device to MPIO and claims the matching disks; `-n` suppresses the automatic reboot, so restart the node yourself afterwards (Learn's Hitachi form uses `-r`, which reboots). The device string is the **vendor ID padded to 8 characters** followed by the **product ID padded to 16 characters**, for example `"PURE    FlashArray      "` (`PURE` + 4 spaces, `FlashArray` + 6 spaces). Check the exact IDs with `Get-Disk | Select-Object FriendlyName, Manufacturer, Model` before you pad them.
:::

<Tabs groupId="san-vendor">
<TabItem value="pure-storage" label="Everpure (Pure) FlashArray" default>

```powershell
# Task 13 - Step 2: Configure MSDSM for Everpure FlashArray (Pure Storage)
# Remove the generic wildcard entry so MSDSM does not claim non-Pure devices (Learn)
Remove-MSDSMSupportedHW -VendorId 'Vendor*' -ProductId 'Product*'

# Register the hardware IDs (Learn)
New-MSDSMSupportedHW -VendorId "PURE" -ProductId "FlashArray"

# Claim the array's devices (lab-verified on a Pure FlashArray). Vendor padded to 8, product padded to 16.
mpclaim -n -i -d "PURE    FlashArray      "

# Default load balance policy is Round Robin (Learn)
Set-MSDSMGlobalDefaultLoadBalancePolicy -Policy RR

# Vendor MPIO timers (Learn)
Set-MPIOSetting -NewPathRecoveryInterval 20 -CustomPathRecovery Enabled `
    -NewPDORemovePeriod 20 -NewDiskTimeout 60 -NewPathVerificationState Enabled

# Restart the node to apply the MPIO changes (one node at a time)
```

### iSCSI only: automatic claim

For iSCSI arrays on Azure Local **2604 to 2609**, also enable MPIO automatic claim for the iSCSI bus (Learn: "Enable MPIO for iSCSI using default policy (round robin)"):

```powershell
Enable-MSDSMAutomaticClaim -BusType iSCSI
```

If you enable auto-claim after LUNs are already visible, restart the node so MSDSM can re-enumerate the devices. On **2610**, do not enable iSCSI on the machines before deployment; the deployment wizard's **iSCSI Configuration** does this (see [Task 12](./task-12-install-fc-hba-drivers-conditional.mdx#iscsi-adapters-disaggregated-iscsi-san)). Fibre Channel LUNs are claimed through the registered hardware IDs; Learn does not use `Enable-MSDSMAutomaticClaim -BusType FC`, so this runbook no longer runs it.

## Step 3: Restart and Verify

MPIO policy changes do not take effect until the node restarts. Restart each node (one at a time when clustered), then verify.

## Verification

```powershell
# Confirm MPIO is enabled
Get-WindowsOptionalFeature -Online -FeatureName MultipathIO | Select-Object FeatureName, State

# Confirm supported hardware IDs are registered
Get-MSDSMSupportedHW | Format-Table VendorId, ProductId

# Confirm the load balance policy and MPIO timers
Get-MSDSMGlobalDefaultLoadBalancePolicy
Get-MPIOSetting

# Confirm the array's disks are claimed and show their path counts
mpclaim -s -d
```

**Expected:** `State = Enabled`; your vendor's IDs appear in the supported HW list; the load balance policy is `RR`; `mpclaim -s -d` lists one MPIO disk per LUN with two or more paths. Until the LUNs are presented, `mpclaim` shows no disks, which is expected. If a node shows one disk **per path** instead of one disk per LUN, the disks are registered but not claimed; run the `mpclaim -n -i -d` claim from Step 2 and restart.

## Validation Checklist

- [ ] MPIO verified as enabled on all nodes (restarted only where it had to be enabled)
- [ ] Vendor hardware IDs registered (`New-MSDSMSupportedHW`, or `mpclaim` for Hitachi) on all nodes
- [ ] Array devices claimed (`mpclaim -n -i -d`) and all nodes restarted afterwards
- [ ] Load balance policy is Round Robin (`RR`) unless the vendor guide says otherwise
- [ ] Vendor MPIO timers applied where Learn lists them (Dell, Everpure)
- [ ] iSCSI on 2604 to 2609 only: `Enable-MSDSMAutomaticClaim -BusType iSCSI` confirmed
