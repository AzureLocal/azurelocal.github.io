## Overview

Manually install Azure Stack HCI OS on each cluster node through iDRAC Virtual Console. This is a standard Windows Server Core installation using Windows Setup.

:::info ISO Is Already Mounted from Task 02
The Dell gold image ISO was mounted (or USB inserted) in **Task 02**. After the BOSS virtual disk recreation reboot from **Task 01**, nodes automatically attempt to boot from the next available device — which is the ISO or USB from Task 02. If the node is already at the "Press any key to boot from CD/DVD..." prompt or Windows Setup splash screen, **skip directly to Step 2** below.
:::

:::info Why Manual Installation
Full automation for Windows Setup OS deployment is not yet implemented. Manual installation through iDRAC Virtual Console provides reliable deployment and allows direct verification of BOSS card detection and disk partition layout.
:::

## Installation Procedure

:::tip Parallel Installation
To shorten total deployment time, run Windows Setup on multiple nodes simultaneously by opening separate iDRAC Virtual Console windows — one per node. Start all nodes before monitoring progress.
:::

### Step 1 — Open iDRAC Virtual Console

1. Open `https://<idrac-ip>` for the target node
2. Navigate to **Dashboard** → **Virtual Console** → **Launch**
3. Accept any certificate warnings; the Virtual Console window opens

If the node is still rebooting from the Task 01 BOSS recreation job, wait for the POST screen to complete. The node will boot from the ISO automatically.

### Step 2 — Boot from ISO

At the **"Press any key to boot from CD or DVD..."** prompt, press any key within 5 seconds.

:::warning Missed the Boot Prompt?
If the prompt is missed and the node attempts to boot from a non-existent OS, let it fail to a boot error, then reboot from iDRAC: **Power** → **Power Cycle System**. The prompt will appear again.
:::

Windows Setup loads the boot environment — this takes 1–3 minutes.

### Step 3 — Windows Setup Language Selection

1. Select **Language to install**, **Time and currency format**, and **Keyboard or input method** per site requirements
2. Click **Next**
3. Click **Install now**

### Step 4 — Accept License Terms

1. Read and accept the **Microsoft Software License Terms**
2. Check **I accept the license terms**
3. Click **Next**

### Step 5 — Select Installation Type

1. Select **Custom: Install Windows only (advanced)**

Do **not** select "Upgrade" — this is a clean installation.

### Step 6 — Disk Selection

:::danger Critical — Select the BOSS Card Only
**Select Drive 0 — the Dell BOSS card M.2 RAID-1 volume (~238 GB).**

If multiple drives are visible:

| Drive | Capacity | Description |
|-------|----------|-------------|
| **Drive 0** | ~238 GB | **Dell BOSS card** ← **Install OS here** |
| Drive 1–N | Larger | Data / NVMe drives ← **Do NOT install OS here** |

Installing the OS on a data drive will corrupt the storage pool intended for Azure Local workloads.
:::

Click **Drive 0 Unallocated Space** → **Next**.

Windows Setup automatically creates the required partitions:

| Partition | Size | Purpose |
|-----------|------|---------|
| Partition 1 | 100 MB | EFI System Partition |
| Partition 2 | 16 MB | Microsoft Reserved (MSR) |
| Partition 3 | Remaining | Primary OS partition |

### Step 7 — Monitor Installation

Installation takes 15–30 minutes and consists of five phases:

1. Copying Windows files
2. Getting files ready for installation
3. Installing features
4. Installing updates
5. Finishing up

The node reboots automatically when complete. **Do not interrupt the process.**

### Step 8 — Set Administrator Password

After the first reboot, Windows Server Core displays:

> "The user's password must be changed before signing in."

1. Click **OK**
2. Enter a strong Administrator password that meets Azure password length and complexity requirements: at least 14 characters, containing a lowercase character, an uppercase character, a numeral and a special character (Microsoft Learn 2610). The local administrator password must later be identical on all machines
3. Confirm the password
4. Press **Enter** or click the arrow
5. **"Your password has been changed"** — click **OK**

:::tip Store Password in Key Vault
Record the Administrator password and store it in the Key Vault referenced in `infrastructure.yml` under the `key_vaults[].name` value (secret name: `node-<hostname>-local-admin`). Do not save it in any file or document.
:::

### Step 9 — Verify Server Core Prompt

The Server Core command prompt (`C:\Users\Administrator>`) and `SConfig` menu appear. The node is now ready for Phase 03: OS Configuration.

:::danger Do not, while configuring the OS (Microsoft Learn 2610)
- **Do not install Windows Updates** with SConfig or Azure Update Manager (`Microsoft.SoftwareUpdateManagement.WindowsOsUpdateExtension`). Updates are installed during the deployment, and installing them beforehand causes a deployment failure.
- **Do not use an underscore (`_`) in the computer name.** It is not supported because it impacts storage path creation. Set the name in [Phase 03, Task 10](../../phase-03-os-configuration/task-10-configure-hostname.mdx).
- **Do not leave previously used non-OS drives or virtual media in place.** Clean all non-OS drives on each machine you intend to deploy, remove any virtual media used during OS install, and confirm no other root drives exist. This does not apply to a machine repair operation. Do not wipe SAN LUNs or other external storage this way: see [Phase 03, Task 11](../../phase-03-os-configuration/task-11-clear-previous-storage-configuration-conditional.mdx).
- **Do not rely on inbox NIC drivers.** Inbox drivers are not supported for Azure Local; an adapter whose `DriverProvider` is `Microsoft` is using one. Install the OEM driver (check with `Get-NetAdapter -Name <AdapterName> | Select *Driver*`).
- Copy a Solution Builder Extension to `C:\SBE` **only** if your hardware partner provides one. SBE is opt-in; it is never assumed.
:::

### Step 10 — Repeat for All Nodes

Perform Steps 1–9 for each remaining cluster node. Use parallel Virtual Console sessions where possible to reduce total installation time.

## Validation Checklist

- [ ] Windows Setup completed without errors on all nodes
- [ ] OS installed to Drive 0 (BOSS card) — not to data drives
- [ ] Correct partition layout: EFI + MSR + Primary
- [ ] Administrator password set (14+ characters, complexity met) and stored in Key Vault
- [ ] No Windows Updates installed through SConfig or Azure Update Manager
- [ ] Server Core command prompt and SConfig accessible on all nodes
- [ ] No installation errors or BSODs on first boot

## Troubleshooting

| Issue | Cause | Resolution |
|-------|-------|------------|
| No boot prompt / boot device not found | ISO not mounted or USB missing | Return to [Task 02](./task-02-mount-and-verify-dell-gold-image-iso.mdx) and remount |
| Missed "Press any key" prompt | Timed out | Power cycle node via iDRAC — prompt reappears on next boot |
| BOSS card not visible in drive list | BOSS controller disabled | Verify BIOS: **Device Settings** → **BOSS Controller** |
| Multiple drives shown, unsure which is BOSS | All drives visible | Select the smallest drive (~238 GB) — that is the BOSS RAID-1 volume |
| "Windows cannot be installed to this disk" | Leftover partitions from prior install | Delete all existing partitions on Drive 0 before proceeding |
| Installation hangs at "Getting ready" | ISO corruption or hardware fault | Reboot, re-mount ISO, retry |
| Password complexity error | Password does not meet policy | Use 14+ characters with uppercase, lowercase, numbers, and symbols |
| BSOD on first boot | Driver issue | Verify correct Dell gold image version is being used |
| No drives found at all | Missing storage drivers | Use the Dell gold image ISO — it includes required drivers |

## Optional: domain join before deployment

Starting with Azure Local 2604, you can domain join the machines **before** deployment. This is optional and applies to Active Directory deployments. For local identity deployments Microsoft Learn skips the AD prerequisites and verifies after deployment that the nodes report `WORKGROUP`, so do not domain join them.

Microsoft Learn 2610 states: "Starting with version 2604, domain joining before deployment is supported. If you choose to domain join, you must add the deployment user to the local Administrators group. If you don't domain join beforehand, the machines are automatically joined to a domain during the Deployment via Azure portal."

So there are two supported paths:

| Path | What you do | Who joins the domain |
|------|-------------|----------------------|
| **Default (workgroup)** | Nothing. Leave the machines in the workgroup. | The deployment (Azure portal or ARM template) joins them. |
| **Pre-join (2604 or later)** | Follow the steps below on every machine. | You do, before deployment. |

Use the same path on every machine of an instance. Active Directory must already be prepared (OU and deployment user created, see Part 3 Phase 01), the node DNS must be the DNS of the domain you are joining, and the domain controller must be reachable from the machines.

### Join procedure

<Tabs groupId="domain-join-method">
<TabItem value="sconfig" label="SConfig" default>

1. On each machine, in `SConfig`, choose option **1 Domain/workgroup** and join the machine to your domain.
2. Restart when prompted.
3. Continue with [add the deployment user](#add-the-deployment-user-to-local-administrators).

</TabItem>
<TabItem value="powershell" label="PowerShell">

```powershell title="Join the machine to the domain, directly into the deployment OU (run on each machine)"
$domain = "<DOMAIN_FQDN>"                              # identity.active_directory.domain_fqdn
$ouPath = "<DEPLOYMENT_OU_DISTINGUISHED_NAME>"        # identity.active_directory.ou_path
Add-Computer -DomainName $domain -OUPath $ouPath -Credential (Get-Credential) -Restart
```

`-OUPath` is a standard `Add-Computer` parameter. Placing the computer object in the Azure Local deployment OU at join time is Azure Local Cloud practice, so that the object lives in the OU that `New-HciAdObjectsPreCreation` prepared; Learn does not prescribe the join cmdlet. Do not move computer objects to a different OU after deployment: that is not supported.

</TabItem>
</Tabs>

### Add the deployment user to local Administrators

Run on each domain-joined machine (the deployment user is the LCM deployment account you created during AD preparation). Learn gives this command:

```powershell
Add-LocalGroupMember -Group "Administrators" -Member "DOMAIN\deploymentuser"
```

### Validate

Run on each machine and confirm the results:

```powershell
$cs = Get-CimInstance Win32_ComputerSystem
[pscustomobject]@{
  Computer     = $cs.Name
  PartOfDomain = $cs.PartOfDomain          # Expected: True
  Domain       = $cs.Domain
}

# Expected: the deployment user is listed
Get-LocalGroupMember -Group "Administrators" | Where-Object Name -like "*deploymentuser*"

# Expected: the computer object is in the deployment OU (run where the AD module is available)
Get-ADComputer -Identity $env:COMPUTERNAME | Select-Object Name, DistinguishedName
```

| Check | Expected |
|-------|----------|
| `PartOfDomain` | `True` on every machine (pre-join path), `False` on every machine (default path) |
| Deployment user | Member of local Administrators on every pre-joined machine |
| Computer object | In the deployment OU, not in the default Computers container |
| Environment Checker | Run the software validator with `-Exclude Test-IsNotPartofDomain`, per Microsoft Learn, so a pre-joined machine does not fail that check |

:::warning Do not mix paths
If the validation shows `PartOfDomain = True` on a machine you meant to leave in the workgroup, either complete the pre-join steps (add the deployment user) or remove the machine from the domain before you continue. Microsoft Learn documents both paths, not a partial one.
:::
