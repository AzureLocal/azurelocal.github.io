Troubleshooting and Known Issues

DOCUMENT CATEGORY: Runbook SCOPE: Troubleshooting simplified machine provisioning, portal and automated routes PURPOSE: Known issues, causes, and recovery MASTER REFERENCE: Microsoft Learn — Troubleshoot Simplified Machine Provisioning

Status: Active

Preview feature

Simplified machine provisioning is in preview, East US only, and doesn't support Arc gateway. Behavior can change between builds.

How to read this page

Items marked proven on Dell AX-760 / iDRAC 7.30 were seen on live runs of the azurelocal-ztp automation on two Dell AX-760 machines with iDRAC 7.30, Azure Local build 12.2690.1003.15 and maintenance image 10.2610.0.3063. They aren't confirmed on other hardware or builds. Where the cause is a best guess, the page says so. Items marked Learn come from Microsoft's documentation, with a link.

Overview​

This page has two parts: issues that Microsoft Learn documents, which apply to both routes, and issues found on live runs of the automation. Start with the summary table.

Issues found on live runs of the automation​

First OS install attempt fails with 5901​

Proven on Dell AX-760 / iDRAC 7.30.

Symptom. The ProvisionOs job fails at the step SetupHybridComputeRP with error 5901, "The device could not read or update its Azure registration", and job code Retryable. On the earlier runs it happened on the first OS install attempt of every machine. On the 2026-11-06 run, one of the two machines passed on its first attempt and the other hit 5901. Expect it, but not on every machine.

What was seen. The maintenance environment's log showed a 403 when it read the new Azure Arc machine. The role that allows the read is assigned seconds after the machine is created.

Likely cause (not confirmed). Azure role assignments can take time to propagate. The most likely explanation is that propagation took longer than the device's retry window, which is about 20 minutes. The 403 was confirmed only up to about minute 6 of that window.

What the automation does. The Ready stage resubmits the failed ProvisionOs job once, by sending the PUT for jobs/ProvisionOs again. Learn says the service doesn't retry a failed OS installation, so the automation does the resubmit for you. On the proven runs the single resubmit passed every time.

What you do. Usually nothing. If the resubmit also fails, the run stops with the reason. Then follow Reattempt a failed OS provisioning, and check the role assignments on the resource group.

A machine takes a long time to register after the claim​

Proven on Dell AX-760 / iDRAC 7.30.

Symptom. After the claim, a machine stays at RegisterMachine NotStarted, with lifecycle AwaitingConnection, for up to about 45 minutes: 42 minutes on the 2026-11-06 run. Another machine in the same run can register in a few minutes.

Outcome. It recovered by itself each time.

Likely cause (not confirmed). The gap between the device's retries to the onboarding service.

What you do. Wait. The Ready stage waits up to 180 minutes by default. Check the machine has power, network, and outbound access to Azure. If it doesn't register at all, collect logs as described in Collect logs.

iDRAC 7.30 behaviors the Boot stage works around​

Proven on Dell AX-760 / iDRAC 7.30. Other BMCs and firmware weren't tested.

BehaviorWhat the automation does
The WriteProtected=false field in the InsertMedia call is rejected.Sets the iDRAC manager attribute RFS.<n>.WriteProtected to Read Write with a Redfish PATCH on /redfish/v1/Managers/iDRAC.Embedded.1/Attributes, then inserts the media. Eject sets the attribute back to Read Only.
After that, Redfish still reports WriteProtected=True, although the share is open for write.Doesn't trust that field. It proves the attach with a read-back instead.
There is no Usb one-time boot target. The USB-stick slot boots as a virtual floppy (vFDD).Sets ServerBoot.1.FirstBootDevice=vFDD with boot-once. This is iDRAC 7.30 behavior, not generic Redfish behavior.
The ServerBoot setting is applied asynchronously.Also sets the standard Once and Floppy boot override (on 7.30, Floppy reaches the USB-stick slot), and waits until the BMC reports it before the reset.
Eject can return HTTP 500 (VRM0010) just after the machine writes to the image.Retries the eject.

Signals. The automation watches the iDRAC log for 10 minutes for event OSE1002, logged with the text "C: boot completed". The automation reads it as the installed OS booting. This is what the log showed on the proven runs, not a definition that Dell documents.

If the machine doesn't boot the image. The iDRAC's SMB client connects out to the management host on TCP 445. Check that the BMC can reach the host on that port, and check the share and the firewall rule on the host. See network paths.

After a failed Boot stage. Before you retry, check on each BMC that the virtual media is ejected and that the one-time boot setting is cleared. A leftover attached image or pending one-time boot can send the next attempt to the wrong place.

Arc machine names are device IDs​

Proven on Dell AX-760 / iDRAC 7.30.

Symptom. Cluster deployment can't find a machine, or fails at "Deploy Arc infrastructure components" with ParentResourceNotFound.

Cause. The provisioned machine (edgeMachines) is named in the Azure Local site after the name you gave it. The Azure Arc for Servers machine is named by the service, <device-id>-1, and the arcMachineResourceId set at claim time is overwritten. On build 12.2690.1003.15, an earlier Deploy failed because the Arc machine names are device IDs.

Why Deploy fails. The step Deploy Arc infrastructure components installs an Arc extension on each node's Arc machine. In the deployment package for that build, the step names the Arc machine after the node's host name, not from the machine's arcMachineResourceId. On the simplified route no Arc machine carries the host name, so Azure returns ParentResourceNotFound.

Why Validate doesn't catch it. Validate runs the readiness checks only. The deployment content that runs this step is downloaded when Deploy starts, so it isn't on the machines during Validate. Validate's Arc checks use the resource IDs you pass in, and those are correct. The ISO route never hits this, because there the Arc machine carries the host name.

What you do. Give cluster deployment each machine's arcMachineResourceId and Arc machine name from the handoff file. That's needed, but on an affected build it doesn't prevent the failure, and no workaround is known. Check Microsoft's known issues for your build, or use the ISO route for that build. The handoff reads them after the Ready stage, so they point at the service-created <device-id>-1 machine. See Output and handoff. Check the names before Deploy.

A resubmitted job keeps the earlier error​

Proven on Dell AX-760 / iDRAC 7.30.

Symptom. After a resubmit, Azure still shows the earlier attempt's error on the ProvisionOs job.

What you do. Don't treat that error as current. Check the job's state and the machine's lifecycle instead. If you run a monitor such as azurelocal-sonar, it must not read the old error as the current result.

Restart over WinRM drops the session​

Proven on Dell AX-760 / iDRAC 7.30.

Symptom. A restart inside a remote WinRM call kills the session before the call returns, so the caller sees an error although the restart worked.

What the automation does. The Prepare stage schedules the restart about 10 seconds out so the call returns first, then waits for the machine to come back with a new boot time. If you restart machines yourself during preparation, do the same.

The iDRAC USB link shows up as an adapter​

Proven on Dell AX-760 / iDRAC 7.30.

The iDRAC's USB link to the operating system (Remote NDIS, 169.254.0.x) appears as a network adapter. It isn't a cluster port, has no gateway, and must stay out of your network intents. Don't disable it or turn off its DHCP client: Dell requires it for the SBE firmware plug-in and SBE health checks (Dell SBE release notes).

Documented by Microsoft Learn​

Reattempt a failed OS provisioning​

Learn. If the OS installation fails, the deployment shows Your deployment failed and the resource reached the provisioning state Failed. Learn states that simplified machine provisioning doesn't retry automatically from the service.

Learn's recovery. Resubmit the ProvisionOs job:

  1. Open Azure Cloud Shell.
  2. Run the script that Learn provides. It reads the provisioned machine's userDetails and osProfile, then sends a PUT for the jobs/ProvisionOs resource with those values. You supply your subscription ID, resource group, and the provisioned machine name.
  3. Wait. The retry takes up to 30 minutes.

The full script is on Learn: Reattempt a failed OS provisioning. Use Learn's current version, because it uses a preview API version.

In the automation. The Ready stage runs this resubmit once, automatically.

USB boot loop with the maintenance environment​

Learn. If the BIOS setting Boot USB Devices First is set, the machine boots the USB media again after every restart. It reinstalls the maintenance environment and reboots, about every 10 minutes.

Learn's recovery. Boot from the USB device only once to install the maintenance environment, then set the machine to boot from the internal disk. See Prepare machines and your hardware vendor's documentation for the boot order.

In the automation. The Boot stage sets a one-time boot, not a permanent boot order. If you still see a loop, check the Boot USB Devices First setting in BIOS.

Operating system image drop-down is empty​

Learn. In Provision new machines, the Operating system > Image drop-down is empty.

Cause (Learn). The Microsoft.AzureStackHCI resource provider registration is missing.

Learn's recovery. Register the resource provider. See the Azure prerequisites. The automation checks the providers in the Bootstrap stage, before the claim.

ARM template validation fails when you provision​

Learn. Creating the machines fails with Arm template validation failed and The value for the template parameter 'hciRPServiceprincipalID' ... is not provided (InvalidTemplate).

Cause (Learn). This can happen if you use Azure Stack HCI for the first time in the subscription.

Learn's recovery.

  1. Delete the provisioned machine: Azure Arc > Operations > Machine provisioning (preview) > Provisioned machines, select the machine, then Delete.
  2. Wait 15 minutes.
  3. Provision the machine again with the voucher.

Internal server error when you provision (Azure Policy)​

Learn. Creating the site or machine fails with Failed to verify creation of MoboBroker resource (InternalServerError).

Cause (Learn). An Azure Policy blocks resource creation. Policies named by Learn:

  • resource groups must be in a specific region (the preview supports only eastus),
  • resource groups must follow a naming convention, or
  • resources must have tags. Learn says simplified machine provisioning doesn't currently support this requirement.

Learn's recovery.

  1. In the resource group, open Monitor > Activity log to find the policy that blocked creation.
  2. Add an Azure Policy exemption for that policy.
  3. If the managed resource group name is the cause, set the managed resource group name to match your policy. After you select the site, select Configure and set it. In the preview, only eastus supports managed resource groups.
  4. Delete the provisioned machine, then provision it again with the voucher.

Inbox drivers and default gateways after a fresh OS​

Learn. Inbox drivers aren't supported for Azure Local. An adapter uses an inbox driver if its DriverProvider property is Microsoft. Install the latest driver from your OEM. Also, network validation fails if it detects more than one physical adapter with a default gateway.

What was seen. Proven on Dell AX-760 / iDRAC 7.30. After a fresh OS, a machine has inbox drivers, DHCP and a default gateway on more than one port, and an empty C:\SBE. Dell states that the SBE can't install drivers or firmware during deployment, so the drivers must go on before Validate and Deploy.

What the automation does. The Prepare stage installs the SBE's network drivers, sets one static management address, and turns off DHCP and the gateway on the other adapters.

Check by hand.

Get-NetAdapter -Physical | Select-Object Name, InterfaceDescription, MacAddress, DriverProvider, DriverVersionString
Get-NetIPConfiguration | Select-Object InterfaceAlias, IPv4Address, IPv4DefaultGateway

Collect logs​

Learn. The logs are at these locations:

Target operating systemLog files
Azure Stack HCIC:\Windows\System32\Bootstrap\Logs
Maintenance environment/var/log/bootstrap, /var/log/provisioningextension, /var/log/trident-full.log, /var/log/messages, /var/log/bootstraprestservice

In the Configurator app, Support + troubleshooting can run diagnostic tests and create a support package. See Learn.

For the automation, the event file ztp-events.jsonl in the ztp-state folder records each stage with a timestamp. azurelocal-sonar can read it live.
