## Overview

The operator supplies one input: **the master `infrastructure.yml`** of the [azurelocal-toolkit](https://github.com/AzureLocal/azurelocal-toolkit/tree/main/config/variables), schema 5. Every tool in the route reads the same file: ZTP, [OS configuration](../../../phase-03-os-configuration/index.mdx) and the cluster deployment. It describes the machines, the network, the BIOS settings and the Azure target. Everything else is automated, with a gate at each step.

:::info Schema 5 is the only input
ZTP reads only the toolkit's `infrastructure.yml` (`_metadata.schema_version` 5.x). Its own older environment-file layout (`cluster_nodes`, `network_intents`, `ztp`) is retired since azurelocal-ztp 5b75c9a: any other file, or a missing one, stops the run with exit code 2. The full key reference is [azurelocal-ztp: infrastructure file reference](https://azurelocal.cloud/azurelocal-ztp/environment-file).
:::

:::note The OEM SBE is not a ZTP input
ZTP resolves and stages no SBE, and it reads no `hardware.sbe`. The SBE package (`hardware.sbe.source_path` in the master file) is a requirement and is read by OS configuration, which puts it in `C:\SBE` and installs the OEM's network drivers from it. See [The OEM SBE](#the-oem-sbe).
:::

`Invoke-ZtpEnvironment.ps1` checks the file, then generates the JSON inputs that the stage scripts need. Those generated files are specific to your environment. Don't copy them between environments or commit them.

## The environment file

The file is passed with `-InfrastructureFile`. There is no default path. The tables list only the keys ZTP reads; the file can hold every other key of the schema, and ZTP ignores them.

### Which template to start from

- **ZTP only.** You install the OS and register the machines with ZTP, and run no automation after it: the [ZTP-only template](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/examples/infrastructure.ztp.example.yml) (`_metadata.scope: ztp`). It holds only the keys ZTP reads. A file with `_metadata.scope: ztp` needs no `identity` section, and its `hardware.sbe` is not checked (registry 5.0.61).
- **ZTP, then OS configuration and deployment.** The [full template](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/examples/infrastructure.example.yml). ZTP reads its part of it and ignores the rest.

Check the file with the toolkit before a run (in the toolkit clone):

```powershell
./scripts/common/infrastructure/Test-InfrastructureFile.ps1 -Path ./infrastructure.yml
```

:::info How ZTP checks the file
When the toolkit is found (`$env:AZL_TOOLKIT_ROOT`, else an `azurelocal-toolkit` clone next to the ZTP clone), ZTP runs the toolkit's check of the schema and the rules, and its errors stop the run. ZTP then always runs its own check and lists every problem at once, in schema 5 paths. It runs an extra validator only when `-ValidatorPath` names one; it looks for none by default.
:::

### Example

All values are placeholders for the example company: `iic-*` names, addresses from the RFC 5737 documentation ranges, MAC addresses from the RFC 7042 range, all-zero GUIDs.

```yaml title="infrastructure.yml (the keys ZTP reads)"
_metadata:
  schema_version: "5.6.27"
  scope: ztp                        # optional: a file for ZTP only

scenario:
  os_install: simplified
  outbound_path: direct             # or proxy

azure:
  tenant_id: "00000000-0000-0000-0000-000000000000"
  subscription_id: "00000000-0000-0000-0000-000000000000"
  resource_group: "rg-iic-azl-01"
  location: eastus                  # preview: eastus only

site:
  name: "IIC site 01"
  time_zone: "UTC"

key_vaults:
  - { name: "kv-iic-mgmt-01", subscription_id: "00000000-0000-0000-0000-000000000000", resource_group: "rg-iic-mgmt-01" }

hardware:
  vendor: Dell                      # picks config/oem/dell.json; the Boot and Bootstrap stages stop without it
  bmc:
    username: "keyvault://kv-iic-mgmt-01/bmc-username"   # or env://, file://, command://, or the name itself
    password: "keyvault://kv-iic-mgmt-01/bmc-password"

networking:
  management:
    subnet: "192.0.2.0/24"
    gateway: "192.0.2.1"
    dns_servers: ["192.0.2.30", "192.0.2.31"]

nodes:
  - name: "iic-azl-n01"
    serial_number: "SERIAL01"
    bmc: { ip_address: "198.51.100.11" }
    network_adapters:
      - { name: "Embedded NIC 1", mac_address: "00:00:5E:00:53:11", roles: [management], ip_assignment: static, ip_address: "192.0.2.11" }

provisioning:
  os_version: "<solution-version>"  # pin a validated solution recipe version; Get-ZtpOsImage.ps1 lists them
  simplified:
    site_name: "iic-site-01"
    maintenance_iso: latest
    media_share: { host: "192.0.2.10", name: "ztp-virtual-usb" }
    admin: { username: "administrator", password: "keyvault://kv-iic-mgmt-01/provisioning-admin-password" }
    maintenance_password: "keyvault://kv-iic-mgmt-01/maintenance-password"
```

### Machines and network

| Key | What it is |
|-----|------------|
| `nodes[].name` | The node name. Also the name of its provisioned machine in Azure. |
| `nodes[].serial_number` | The machine serial or service tag. It must match the serial in the voucher. |
| `nodes[].bmc.ip_address` | The BMC address. The BMC login is `hardware.bmc`; a node that sets another login stops the run. |
| `nodes[].network_adapters[]` | The machine's ports. ZTP reads the **management port**: the one entry with role `management` and an `ip_assignment` other than `none`. |
| Management port `mac_address` | The Device stage finds the maintenance environment's adapter by it, the Network stage finds the installed machine's adapter by it, and OS configuration finds the port by it too. The installed OS names its ports `Port0` to `Port6`. |
| Management port `ip_assignment` | `dhcp_reservation` (Mode A, recommended), `static` (Mode B or C), `dhcp` or `preconfigured`. See [Management address modes](./index.mdx#management-address-modes). |
| Management port `ip_address` | The node's management address. With `static`, the Device stage sets it on the port with the MAC above before the claim; with `dhcp_reservation`, the Network stage verifies it. |
| `nodes[].maintenance_address` | Optional. The maintenance environment's address. Without it, the Device stage scans `networking.management.provisioning_dhcp_range` (default: the management subnet) by MAC. |
| `networking.management.static_method` | Who sets a static address: `device` (default, the Device stage) or `site`. |
| `networking.management.subnet` | Management subnet in CIDR form. The prefix length is read from it. |
| `networking.management.gateway` | The one default gateway. |
| `networking.management.dns_servers` | DNS servers for the management network. ZTP passes them to the Device stage (Modes B and C); OS configuration sets them on the host. |
| `hardware.bios` and `hardware.bios_during_provisioning` | BIOS settings by attribute. Boot applies `bios_during_provisioning` over `bios`, so an install-only value wins; Restore sets those attributes back. See [BIOS isolation during the install](./index.mdx#bios-isolation-during-the-install). |
| `hardware.vendor` | The OEM, such as `Dell`. It selects `config/oem/<vendor>.json` (the BMC log services and signals, the BIOS slot mapping, the one-time USB boot). ZTP has no built-in vendor: the Boot and Bootstrap stages stop without it. |

### Azure target

| Key | What it is |
|-----|------------|
| `azure.tenant_id` | Tenant of every Azure call. |
| `azure.location` | Region. The preview supports East US only. |
| `azure.subscription_id`, `azure.resource_group` | Subscription and resource group of the site and the machines. The run creates the group if it doesn't exist. |
| `provisioning.simplified.subscription_id`, `.resource_group` | Optional. The same, when the provisioning resources go elsewhere than `azure.*`. |
| `azure.hci_resource_provider_object_id` | Optional. Object ID of the Azure Local resource provider in your tenant. If you leave it out, the script looks it up, which needs directory read rights that a managed identity doesn't have by default. Set it for pipelines. |
| `site.name`, `site.time_zone` | Display name and time zone of the site. |
| `provisioning.simplified.site_name` | Resource name of the Azure Local site. |
| `tags` | Optional. Tags for the site configuration and the edge machines. |

### ZTP settings

| Key | What it is |
|-----|------------|
| `provisioning.simplified.maintenance_iso` | Which maintenance ISO to resolve: `latest`, a train such as `2610`, a build, or a Microsoft download URL. |
| `provisioning.os_version` | The Azure Local OS solution version to install: `latest`, `latest-preview`, or a validated solution recipe version. ZTP does not check it against an SBE: pin a build your OEM supports. |
| `provisioning.simplified.media_share.host` or `.host_adapter` | The address of the management host as the BMCs reach it. Use `host_adapter` to name the network adapter and let the script read its IPv4 address, or `host` to give the address. One of them is required. |
| `provisioning.simplified.media_share.name` | Name of the SMB share for the images. |
| `provisioning.simplified.media_path`, `.evidence_path` | Optional. Where the run keeps its downloads and its evidence (the event log Sonar follows). Default: under `%ProgramData%\AzureLocalZtp\<site_name>`. Never inside a git working tree. |

### Secrets

The file holds **references only**, never values. ZTP reads each reference through the toolkit's one resolver (`scripts/common/secrets/AzlSecret.psm1`), so it needs the toolkit: `$env:AZL_TOOLKIT_ROOT`, or an `azurelocal-toolkit` clone next to the ZTP clone. With `-Execute` and no toolkit, the run stops with exit code 2 before it writes anything. The plan (without `-Execute`) reads no secret. Nothing prompts.

| Key | What it points to |
|-----|-------------------|
| `hardware.bmc.username`, `hardware.bmc.password` | The BMC login of every machine: a secret reference (`keyvault://`, `env://`, `file://` or `command://`); the user name may also be given as plain text. |
| `provisioning.simplified.admin.username`, `.password` | The provisioning administrator. The password is a `keyvault://<vault>/<secret>` reference only: Azure reads it from the vault itself when it provisions the machines. The secret must exist before the run. |
| `provisioning.simplified.maintenance_password` | Optional. The maintenance environment's `edgeuser` password, any provider. Without it the image keeps the published default. |
| `key_vaults[]` | Every vault a `keyvault://` reference names. |
| `secrets.file.directory`, `secrets.command.*` | Where the resolver reads `file://` and `command://` references from. |
| `identity.local_admin` | The deployment administrator. ZTP doesn't read it: [OS configuration](../../../phase-03-os-configuration/index.mdx) creates the account. |

:::danger Never commit secret values
Don't put a password, token or key in the file or in any file you commit. The run reads the values through the resolver at run time.
:::

## The OEM SBE

A Solution Builder Extension (SBE) is the hardware vendor's package for an Azure Local release. The OEM requires its network drivers to be on the machine before Validate and Deploy; for Dell, the SBE can't install drivers or firmware during deployment. ZTP does neither: **OS configuration** puts the SBE in `C:\SBE` and installs the drivers from it.

The package is a **requirement**. Download your hardware vendor's Solution Builder Extension package for your model and the Azure Local version you deploy, before you start, into one folder or share outside any repository, and set `hardware.sbe.source_path` in the master file to it (`bundle_path` has the same meaning, and `source_path` is the one read when both are set). You need it to update the cluster, and the automation reads it from the share and checks it before the cluster is created. Dell requires a support account for the download. To install it during the build, switch on the side-load with `hardware.sbe.delivery`; it is off by default. Vendors differ, so check your vendor's page. The checks, the keys and the vendor summary are in [the SBE package prerequisite](../../../../04-prerequisites-and-assumptions.mdx#sbe-package).

| File | Purpose |
|------|---------|
| `SBE_<...>.zip` | The SBE package. The folder must hold exactly one `SBE_*.zip`. |
| `SBE_<...>.xml` | The package's metadata. It has the same name as the zip, with `.xml`. |
| `SBE_Discovery_<oem>.xml` | The OEM's SBE discovery manifest. |

How the files reach each node is a separate choice (`hardware.sbe.delivery`); see [Automated OS configuration](../../../phase-03-os-configuration/automated-os-configuration.mdx#the-sbe-delivery-route).

## Validation

- [ ] The file is schema 5 (`_metadata.schema_version` 5.x) and passes `Test-InfrastructureFile.ps1`
- [ ] Every machine has `name`, `serial_number`, `bmc.ip_address` and a management port with `mac_address` (and `ip_address` for `static`)
- [ ] `hardware.vendor` is set
- [ ] `provisioning.simplified.media_share.host` or `.host_adapter` is set to the address the BMCs reach
- [ ] The secrets the references name exist, the file holds no secret values, and the toolkit clone is found (`AZL_TOOLKIT_ROOT` or next to the ZTP clone)
- [ ] If the machines have BIOS settings that differ during the install, `bios_during_provisioning` names them and `bios` holds the final values
- [ ] The SBE share or folder (read by OS configuration and the cluster update, not by ZTP) holds the zip, its XML and the discovery XML, or `hardware.sbe.requirement` is `not_applicable` with a reason
