## Azure

These are Microsoft's prerequisites for simplified machine provisioning (see [Learn](https://learn.microsoft.com/en-us/azure/azure-local/deploy/simplified-machine-provisioning?view=azloc-2610#azure-prerequisites)). The automation checks the feature and the resource providers in the Bootstrap stage and doesn't report a machine ready until they're registered. It doesn't check roles up front: missing roles make the template validation in the Azure stage fail.

| Requirement | Details |
|-------------|---------|
| Feature registration | `Microsoft.DeviceOnboarding/AzureLocalZTP` registered on the subscription. See [Task 03](../task-03-provision-from-azure.mdx#step-1-register-the-provisioning-feature) for the command. |
| Resource providers | Registered, as listed in the [section overview](../index.mdx#azure). |
| Region | East US for the provisioning resources (preview limit). The resource group can be in another region. |
| Operator roles | Owner on the resource group, or Contributor and Role Based Access Control Administrator on it. The identity that runs the automation needs these. |
| Key Vault, administrator secret | A vault that holds the provisioning administrator password as a secret. The secret must exist before the run, because `Invoke-ZtpEnvironment.ps1` doesn't pass a password. The identity also needs rights to delegate on this vault, because the machine's role delegation includes a Key Vault role. |
| Key Vault, BMC account | A secret for the BMC user name and one for the BMC password, which the run reads. See [Operator inputs](./operator-inputs.mdx). |
| Key Vault, deployment administrator | A secret for the local administrator password used for cluster deployment, referenced as `keyvault://<vault>/<secret>`. |
| Resource provider object ID | The object ID of the Azure Local resource provider in your tenant. Set it in the environment file so the run doesn't need directory read rights, which a managed identity doesn't have by default. |

:::note Roles are a one-time setup
Someone with enough rights gives the automation identity its roles once, before the first run. After that the run needs no more than the roles above.
:::

## Hardware and BMC

| Requirement | Details |
|-------------|---------|
| Machines | Hardware that supports simplified machine provisioning. Learn lists Dell AX-750 and AX-650, Lenovo ThinkAgile MX650 V3 and V4, and HPE ProLiant DL360 Gen11. The automation was **proven on Dell AX-760 with iDRAC 7.30**. |
| BMC | A BMC with Redfish and a way to attach a virtual USB image over SMB. Dell iDRAC is proven. The repository carries OEM definitions for other vendors, but only Dell is complete. |
| BMC account | An account that can insert virtual media, change iDRAC manager attributes, set the one-time boot, and reset the machine. Change the iDRAC factory password first, and keep the credential in Key Vault. |
| Firmware | Match the BMC and machine firmware to the OEM's Azure Local support matrix before you start. Only iDRAC 7.30 was proven. |
| Secure Boot and TPM | Enabled, as Learn requires for the maintenance environment. |
| Machine state | The machines carry no cluster to keep. The run **reinstalls** them. |
| OEM SBE package | A requirement, downloaded before you start. ZTP itself does not read it, but the OS configuration run and the update later do. Download your hardware vendor's Solution Builder Extension package for your model and the Azure Local version you deploy, and put it on a share the automation can read. To install it during the build, switch on the side-load in the file; it is off by default. See [The OEM SBE](./operator-inputs.mdx#the-oem-sbe) and [the SBE package prerequisite](../../../../04-prerequisites-and-assumptions.mdx#sbe-package). |

:::caution BMC behavior proven on iDRAC 7.30 only
The Boot stage works around several iDRAC 7.30 behaviors, such as the `InsertMedia` call rejecting `WriteProtected=false`, and `Floppy` being the one-time boot override that reaches the USB-stick slot. These are described in [Troubleshooting and known issues](../troubleshooting.mdx#idrac-730-behaviors-the-boot-stage-works-around). Other BMC models and firmware haven't been proven.
:::

## Network paths

| From | To | Port | Used for |
|------|----|------|----------|
| Management host | BMC | TCP 443 (HTTPS, Redfish) | Insert media, set boot, reset, read power, boot state and logs |
| **BMC** | **Management host** | **TCP 445 (SMB)** | The iDRAC's SMB client connects out to the share on the host to read and write the virtual USB image |
| Management host | The maintenance environment of each machine (its `maintenance_address`, or the provisioning DHCP range) | TCP 20001 (HTTPS, self-signed) | The Device stage (Modes B and C), before the claim: find the machine by its MAC and set the static management address. Keep the range isolated. |
| Management host | Azure | HTTPS | Azure Resource Manager, Key Vault, downloads |
| Machine | Azure | HTTPS | Call-home, OS download, Arc registration. See [Azure Local firewall requirements](https://learn.microsoft.com/en-us/azure/azure-local/concepts/firewall-requirements?view=azloc-2610). |

The BMC-to-host path is the one people miss. The direction matters: the BMC connects out to the host, so no inbound port is needed on the BMC. The Boot stage creates a firewall rule on the host that allows inbound TCP 445 only from the BMC addresses, and the share uses a dedicated local account. If a firewall between the BMC network and the host blocks the connection, the BMC can't read the image and the machine never boots the maintenance environment.

You can check endpoint and network readiness before the first run with [azurelocal-beacon](https://azurelocal.cloud/azurelocal-beacon/).

## Management host

| Requirement | Details |
|-------------|---------|
| Operating system | **Windows.** The Boot stage shares the images over SMB with Windows commands, so Linux and macOS hosts don't work. |
| PowerShell | PowerShell 7 or later. |
| Elevation | Run elevated. The Boot stage creates an SMB share, a local account and a firewall rule on the host. |
| Azure sign-in | The Az PowerShell modules, signed in as an identity that has the [Azure roles](#azure). With `-UseManagedIdentity` the script signs in as the managed identity attached to the host. |
| Bicep | Available on the host. `Invoke-ZtpEnvironment.ps1` adds the Azure CLI's Bicep folder to `PATH`, so installing the Azure CLI's Bicep is enough. |
| `powershell-yaml` | Reads the environment file. |
| Pester 5 | Only needed to run the repository's tests. |
| Disk | Space for the maintenance ISO and one image per machine. |
| Network | The [paths above](#network-paths). |

The host can be a dedicated server, a VM on the management network, or a self-hosted pipeline runner. See [Run from a pipeline](./run-from-pipeline.mdx).

## Security

:::caution Before the first run
- **Change the iDRAC factory password** and keep the BMC credential in Key Vault.
- **Vouchers are secrets.** A voucher proves ownership of a machine. Restrict the folder that holds them and delete them when provisioning is done.
- **The read-write SMB share is a tampering risk while it is up.** The Boot stage limits it to the BMC addresses with a firewall rule and removes it after the Vouchers stage. Keep the host on an isolated network and consider requiring SMB signing.
- **After a failed Boot stage**, check on each BMC that the media is ejected and the one-time boot is cleared before you retry.
:::

## Validation

- [ ] `Microsoft.DeviceOnboarding/AzureLocalZTP` registered and the resource providers registered
- [ ] The operator identity holds the required roles on the resource group
- [ ] The administrator, BMC and deployment administrator secrets exist in Key Vault
- [ ] The management host can reach every BMC on TCP 443, and every BMC can reach the host on TCP 445
- [ ] The management host runs Windows with PowerShell 7, elevated, signed in to Azure
- [ ] The OEM SBE package (three files) is downloaded and available on a share the automation can read. ZTP does not read it, but the OS configuration run and the later cluster update need it
