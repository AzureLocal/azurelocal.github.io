Operator Inputs: The Environment File

DOCUMENT CATEGORY: Runbook SCOPE: Operator inputs for the azurelocal-ztp zero-touch automation PURPOSE: Fill in the environment file, and know where the OEM SBE belongs MASTER REFERENCE: azurelocal-ztp repository

Status: Active

Overview​

The operator supplies one input: the environment file, a YAML file that describes the machines, the network, the BIOS settings, the Azure target and the ZTP settings. Everything else is automated, with a gate at each step.

The master file, and the older layout

New files use the master infrastructure.yml (schema 5), the one file that every tool in the route reads: ZTP, OS configuration and the cluster deployment. Its schema, examples and variables reference are in the azurelocal-toolkit and described in azurelocal-ztp: schema 5. The example and tables below use the older layout, which ZTP still reads; the keys map one to one.

The OEM SBE is not a ZTP input

ZTP resolves and stages no SBE. The SBE package (hardware.sbe.source_path in the master file) is a requirement and is read by OS configuration, which puts it in C:\SBE and installs the OEM's network drivers from it. A ztp.node_preparation block in an old file is accepted and ignored. See The OEM SBE.

Invoke-ZtpEnvironment.ps1 validates the environment file, then generates the JSON inputs that the stage scripts need. Those generated files are specific to your environment. Don't copy them between environments or commit them.

The environment file​

The file is passed with -InfrastructureFile. The scripts read the keys below. The tables list only the keys the ZTP scripts use. Your environment file can carry more keys for other tools.

Validation before anything runs

If a tools\Validate-Infrastructure.ps1 script sits next to the environment file's folder, Invoke-ZtpEnvironment.ps1 runs it first and stops if it fails. If the script is absent, the run warns that the file wasn't checked. Check the file yourself in that case.

Example​

This is the template from the repository, examples/infrastructure.example.yml. Copy it, keep your copy outside the repository clone, and replace every value. All values here are placeholders: addresses are from the RFC 5737 documentation ranges, MAC addresses from the RFC 7042 range. The tables below describe each key, and the environment file reference has the format of each one.

infrastructure.yml
azure_identity:
  azure_tenant_id: "<tenant-id>"

azure_resources:
  # Region of the site configuration and the edge machines. Preview: eastus only.
  location: eastus

site:
  name: "Example site"

hardware:
  vendor: Dell                     # picks config/oem/dell.json (BMC log services and signals)
  # BIOS: the final settings, and any that must differ during the install only (see below).
  # bios:
  #   Slot2: Enabled
  # bios_during_provisioning:
  #   Slot2: Disabled

network_intents:
  management:
    subnet: 192.0.2.0/24
    gateway: 192.0.2.1
    dns_servers:
      - 192.0.2.53
      - 192.0.2.54

cluster_nodes:
  - name: node-01
    service_tag: <serial-number-1>
    idrac_ip: 198.51.100.11        # BMC address
    ip_address: 192.0.2.11         # management address, set on the port with the MAC below
    mac_address: "00-00-5E-00-53-01"
  - name: node-02
    service_tag: <serial-number-2>
    idrac_ip: 198.51.100.12
    ip_address: 192.0.2.12
    mac_address: "00-00-5E-00-53-02"

ztp:
  subscription_id: "<subscription-id>"
  resource_group: <resource-group>
  site_name: <site-name>
  time_zone: UTC
  # Pin a validated solution recipe version (12.YYMM.x.y); Get-ZtpOsImage.ps1 lists them. latest also works.
  os_version: "<solution-version>"
  # Maintenance ISO: latest, a train such as 2610, a build, or a Microsoft download URL.
  provisioning_iso: latest

  # The address the BMCs reach this host on. Or set share_host_adapter to a local adapter name instead.
  share_host: 192.0.2.10
  # share_host_adapter: "<adapter-name>"
  share_name: ztp-virtual-usb

  # Object ID of the Azure Local resource provider service principal in your tenant. Set it for pipelines.
  # azl_rp_object_id: "<object-id>"

  tags:
    workload: azurelocal

  # Provisioning administrator. The secret must exist before the run.
  admin_secret:
    subscription_id: "<subscription-id>"
    resource_group: <key-vault-resource-group>
    vault: <vault-name>
    name: <provisioning-admin-secret-name>
    username: <provisioning-admin-username>

  # BMC login: two secrets, the user name and the password.
  bmc_secret:
    vault: <vault-name>
    username_name: <bmc-username-secret-name>
    password_name: <bmc-password-secret-name>

Machines and network​

KeyWhat it is
cluster_nodes[].nameThe node name. Also the name of its provisioned machine in Azure.
cluster_nodes[].service_tagThe machine serial or service tag. It must match the serial in the voucher.
cluster_nodes[].idrac_ipThe BMC address.
cluster_nodes[].ip_addressThe node's management address. With a static assignment (Mode B or C), the Device stage sets it on the port with the MAC below before the claim; with a DHCP reservation (Mode A), the Network stage verifies it. See Management address modes.
cluster_nodes[].mac_addressThe MAC of the management port. The Device stage finds the maintenance environment's adapter by it, the Network stage finds the installed machine's adapter by it, and OS configuration finds the port by it too. The installed OS names its ports Port0 to Port6.
network_intents.management.ip_assignmentHow each management address is set: dhcp_reservation (Mode A, recommended), static (Mode B or C), dhcp or preconfigured.
network_intents.management.static_methodWho sets a static address: device (default, the Device stage) or site.
network_intents.management.subnetManagement subnet in CIDR form. The prefix length is read from it.
network_intents.management.gatewayThe one default gateway.
network_intents.management.dns_serversDNS servers for the management network. ZTP passes them to the Device stage (Modes B and C); OS configuration sets them on the host.
hardware.bios and hardware.bios_during_provisioningBIOS settings by attribute. Boot applies bios_during_provisioning over bios, so an install-only value wins; Restore sets those attributes back. See BIOS isolation during the install.
hardware.vendorThe OEM, such as Dell. It selects the OEM definition for the BMC (manager and system IDs, the USB-stick slot, the log signals).

Azure target and identity​

KeyWhat it is
azure_identity.azure_tenant_idTenant for sign-in and for the Azure context.
azure_resources.locationRegion. The preview supports East US only.
site.nameDisplay name of the site.
ztp.subscription_idSubscription of the site and the machines.
ztp.resource_groupResource group of the site and the machines. The run creates it if it doesn't exist.
ztp.site_nameName of the Azure Local site resource.
ztp.time_zoneSite time zone.
ztp.tagsTags for the resource group and for the resources the deployment creates.
ztp.azl_rp_object_idObject ID of the Azure Local resource provider in your tenant. If you leave it out, the script looks it up, which needs directory read rights that a managed identity doesn't have by default.

ZTP settings​

KeyWhat it is
ztp.provisioning_isoWhich maintenance ISO to resolve: latest, a train such as 2610, a build, or a Microsoft download URL.
ztp.os_versionThe Azure Local OS solution version to install: latest, latest-preview, or a validated solution recipe version. ZTP does not check it against an SBE: pin a build your OEM supports.
ztp.share_host or ztp.share_host_adapterThe address of the management host as the BMCs reach it. Use share_host_adapter to name the network adapter and let the script read its IPv4 address, or share_host to give the address. One of them is required.
ztp.share_nameName of the SMB share for the images.

Secrets​

The environment file holds names and references only, never values.

KeyWhat it points to
ztp.admin_secret.*The Key Vault secret that holds the provisioning administrator password, and that administrator's user name. Provisioning sets this account on the installed OS. The secret must exist before the run.
ztp.bmc_secret.*The vault and the names of the secrets that hold the BMC user name and the BMC password.
identity.local_admin (master file)The deployment administrator's name and Key Vault password reference. ZTP doesn't read it: OS configuration creates the account.
Never commit secret values

Don't put a password, token or key in the environment file or in any file you commit. The run reads the values from Key Vault at run time.

The OEM SBE​

A Solution Builder Extension (SBE) is the hardware vendor's package for an Azure Local release. The OEM requires its network drivers to be on the machine before Validate and Deploy; for Dell, the SBE can't install drivers or firmware during deployment. ZTP does neither: OS configuration puts the SBE in C:\SBE and installs the drivers from it.

The package is a requirement. Download your hardware vendor's Solution Builder Extension package for your model and the Azure Local version you deploy, before you start, into one folder or share outside any repository, and set hardware.sbe.source_path in the master file to it (bundle_path has the same meaning, and source_path is the one read when both are set). You need it to update the cluster, and the automation reads it from the share and checks it before the cluster is created. Dell requires a support account for the download. To install it during the build, switch on the side-load with hardware.sbe.delivery; it is off by default. Vendors differ, so check your vendor's page. The checks, the keys and the vendor summary are in the SBE package prerequisite.

FilePurpose
SBE_<...>.zipThe SBE package. The folder must hold exactly one SBE_*.zip.
SBE_<...>.xmlThe package's metadata. It has the same name as the zip, with .xml.
SBE_Discovery_<oem>.xmlThe OEM's SBE discovery manifest.

How the files reach each node is a separate choice (hardware.sbe.delivery); see Automated OS configuration.

Validation​

  • The environment file passes the validator, or you have checked it by hand
  • Every machine has name, service_tag, idrac_ip, ip_address and mac_address
  • ztp.share_host or ztp.share_host_adapter is set to the address the BMCs reach
  • The secrets named in the file exist in Key Vault, and the file holds no secret values
  • If the machines have BIOS settings that differ during the install, bios_during_provisioning names them and bios holds the final values
  • The SBE share or folder (read by OS configuration and the cluster update, not by ZTP) holds the zip, its XML and the discovery XML, or hardware.sbe.requirement is not_applicable with a reason
