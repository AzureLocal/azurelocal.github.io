## Overview

The automation ends at the **Handoff**. At that point each machine is Provisioned in Azure, connected to Azure Arc with its mandatory extensions, and has its BIOS on its final settings. The machines are **not yet ready for Validate**: the OEM's drivers, the SBE in `C:\SBE`, DHCP and gateways on the other ports, DNS, time, the host name, the deployment administrator, and (in Modes B and C) the static management address are still to do. That is [OS configuration](../../../phase-03-os-configuration/index.mdx).

The automation does **not**:

- configure the OS (see above),
- prepare Active Directory,
- run cluster Validate, or
- deploy the cluster.

See [Which provisioning method, then OS configuration](../../../phase-03-os-configuration/which-method-then-os-configuration.mdx), [Prepare your Active Directory](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deployment-prep-active-directory?view=azloc-2610) and the [cluster deployment phase](../../../phase-05-cluster-deployment/index.mdx).

## The end state

A successful run ends with a message that ZTP is done, with the next step named, and a table per node with the management port marked:

```text
ZTP is done: the machines are Provisioned and Arc-connected. ...
Next: OS configuration (OEM drivers, the SBE in C:\SBE, DHCP off on the other ports, DNS and time, the deployment admin), then Validate and Deploy.
```

Before it writes the handoff, the run has checked each machine:

| Check | Evidence |
|-------|----------|
| Azure reports the machine Ready to cluster | Provisioned, `ProvisionOs` job succeeded, Arc Connected, extensions done (the Ready stage, and again after Restore) |
| The management address, by mode | Network: Mode A, the reserved address is on the port with the management MAC. Modes B and C, the OS install reset the static, so the machine is recorded as left to OS configuration |
| The BIOS values changed for the install are back | Restore, recorded as `biosRestored` |

You can also confirm in the Azure portal. Go to **Azure Arc** > **Operations** > **Provisioning (preview)** > **Provisioned machines**. Each machine shows **Ready to cluster**. See [Task 05](../task-05-verify-arc.mdx) for the portal checks.

## Files the run writes

The run writes its state and outputs to the `ztp-state` folder under the `_media` folder at the root of the repository clone. The file names start with the run name, which is the names of the machines in the run joined with `+`.

| File | What it holds |
|------|---------------|
| `<run>.ztp-handoff.json` | The handoff (schema 2), only what Azure generated: for each machine, its name, serial, provisioned machine name and resource ID, Arc machine name, **`arcMachineResourceId`**, the management mode, `managementAddressVerified` with its reason, `biosRestored`, and every port as Azure reports it. It also records the site and the installed OS build (`solution.vsrVersion`). It no longer carries SBE, bootstrap or timestamp blocks. |
| `<run>.ztp-cluster-inputs.yaml` | The cluster inputs: an `arc_machine_names` block that maps each node name to its Arc machine name, plus `release.azure_local_version`, the build installed. The SBE values for deployment come from OS configuration. |
| `<run>.arc-machine-names.json` | The map from node to Arc machine name. |
| `<run>.ztp-provisioning.state.json` | The state file that makes the run resumable. |
| `ztp-events.jsonl` | Structured events that Sonar can follow. |

The handoff and cluster inputs hold environment-specific names and resource IDs. Treat them as internal. Don't publish them.

## What to hand to OS configuration and cluster deployment

OS configuration reads the **handoff file** (`-HandoffFile`) for each machine's `arcMachineResourceId`, the installed build and the management address result, and the master `infrastructure.yml` for everything else. Cluster deployment needs **each machine's `arcMachineResourceId`** and the `arc_machine_names` map in the cluster inputs file.

:::caution Use the Arc names from the handoff, not the node names
Simplified machine provisioning creates two resources for each machine:

- the **provisioned machine** (`edgeMachines`), which is named in the Azure Local site after the name you gave it, and
- the **Azure Arc for Servers machine**, which the service names `<device-id>-1`.

The `arcMachineResourceId` that the claim sets is overwritten by the service. The handoff reads each `arcMachineResourceId` after the Ready stage, so it points at the service-created `<device-id>-1` machine. The Arc machine name is therefore **not** the node name. If cluster deployment builds the Arc resource ID from the node name, it points at a resource that doesn't exist.

On build 12.2690.1003.15, an earlier Deploy failed at "Deploy Arc infrastructure components" with `ParentResourceNotFound` because the Arc machine names are device IDs. Check the names before Deploy.
:::

To convert a handoff file into the cluster inputs block yourself, the repository has `Convert-ZtpHandoffToClusterInputs.ps1`. It takes `-HandoffPath`, an optional `-Only` of `arc_machine_names`, `sbe` or `release`, and `-Format` of `Yaml` or `Json`. See the script's help for the full parameters.

Check the `release` value against your cluster deployment environment schema before you paste it. Only `arc_machine_names` is needed by the cluster deployment inputs.

## Before you start OS configuration, then Validate

| Check | Why |
|-------|-----|
| Active Directory is prepared | Learn lists it as an on-site prerequisite. The automation doesn't do it. |
| The Arc machine names in your cluster inputs are the ones in the handoff | See the caution above. |
| OS configuration has run and every machine matches the file | Learn says [inbox drivers aren't supported](https://learn.microsoft.com/en-us/azure/azure-local/concepts/host-network-requirements?view=azloc-2610#driver-requirements), and validation fails with more than one physical adapter that has a default gateway. A ZTP-built machine has inbox drivers, DHCP and often a gateway on more than one port, and no static address in Modes B and C. [OS configuration](../../../phase-03-os-configuration/automated-os-configuration.mdx) fixes all of it. |
| The iDRAC USB link adapter is not in any network intent | It appears as a network adapter (Remote NDIS, `169.254.0.x`). It isn't a cluster port. |
| `C:\SBE` holds the SBE files | OS configuration delivers them (`hardware.sbe.delivery`) and checks the hashes. ZTP leaves the folder empty. |

---

## Validation

- [ ] The run printed that ZTP is done, and every machine has a result in the per-node table
- [ ] The handoff file lists every machine with an `arcMachineResourceId`
- [ ] The Arc machine names are not the node names, and your cluster inputs use the handoff values
- [ ] Every machine shows **Ready to cluster** and **Connected** in the portal
- [ ] `managementAddressVerified` is true for Mode A machines; for Modes B and C the reason says OS configuration sets the address
