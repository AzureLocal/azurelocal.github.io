> **MASTER REFERENCE**: [azurelocal-ztp repository](https://github.com/AzureLocal/azurelocal-ztp)

**Status**: Active

:::warning Execute reinstalls the machines
Without `-Execute` the run is a plan and changes nothing. With `-Execute` it **reinstalls the named machines**. Run the plan first, confirm the machine list, and confirm that none of the machines holds a cluster or data you need.
:::

## Overview

You run one command, `Invoke-ZtpEnvironment.ps1`, with the environment file. It does the whole flow from the [overview](./index.mdx): Resolve, Media, Boot, Bootstrap, Vouchers, Azure, Ready, Handoff, and Prepare. This page shows how to run it from a Windows management host. To run it from a pipeline, see [Run from a pipeline](./run-from-pipeline.mdx).

The script is in the `scripts/simplified-provisioning` folder of the [azurelocal-ztp repository](https://github.com/AzureLocal/azurelocal-ztp).

## Step-by-Step

### Step 1: Get the scripts

Clone the repository onto the management host and open an **elevated** PowerShell 7 session in it.

```powershell
git clone https://github.com/AzureLocal/azurelocal-ztp.git
Set-Location .\azurelocal-ztp
```

The run writes its working files, such as downloaded ISOs, images, vouchers and state, to a `_media` folder at the root of the clone. Git ignores that folder. Keep the clone in a place that lasts, because resume depends on what is in `_media`.

### Step 2: Sign in to Azure

Sign in as an identity that holds the required roles. The script uses the current Az sign-in.

```powershell
Connect-AzAccount -Tenant <tenant-id>
```

If the host has a managed identity attached, you can pass `-UseManagedIdentity` instead, and the script signs in as that identity.

### Step 3: Run the plan

Without `-Execute`, the script validates the environment file, writes the generated settings, and shows the plan for the stages. It changes nothing in Azure or on a machine.

```powershell
.\scripts\simplified-provisioning\Invoke-ZtpEnvironment.ps1 `
  -InfrastructureFile .\infrastructure.yml
```

Read the output. Check:

- the share host address is the address the BMCs reach,
- the machine list is the one you expect, and
- the plan lists the stages and the commands each would run.

### Step 4: Run it

Add `-Execute`.

```powershell
.\scripts\simplified-provisioning\Invoke-ZtpEnvironment.ps1 `
  -InfrastructureFile .\infrastructure.yml `
  -Execute
```

The script then:

1. Reads the BMC account from Key Vault.
2. Creates the resource group if it doesn't exist.
3. Runs Resolve to Handoff. A failed OS install is resubmitted once automatically.
4. Runs the Prepare stage on every machine in parallel.

Keep the session open. The run takes about 1.5 to 2 hours on the proven setup. Don't close the window or let the host sleep.

To provision only some machines, name them. The names are those in `cluster_nodes[].name`.

```powershell
.\scripts\simplified-provisioning\Invoke-ZtpEnvironment.ps1 `
  -InfrastructureFile .\infrastructure.yml `
  -Node node-02 `
  -Execute
```

### Step 5: Watch the run

The orchestrator writes structured events to a JSON-lines file, `ztp-events.jsonl`, in the `ztp-state` folder under `_media`. Follow it live and read-only with [azurelocal-sonar](https://azurelocal.cloud/azurelocal-sonar/): start it in a second window with the repository's `Start-ZtpMonitor.ps1`. [Monitor with Sonar](./monitor-with-sonar.mdx) has the steps, what the page shows and what's normal.

To read the event file without Sonar:

```powershell
Get-Content -Wait -Tail 20 .\_media\ztp-state\ztp-events.jsonl
```

In the Azure portal, **Azure Arc** > **Operations** > **Provisioning (preview)** > **Provisioned machines** shows each machine's status as Azure sees it.

### Step 6: Resume after a stop

If a gate fails or times out, the run stops with the reason. Fix the cause and run the same command again. The orchestrator records completed stages in a state file and skips them.

To force a restart from a stage, add `-From` with the stage name:

```powershell
.\scripts\simplified-provisioning\Invoke-ZtpEnvironment.ps1 `
  -InfrastructureFile .\infrastructure.yml `
  -From Azure `
  -Execute
```

`-From` takes `Resolve`, `Media`, `Boot`, `Bootstrap`, `Vouchers`, `Azure`, `Ready`, `Handoff` or `Prepare`. The named stage and every later stage run again.

| Where it stopped | Resume with |
|------------------|-------------|
| Before the Boot stage | The same command, or `-From Resolve` or `-From Media`. |
| After Boot, before the claim | `-From Bootstrap`, `-From Vouchers` or `-From Azure`. Don't use `-From Resolve` or `-From Media`, because they rebuild the images that now hold the vouchers. |
| After the claim | `-From Ready`. |
| Prepare failed on one machine | `-From Prepare` with `-Node` naming that machine. Prepare skips steps that are already done. |

Each set of machines keeps its own state, named after the machines. Running machine `node-02` on its own doesn't disturb the state of a run for the others.

## Timeouts

`Invoke-ZtpEnvironment.ps1` sets these waiting budgets in the settings it generates. They are in the script, not in the environment file.

| Wait | Budget |
|------|--------|
| Bootstrap, overall | 120 minutes |
| Bootstrap, until a valid voucher appears | 90 minutes |
| Vouchers | 120 minutes |
| Ready to cluster | 180 minutes |
| Prepare, Azure Ready gate | 240 minutes |
| Prepare, sign-in and restart gates | 30 minutes |

## Troubleshooting

See [Troubleshooting and known issues](../troubleshooting.mdx). The ones you are most likely to meet are the first OS install attempt failing with 5901, and a machine that takes up to about 45 minutes to register after the claim. Both recovered on their own on the proven runs.
