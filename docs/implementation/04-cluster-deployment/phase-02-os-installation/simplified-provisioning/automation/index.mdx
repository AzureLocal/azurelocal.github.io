## Overview

The [portal route](../index.mdx) of simplified machine provisioning needs a person in the rack for the USB boot, then a person in the Azure portal to upload vouchers. The [azurelocal-ztp](https://github.com/AzureLocal/azurelocal-ztp) scripts replace both with automation. Given one environment file (the master `infrastructure.yml`), they:

1. Build one virtual USB image per machine from Microsoft's maintenance environment.
2. Attach each image through the machine's BMC (Redfish), boot the machine once from it, and collect the ownership voucher it writes.
3. Set each static management address in the maintenance environment before the claim (Modes B and C), then claim the machines in Azure with the vouchers, so Azure installs the OS and registers each machine with Azure Arc.
4. Verify each management address through Azure, and put back any BIOS setting that was changed for the install only.

The run ends at the **Handoff**: every machine is Provisioned, Arc-connected and ready to cluster again, and one handoff file records what Azure generated. OS configuration is a separate step that follows; see [Where ZTP ends](#where-ztp-ends). The azurelocal-ztp repository holds the scripts, the full parameter reference and example pipelines. This section explains the design and how to run it. It does not copy the scripts.

:::info Virtual USB image, not virtual media ISO
Other pages on this site describe azurelocal-ztp as mounting the maintenance ISO as BMC virtual media. The current automation builds a **raw virtual USB image** per machine and attaches it to the BMC's USB-stick slot. The maintenance environment writes the ownership voucher back to the media it booted from, and the automation reads the voucher from that image.
:::

## When to use this route

| Choose | When |
|--------|------|
| **Automated route** (this section) | The machines' BMCs are reachable from a Windows management host, you want a repeatable run with evidence at each step, or you provision many machines or sites. |
| **Portal route** ([Tasks 1 to 5](../index.mdx#steps-in-this-section)) | Someone is on site with USB media, the BMC is not reachable from a management host, or you want to follow Microsoft's documented steps exactly. |
| **ISO route** ([Phase 02](../../index.mdx)) | You need a generally available method, Arc gateway, or hardware that simplified provisioning doesn't cover. |

## Stages and gates

You start the whole run with `Invoke-ZtpEnvironment.ps1`. It validates the environment file, writes the settings that the stage scripts need, and calls `Invoke-ZtpProvisioning.ps1`, which runs the eleven stages from Resolve to Handoff.

Each stage runs only after the previous stage's gate passes. A gate that fails or times out stops the run with the reason.

| Stage | What it does | Gate or evidence |
|-------|--------------|------------------|
| **Resolve** | Finds, downloads and hash-verifies the maintenance ISO for the train you pin. ZTP resolves no SBE: the SBE belongs to OS configuration. | ISO SHA-256. |
| **Media** | Builds one raw virtual USB image per machine from the ISO. Optionally sets a password for the maintenance environment's `edgeuser` account (only its hash enters the image). | One image per machine. |
| **Boot** | Sets each machine's BIOS from `hardware.bios` with `bios_during_provisioning` merged over it (the temporary values win; for example a Fibre Channel card slot Disabled), and saves the original value of each changed setting. Shares the images over SMB (read-write, inbound TCP 445 allowed only from the BMC addresses, through a dedicated local account), closes stale SMB handles, inserts each image into the BMC's USB-stick slot, sets a one-time boot, and resets the machine. **All machines run in parallel**, one worker each. | The BMC reports the one-time boot override (`Once`, `Floppy`) before the reset. The iDRAC log is watched for 10 minutes for event `OSE1002`, logged as "C: boot completed", which the automation reads as the installed OS booting. |
| **Bootstrap** | Waits for the maintenance environment to run and to write the voucher back into each image. | A voucher per machine. |
| **Vouchers** | Reads each voucher from the image, checks it matches the machine serial, replaces a spent local copy, ejects the media, and removes the share. | A valid voucher per serial. |
| **Device** | Modes B and C only. In the maintenance environment, before the claim: finds each machine (a scan of the provisioning DHCP range on TCP 20001, matched by its management MAC), sets the static management address, mask, gateway, DNS and VLAN on that port through the maintenance environment's Configurator service, and reads it back. | The static configuration is on the management adapter, in the maintenance environment. |
| **Azure** | Prerequisite gate, Bicep validate, plan, and claim. With `static_method: device` (the default) the site's network setting is Automatic and the claim carries no Manual adapter. | Deployment accepted. |
| **Ready** | Waits for "Ready to cluster" on every machine. Resubmits a failed `ProvisionOs` job once, by sending the PUT for `jobs/ProvisionOs` again. | Provisioned, job succeeded, Arc Connected, extensions done. |
| **Network** | **Verify-only.** Reads each machine's per-NIC report from Azure, finds the management port by its MAC and compares it with the file, by mode (see [Management address modes](#management-address-modes)). It sends and waits on no Azure job. | Every machine has a result. Only a management MAC that no adapter reports stops the stage. |
| **Restore** | Sets each `bios_during_provisioning` setting back to its final `hardware.bios` value (or the saved original), restarts the machine through Redfish, waits until the BIOS reports the values, then waits until Arc is Connected and the machine is ready to cluster again. Does nothing without `bios_during_provisioning`. | Each restarted machine is Connected and ready to cluster. |
| **Handoff** | Writes the handoff file (schema 2) and the cluster inputs. | Files written. |

The **Azure** stage prerequisite gate checks that:

- the maintenance environment is running on every machine,
- the `Microsoft.DeviceOnboarding/AzureLocalZTP` feature and the resource providers are registered, and
- the operator holds Contributor and Role Based Access Control Administrator on the resource group.

The plan refuses to submit if a voucher is missing or invalid.

:::info Why the OS install is resubmitted automatically
Learn states that simplified machine provisioning doesn't retry a failed OS installation from the service, and it gives a manual resubmit procedure. The **Ready** stage does that resubmit once, automatically. See [Troubleshooting and known issues](../troubleshooting.mdx#first-os-install-attempt-fails-with-5901).
:::

### Management address modes

The mode is set in the master file (`ip_assignment` on the management port, with `static_method`). It decides what is on the management port when ZTP ends.

| Mode | Management port during provisioning | After the OS install | What Network does | What OS configuration does |
|------|-------------------------------------|----------------------|-------------------|----------------------------|
| **A, Reserved** (recommended) | DHCP; the DHCP server reserves the node's address for the management MAC | The reserved address | Verifies it | Leaves it and verifies it |
| **B, Static with DHCP** | The Device stage sets the static; the maintenance environment also takes DHCP | The OS install resets the port to DHCP | Records the node as deferred to OS configuration | Sets the static by MAC |
| **C, Static without management DHCP** | The Device stage sets the static; Arc is reached over the provisioning port | No address on the management port | Records the node as deferred to OS configuration | Sets the static by MAC, before any other port loses DHCP |

Use Mode A when you can. It is the only mode where ZTP ends with every management address right. Microsoft's OS install resets every port, and Microsoft's post-install per-NIC job did not start on the live runs, so ZTP no longer tries to set an address after the install.

### BIOS isolation during the install

Some hardware must look different during the install than in production. An Emulex Fibre Channel card, for example, can present a SAN LUN that the OS install picks as its target. Put the final value under `hardware.bios` and the install-only value under `hardware.bios_during_provisioning`. Boot applies the temporary values before the maintenance boot and saves each original value. Restore sets them back after Network, restarts the machine, and waits until Arc is Connected again.

### Where ZTP ends

ZTP ends at the Handoff. The machines are Provisioned and Arc-connected with their BIOS on its final settings, and they are **not yet ready for Validate**. OS configuration comes next: the OEM's network drivers and the SBE in `C:\SBE`, DHCP and extra default gateways off on the other ports, the static management address in Modes B and C, DNS, time, the host name and the deployment administrator. The toolkit does that, in [Phase 03: OS configuration](../../../phase-03-os-configuration/index.mdx), preferably with the [automated run](../../../phase-03-os-configuration/automated-os-configuration.mdx).

:::note The iDRAC USB link is not a cluster port
The iDRAC presents a USB link to the operating system (Remote NDIS, `169.254.0.x`) as a network adapter. It has no gateway, is not a cluster port, and must stay out of your network intents.
:::

## What runs where

| Where | What runs there |
|-------|-----------------|
| **Management host (Windows)** | The environment file check, Resolve, Media, the SMB share, the BMC calls (Redfish over HTTPS), voucher read-back, the Device calls to the maintenance environment, the Azure calls, the handoff. |
| **BMC** | Attaches the image, applies the one-time boot, and resets the machine. The iDRAC's SMB client connects out to the management host on TCP 445 to read and write the image. No inbound port is needed on the BMC. |
| **Machine** | Boots the maintenance environment, writes the voucher, then calls home to Azure. Its maintenance environment takes the static management address (Modes B and C), then Azure installs the OS onto it. ZTP opens no connection to the installed OS. |
| **Azure** | Holds the site, the site configuration, the role assignments and the machine claim. Runs the OS install job and Arc registration. |

The management host must be Windows. The Boot stage shares the images over SMB with Windows commands. See [Prerequisites](./prerequisites.mdx).

## Parallel machines

- **Boot** uses one worker per machine, so all machines boot at the same time.
- **Resolve, Azure and Handoff** run once for the whole set of machines.
- **Device, Network and Restore** work through every machine in the set.

A full run took about 1.5 to 2 hours on the proven setup (two machines).

You can name a subset with `-Node`. Each set of machines keeps its own state file, so proving one machine never disturbs another's run.

---

## Plan by default

Without `-Execute`, `Invoke-ZtpEnvironment.ps1` writes the generated files and shows the plan. Nothing changes in Azure or on a machine. Run the plan first and read it.

With `-Execute`, the run **reinstalls the named machines**. The Boot stage needs a confirmation that the machines carry no cluster to keep, and `Invoke-ZtpEnvironment.ps1` supplies it for you when you pass `-Execute`. Don't run it against machines that hold data you need.

---

## Resume

The orchestrator records each completed stage in a state file. If a run stops, fix the cause and run the same command again. Completed stages aren't repeated.

To force a restart from a stage, pass `-From <Stage>`. That stage and every later stage run again, whatever the state file says. The valid stage names are `Resolve`, `Media`, `Boot`, `Bootstrap`, `Vouchers`, `Device`, `Azure`, `Ready`, `Network`, `Restore` and `Handoff`.

:::caution Don't rebuild media after Boot
After the Boot stage, each image holds that machine's voucher. A run that starts from `Resolve` or `Media` rebuilds the images, so once vouchers exist use `-From Device`, `-From Azure`, `-From Ready` or a later stage.
:::

## Security

:::caution Read before the first run
- **Change the iDRAC factory password** on every BMC before you automate it, and keep the BMC credential in Key Vault only.
- **Treat vouchers as secrets.** A voucher proves ownership of a machine. Restrict the folder that holds them and delete them when provisioning is done.
- **The read-write SMB share is a tampering risk while it is up.** The BMC can write to it, and so can anyone who reaches it. The automation limits inbound TCP 445 to the BMC addresses with a firewall rule it creates, uses a dedicated local account, and removes the share after the Vouchers stage. Keep the management host on an isolated network, and consider requiring SMB signing.
- **Match firmware to the OEM's Azure Local support matrix** before you start. Only iDRAC 7.30 was proven.
- **After a failed Boot stage**, check on each BMC that the media is ejected and the one-time boot is cleared before you retry.
:::
