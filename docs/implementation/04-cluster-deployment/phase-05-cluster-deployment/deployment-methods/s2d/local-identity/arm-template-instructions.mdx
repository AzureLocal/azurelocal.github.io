## Overview

This guide walks through deploying an Azure Local cluster with **local identity** authentication using ARM templates. It is structured as a sequential runbook — complete each task in order from start to finish.

Local identity authentication uses Azure Key Vault for credential management instead of Active Directory, making it ideal for:

- Edge deployments without AD connectivity
- Proof-of-concept and lab environments
- Simplified deployments requiring AD independence
- Multi-site deployments with consistent IaC workflows

:::warning Local identity uses a different template than Active Directory
Per Microsoft Learn (2610), local identity with Azure Key Vault is deployed with the quickstart template `azurestackhci/create-adless-cluster-external-dns-public-preview`, **not** `create-cluster`. Its parameter set differs from the Active Directory template:

- `identityProvider` is set to `LocalIdentity`.
- `dnsServerConfig` is set to `UseDnsServer` for the external DNS template, and `dnsZones` carries the DNS zone configuration (see the [dnsZones example](#dnszones-example)).
- The Learn parameter reference for this template has **no** `domainFqdn`, `adouPath`, `AzureStackLCMAdminUsername` or `AzureStackLCMAdminPassword` parameters. Do not pass them.

Authentication uses the local administrator account (not the built-in `Administrator`), with secrets stored in Azure Key Vault.
:::

:::info Template name, API version and parameter count
The template folder name ends in `public-preview` on Microsoft Learn 2610, and Learn does not state an API version or a total parameter count for it. This runbook therefore does not quote either. Treat the exact `apiVersion` and parameter count as **lab-verified only**: diff your parameter file against the current `azuredeploy.parameters.json` in the quickstart template before each deployment. Learn also notes that every parameter must be filled in, including array placeholders such as `[""]`, or validation fails.
:::

The Azure Local Cloud toolkit provides parameter template files and a generation script that populate the parameter file from `infrastructure.yml`. Confirm that the generator's `-AuthType LocalIdentity` output matches the parameter set above (it must emit `identityProvider`, `dnsServerConfig` and `dnsZones`, and must not emit the Active Directory or LCM parameters) before you use it. See the [Reference](#reference) section for the parameter reference.

## Before You Begin

### Prerequisites

| Requirement | Description | Validation |
|-------------|-------------|------------|
| Azure CLI or PowerShell | Az module installed | `Get-Module -Name Az` |
| Subscription access | User Access Administrator and Contributor on the subscription (Learn deployment checklist) | Verify in IAM |
| Resource group roles | On the Arc resource group: Azure Stack HCI Administrator, Reader, Key Vault Data Access Administrator, Key Vault Secrets Officer, Key Vault Contributor, Storage Account Contributor, plus Azure Connected Machine Onboarding and Azure Connected Machine Resource Administrator | Verify in IAM |
| Resource group | Created for cluster deployment | `Get-AzResourceGroup` |
| Platform Key Vault | Stores the local administrator password used for Key Vault references | Secret populated in prior phases |
| Arc-registered nodes | All nodes registered in Azure Arc | Verify in Azure Portal |
| Identical local credentials | Same admin password on all nodes | Verify login via WinRM |

### What You Need Ready

Before starting the deployment procedure, confirm each item:

1. **`infrastructure.yml` fully populated** — all 13 sections complete, including `cluster_arm_deployment`, `accounts`, `network_intents`, and `compute.cluster_nodes`
2. **Authenticated to Azure** — run `Connect-AzAccount` (PowerShell) or `az login` (CLI) on the machine where you will execute commands
3. **`powershell-yaml` module installed** — required by the generation script: `Install-Module powershell-yaml -Scope CurrentUser`
4. **Arc nodes registered** — Phase 04 complete; `arc_node_resource_ids` populated in `infrastructure.yml`
5. **Platform Key Vault secret stored** — the `local-admin-password` secret exists in the platform Key Vault (from prior phases). Local identity has no LCM deployment account, so no `lcm-deployment-password` secret is needed for this template
6. **Nodes in a workgroup** — local identity deployments do not use Active Directory: Learn tells you to skip the AD prerequisites and verifies after deployment that the nodes report `WORKGROUP`. Do not domain join the nodes (the domain-join-before-deployment option in Learn is described for Active Directory deployments). Each node has the same custom local administrator account (not the built-in `Administrator`), static IP addressing (DHCP is not supported for local identity nodes) and SSH enabled, per Microsoft Learn

:::info Where to Run From
All commands in this runbook run from the **azurelocal-toolkit repository root** on a management/jump box authenticated to Azure. The toolkit scripts expect `infrastructure.yml` at `infrastructure.yml` relative to the repo root.
:::

:::info Key Vault Architecture
Two Key Vaults are involved in Azure Local deployment:

- **Platform Key Vault** — Already exists from prior phases. Stores the local administrator password. Referenced in the parameter file via a Key Vault reference. **No action needed here.**
- **Cluster Key Vault** — Created automatically by the ARM template when `createNewKeyVault` is `true`. The name (`keyVaultName`) and other settings are already defined in `infrastructure.yml`.
:::

### Task 1: Get HCI Resource Provider Object ID

The `hciResourceProviderObjectID` parameter requires the tenant-specific Object ID of the `Microsoft.AzureStackHCI` resource provider service principal. This GUID is unique per Entra ID tenant and must be looked up once, then stored in `infrastructure.yml` at `azure.hci_resource_provider_object_id`.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Manual" default>

**When to use**: Quick one-time lookup without running a script.

```powershell title="Look up the Object ID via Azure PowerShell"
(Get-AzADServicePrincipal -ApplicationId "1412d89f-b8a8-4111-b4fd-e82905cbd85d").Id
```

```bash title="Azure CLI alternative"
az ad sp list --filter "appId eq '1412d89f-b8a8-4111-b4fd-e82905cbd85d'" --query "[0].id" -o tsv
```

The application ID `1412d89f-b8a8-4111-b4fd-e82905cbd85d` is the Azure Local resource provider application ID published on Microsoft Learn. Looking it up by application ID is the documented method.

**Expected output**: A single GUID, e.g. `ab12cd34-ef56-7890-ab12-cd34ef567890`

**Next**: Open `infrastructure.yml`, find `azure.hci_resource_provider_object_id`, and paste the GUID as the value.

### Task 2: Generate Parameter File

Create the deployment-ready JSON parameter file for the `create-adless-cluster-external-dns-public-preview` template. This step produces the file used by Tasks 3 and 4. Start from the example [azuredeploy.parameters.json](https://github.com/Azure/azure-quickstart-templates/blob/master/quickstarts/microsoft.azurestackhci/create-adless-cluster-external-dns-public-preview/azuredeploy.parameters.json) that Microsoft Learn links for this template.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Manual" default>

**When to use**: You want to build the parameter file by hand or use a pre-built example as a starting point.

1. Copy the template: `configs/azure/arm-templates/04-cluster-deployment/azuredeploy.parameters.local-identity.json`
2. Replace all `{{VARIABLE}}` placeholders with values from your `infrastructure.yml`

**Key placeholders to replace** (most common errors come from these):

| Placeholder | YAML Source Path | Description |
|-------------|-----------------|-------------|
| `{{CLUSTER_NAME}}` | `cluster.name` | Cluster resource name |
| `{{RESOURCE_GROUP}}` | `azure.resource_group` | Target resource group |
| `{{LOCATION}}` | `azure.location` | Azure region |
| `{{KEY_VAULT_NAME}}` | `cluster.key_vault.name` | Cluster KV (created by ARM) |
| `{{DIAGNOSTIC_STORAGE}}` | `cluster.diagnostics.storage_account` | KV diagnostics storage |
| `{{WITNESS_STORAGE}}` | `cluster.witness.storage_account` | Cloud witness storage |
| `{{LOCAL_ADMIN_USER}}` | `identity.local_admin.username` | Local admin on all nodes |
| `{{HCI_RP_OBJECT_ID}}` | `azure.hci_resource_provider_object_id` | From Task 1 |
| `{{NAMING_PREFIX}}` | `cluster.naming_prefix` | Resource prefix |

For Local Identity, **omit** `domainFqdn`, `adouPath`, `AzureStackLCMAdminUsername` and `AzureStackLCMAdminPassword`: they are not parameters of the local identity template. Instead set:

| Parameter | Value |
|-----------|-------|
| `identityProvider` | `LocalIdentity` |
| `dnsServerConfig` | `UseDnsServer` (for the external DNS template) |
| `dnsZones` | One entry per zone, for example `dnsZoneName` and `dnsForwarder` (see the [dnsZones example](#dnszones-example)) |
| `dnsServers` | The DNS server IPs that host the zone |

For `localAdminPassword`, use a Key Vault reference (not plain text):

```json title="Key Vault reference format (points to platform Key Vault)"
"localAdminPassword": {
 "reference": {
 "keyVault": {
 "id": "/subscriptions/<SUB_ID>/resourceGroups/<RG>/providers/Microsoft.KeyVault/vaults/<PLATFORM_KV_NAME>"
 },
 "secretName": "local-admin-password"
 }
}
```

3. Verify all `{{` placeholders are replaced: search the file for `{{` — there should be zero matches
4. Save as `azuredeploy.parameters.local-identity.json` in your working directory

:::tip Use an Example as Reference
Validated IIC examples exist for each networking pattern in `config/azure/arm-templates/examples/`. Compare your file against the matching pattern — see the **Example Parameter Files** collapsible in the [Reference](#reference) section below.
:::

### Task 3: Validate Deployment

Run the ARM template in **Validate** mode first. Validation executes the full deployment pipeline — environment checks, connectivity tests, credential validation — but stops before provisioning. Fix all errors before proceeding to Deploy.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Manual" default>

**When to use**: You built the parameter file manually in Task 2 and want to run validation directly.

```powershell title="Define deployment variables"
# Values from infrastructure.yml
$subscriptionId = "<SUB_ID>" # azure.subscription_id
$resourceGroup = "<RESOURCE_GROUP>" # azure.resource_group
$parametersFile = ".\azuredeploy.parameters.local-identity.json" # File from Task 2
$templateUri = "https://raw.githubusercontent.com/Azure/azure-quickstart-templates/master/quickstarts/microsoft.azurestackhci/create-adless-cluster-external-dns-public-preview/azuredeploy.json"

# Set subscription context
Set-AzContext -SubscriptionId $subscriptionId
```

```powershell title="Ensure deploymentMode is set to Validate"
# Check current mode in the parameters file
$json = Get-Content $parametersFile | ConvertFrom-Json
$currentMode = $json.parameters.deploymentMode.value
Write-Host "Current deploymentMode: $currentMode"

# If not "Validate", update it:
if ($currentMode -ne "Validate") {
 $json.parameters.deploymentMode.value = "Validate"
 $json | ConvertTo-Json -Depth 20 | Set-Content $parametersFile
 Write-Host "Updated deploymentMode to Validate" -ForegroundColor Yellow
}
```

```powershell title="Run validation"
$validateResult = New-AzResourceGroupDeployment `
 -Name "azl-validate-$(Get-Date -Format 'yyyyMMddHHmmss')" `
 -ResourceGroupName $resourceGroup `
 -TemplateUri $templateUri `
 -TemplateParameterFile $parametersFile `
 -Verbose

$validateResult | Select-Object DeploymentName, ProvisioningState, Timestamp
```

**Expected output** for a successful validation:
```
DeploymentName ProvisioningState Timestamp
-------------- ----------------- ---------
azl-validate-20260309142055 Succeeded 3/9/2026 2:45:30 PM
```

If validation fails, check the error output against the [Troubleshooting](#troubleshooting) table.

</TabItem>

### Task 4: Deploy Cluster

After validation passes, switch to **Deploy** mode and run the deployment. This provisions the cluster — the process takes 1.5–3 hours depending on node count.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Manual" default>

**When to use**: You ran validation manually in Task 3 and want to continue with direct commands.

```powershell title="Step 1 — Switch deploymentMode to Deploy"
$parametersFile = ".\azuredeploy.parameters.local-identity.json"

$json = Get-Content $parametersFile | ConvertFrom-Json
$json.parameters.deploymentMode.value = "Deploy"
$json | ConvertTo-Json -Depth 20 | Set-Content $parametersFile
Write-Host "Updated deploymentMode to Deploy" -ForegroundColor Green
```

```powershell title="Step 2 — Run deployment"
$templateUri = "https://raw.githubusercontent.com/Azure/azure-quickstart-templates/master/quickstarts/microsoft.azurestackhci/create-adless-cluster-external-dns-public-preview/azuredeploy.json"
$resourceGroup = "<RESOURCE_GROUP>" # azure.resource_group
$deploymentName = "azl-deploy-$(Get-Date -Format 'yyyyMMddHHmmss')"

$deployment = New-AzResourceGroupDeployment `
 -Name $deploymentName `
 -ResourceGroupName $resourceGroup `
 -TemplateUri $templateUri `
 -TemplateParameterFile $parametersFile `
 -Verbose

$deployment | Select-Object DeploymentName, ProvisioningState, Timestamp
```

## Troubleshooting

| Issue | Cause | Resolution |
|-------|-------|------------|
| Key Vault access denied | Missing RBAC on platform KV | Grant `Key Vault Secrets User` to deployment identity on the **platform** Key Vault |
| Credential mismatch | Different local passwords across nodes | Reset to identical password on all nodes |
| Validation fails on `hciResourceProviderObjectID` | Wrong Object ID | Re-run `Get-AzADServicePrincipal` (Task 1) |
| `networkingPattern` error | Intent layout doesn't match pattern | Verify intent count and traffic types match pattern |
| Deployment timeout | Network or Azure service issue | Check node Azure endpoint connectivity |
| Arc extension failed | Node not reachable from Azure | Verify WinRM/HTTPS and Arc agent status |
| `deploymentMode` stuck on `Validate` | Forgot to switch mode | Re-run the script with `-DeploymentMode Deploy` or edit the JSON |
| Parameter file has `{{` placeholders | Incomplete placeholder replacement | Search file for `{{` and replace all remaining |
| `domainFqdn`, `adouPath` or LCM parameters in the parameter file | Active Directory parameter file or wrong template used | Use the `create-adless-cluster-external-dns-public-preview` template and remove those parameters; set `identityProvider` to `LocalIdentity` |
| `dnsZones` or `dnsServerConfig` validation error | Missing or placeholder values | Provide `dnsServerConfig = UseDnsServer` and a real `dnsZones` array (`dnsZoneName`, `dnsForwarder`) |

### Network intent adapter property overrides

The `intentList` entries accept optional override blocks. Microsoft's `Microsoft.AzureStackHCI/clusters/deploymentSettings` reference describes the adapter overrides `jumboPacket`, `networkDirect` and `networkDirectTechnology` (expected technologies `iWARP`, `RoCEv2`, `RoCE`) and states for each: "This parameter should only be modified based on your OEM guidance. Do not modify this parameter without OEM validation." Leave the override flags `false` unless the hardware vendor tells you otherwise.

```json title="intentList entry shape (illustrative values; confirm against the template and OEM guidance)"
{
  "name": "Storage",
  "trafficType": ["Storage"],
  "adapter": ["SMB1", "SMB2"],
  "overrideVirtualSwitchConfiguration": false,
  "virtualSwitchConfigurationOverrides": {},
  "overrideQosPolicy": false,
  "qosPolicyOverrides": {},
  "overrideAdapterProperty": true,
  "adapterPropertyOverrides": {
    "jumboPacket": "9014",
    "networkDirect": "Enabled",
    "networkDirectTechnology": "RoCEv2"
  }
}
```

The portal equivalents (**Customize network settings**) are storage traffic priority, system traffic priority (5, 6 or 7), storage bandwidth reservation, jumbo frame size (1514, 4088 or 9014) and the RDMA protocol (iWARP, RoCE, RoCEv2 or disabled). Microsoft Learn does not publish per-intent defaults. The Azure Local Cloud design intent of "storage intent: RDMA on and jumbo frames; management and compute intents: RDMA off, jumbo at the default" is **owner policy, lab-verified only**: confirm it after deployment with `Get-NetIntent`, `Get-NetAdapterAdvancedProperty -RegistryKeyword *JumboPacket` and `Get-NetAdapterRdma`. Guest RDMA is not supported on Azure Local.

#### networkingPattern Values

:::note Only `hyperConverged` is shown by Microsoft Learn
Learn gives `hyperConverged` as the example value for `networkingPattern`. | Pattern | Intents | Description | Use Case |

<details>
<summary><strong>Key Vault Reference Syntax</strong></summary>

The sensitive parameter `localAdminPassword` uses a Key Vault reference that point to the **platform Key Vault** — the vault provisioned in prior phases where deployment credentials are already stored:

```json title="Key Vault reference pointing to platform Key Vault"
"localAdminPassword": {
 "reference": {
 "keyVault": {
 "id": "/subscriptions/<SUB_ID>/resourceGroups/<RG>/providers/Microsoft.KeyVault/vaults/<PLATFORM_KV_NAME>"
 },
 "secretName": "local-admin-password"
 }
}
```

This is **not** the cluster Key Vault (`keyVaultName`) — that vault is created by the ARM template during deployment.

:::danger Never Store Passwords in Plain Text
Always use Key Vault references to the platform Key Vault for sensitive parameters.
:::
