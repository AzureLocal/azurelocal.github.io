## Overview

Local Identity deployment enables Azure Local clusters without Active Directory dependency. Authentication is managed through local Windows accounts on each node, with credentials stored securely in Azure Key Vault.

:::info Use Cases for Local Identity
- Edge locations without AD connectivity
- Proof-of-concept deployments
- Simplified lab environments
- Scenarios requiring AD independence
- Remote/disconnected site deployments
:::

:::warning Windows Admin Center Not Supported
Windows Admin Center (WAC) is **not supported** with Local Identity deployments. Use PowerShell or the Azure portal for administrative tasks.

**Source**: [MS Learn — Local Identity with Key Vault](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deployment-local-identity-with-key-vault?view=azloc-2610)
:::

### Node Requirements

| Requirement | Description | Validation |
|-------------|-------------|------------|
| Local Admin | **Identical credentials on ALL nodes** | Verify login works |
| Windows Server | Azure Stack HCI OS installed | `winver` |
| Network | All nodes can communicate | `Test-NetConnection` |
| WinRM | Remote management enabled | `Test-WSMan` |

:::warning Critical Requirement
The local administrator password **MUST be identical** across all cluster nodes. Different passwords will cause deployment failure.
:::

## Pre-Deployment: Create Local Accounts

Microsoft requires a **non-built-in** local administrator account with identical credentials on every cluster node before portal deployment begins.

:::danger Do NOT use the built-in Administrator account
Microsoft explicitly states: do not use the built-in `Administrator` account for Local Identity deployments. Create a separate, non-default local account. The account name is configured at `identity.local_admin.username` in `infrastructure.yml`.

**Source**: [MS Learn — Local Identity with Key Vault](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deployment-local-identity-with-key-vault?view=azloc-2610)
:::

<Tabs groupId="deployment-method">
<TabItem value="manual" label="On Each Node (GUI)" default>

On each cluster node (via RDP or console), use **Computer Management** (`compmgmt.msc`) to create the local account:

1. Open **Computer Management** → **Local Users and Groups** → **Users**
2. Right-click **Users** → **New User**
3. Set **User name** to the value from `identity.local_admin.username`
4. Set **Password** — minimum 14 characters, **identical on ALL nodes**
5. Uncheck **User must change password at next logon**
6. Check **Password never expires** and **Account never expires**
7. Click **Create**, then **Close**
8. Right-click the new user → **Properties** → **Member Of** tab → **Add** → type `Administrators` → **OK**

Repeat on every cluster node. Verify by signing in locally with the new account credentials on each node before proceeding.

:::warning
Do NOT set the same password as the built-in `Administrator` account, and do NOT use `Administrator` as the username. Use a unique, non-default account name.
:::

</TabItem>
<TabItem value="direct" label="Direct Script (On Node)">

Run this script directly on each node via RDP or console session. All variables are defined inline — no `infrastructure.yml` or toolkit access required on the node.

**Script:** `scripts/deploy/04-cluster-deployment/phase-05-cluster-deployment/local-identity/task-01-initiate-deployment-via-azure-portal/powershell/Deploy-CreateLocalAdmin.ps1`

```powershell title="Deploy-CreateLocalAdmin.ps1 — run on each node directly"
#region CONFIGURATION
$Username = "REPLACE_LOCAL_ADMIN_USERNAME" # identity.accounts.account_local_admin_username — must be identical on all nodes
$Password = "REPLACE_LOCAL_ADMIN_PASSWORD" # identity.accounts.account_local_admin_password — minimum 14 characters
#endregion CONFIGURATION

if ($Username -match '^REPLACE_') { throw 'Edit the REPLACE_ variables in #region CONFIGURATION before running.' }
if ($Username -ieq 'Administrator') { throw 'Do not use the built-in Administrator account. Use a custom non-default account name.' }
if ($Password.Length -lt 14) { throw "Password must be at least 14 characters. Current length: $($Password.Length)" }

$secPwd = ConvertTo-SecureString $Password -AsPlainText -Force
$existing = Get-LocalUser -Name $Username -ErrorAction SilentlyContinue

if (-not $existing) {
 New-LocalUser -Name $Username -Password $secPwd -PasswordNeverExpires -AccountNeverExpires
 Write-Host "[PASS] Account '$Username' created on $env:COMPUTERNAME" -ForegroundColor Green
} else {
 Set-LocalUser -Name $Username -Password $secPwd
 Write-Host "[PASS] Account '$Username' password updated on $env:COMPUTERNAME" -ForegroundColor Green
}

$inAdmins = [bool](Get-LocalGroupMember -Group 'Administrators' -ErrorAction SilentlyContinue | Where-Object { $_.Name -like "*$Username" })
if (-not $inAdmins) {
 Add-LocalGroupMember -Group 'Administrators' -Member $Username
 Write-Host "[PASS] '$Username' added to Administrators group on $env:COMPUTERNAME" -ForegroundColor Green
}

Write-Host "`nVerification:" -ForegroundColor Cyan
Get-LocalUser -Name $Username | Format-Table Name, Enabled, PasswordNeverExpires, AccountNeverExpires -AutoSize
```

Repeat on every cluster node. Verify the account exists with identical credentials before proceeding.

</TabItem>

:::note Authentication and Key Vault changes (software 12.2512 and later)
Per Microsoft Learn 2610, starting with software version 12.2512 new deployments no longer create a Microsoft Entra ID application (service principal). The cluster uses a system-assigned managed identity to authenticate with Azure, so do not plan to create or rotate an SPN for the cluster. For deployments created on earlier versions, the Entra application is no longer used and can be deleted after you confirm event ID 609 in the `Microsoft-AzureStack-HCI/Admin` event log (registration context v4). Also, Azure Local does not support deploying with an existing Azure Key Vault that has Private Endpoints enabled.

### Task 5: Networking Configuration

**Storage connectivity:**

| Option | When to use |
|--------|-------------|
| **Network switch for storage traffic** | 3+ node clusters (recommended) |
| **No switch for storage** | 1–2 node clusters only (switchless) |

**Network intents:**

:::info Network intents are defined by your planning design
The number of intents, traffic type assignments, and adapter bindings configured here must match the design from your planning and discovery sessions, as captured in `infrastructure.yml` under `networking.intents[]`. Do not assume a specific number of intents or a fixed layout.

Typical layouts:

| Layout | Intent | Traffic types |
|--------|--------|---------------|
| 2-intent | Management + Compute | Management, Compute |
| 2-intent | Storage | Storage |
| 3-intent | Management | Management |
| 3-intent | Compute | Compute |
| 3-intent | Storage | Storage |

For adapter assignments for each intent, refer to `networking.intents[].adapters` in your `infrastructure.yml`.
:::

**IP Allocation:**

| Setting | Value | Source |
|---------|-------|--------|
| Starting IP | First available IP | `infrastructure.yml`: `networking.management.infrastructure_pool.start` |
| Ending IP | Last available IP | `infrastructure.yml`: `networking.management.infrastructure_pool.end` |
| Subnet mask | e.g., `255.255.255.0` | `infrastructure.yml`: `networking.management.subnet` |
| Default gateway | Gateway IP | `infrastructure.yml`: `networking.management.gateway` |
| DNS servers | Primary, Secondary | `infrastructure.yml`: `networking.management.dns_servers` |
| **Zone name (domain)** | `<DNS_ZONE_NAME>` | `infrastructure.yml`: `identity.active_directory.domain_fqdn` — **Local Identity only** |

:::info Zone name — Local Identity only
This field only appears for Local Identity deployments. Enter the DNS zone where Host A records for each node have been pre-created (e.g., `iic.local`). Must match the zone used when configuring node DNS entries in the pre-deployment DNS requirements step.
:::

:::warning IP Pool Requirement
Minimum **6 consecutive IPs** required for cluster + Arc Resource Bridge. Do NOT include node management IPs in this pool.
:::

:::note Internal DNS (preview)
Learn 2610 also describes **Deploy with Internal DNS (preview)** for environments without a DNS server: on the Networking tab you enter a Zone name, answer **No** to "Do you have an existing DNS Service?", and enter a **Zone Forwarder** IP address. The Internal DNS service supports cluster operations and infrastructure name resolution only. Do not use it as the primary DNS for VMs, Arc-enabled VMs, Kubernetes workloads or applications. This runbook uses an existing DNS server with a configured zone.
:::

**Customize network settings (adapter property overrides):**

For each network intent you can select **Customize network settings**. Microsoft Learn 2610 lists these portal options:

| Setting | Options |
|---------|---------|
| Storage traffic priority | Priority Flow Control priority where Data Center Bridging (DCB) is used |
| System traffic priority | 5, 6 or 7 |
| Storage traffic bandwidth reservation | Percentage allocated to storage traffic |
| Jumbo frame size (bytes) | 1514, 4088 or 9014 |
| RDMA protocol | iWARP, RoCE, RoCEv2, or disabled |

Learn does not state per-intent defaults for these values (for example RDMA off and jumbo 1514 on management and compute, RDMA and jumbo only on storage). Treat any such default as **lab-verified only** and confirm it on a 2610 deployment with `Get-NetIntent`, `Get-NetAdapterAdvancedProperty -RegistryKeyword *JumboPacket` and `Get-NetAdapterRdma`. Change adapter properties only on OEM guidance. Guest RDMA is not supported on Azure Local. These settings do not apply to low capacity class devices.

### Verify Local Identity Configuration

Run these MS-required checks to confirm the cluster deployed in AD-less mode.

**Expected values:**
- `Domain` → `WORKGROUP` — nodes must NOT be domain-joined
- `ADAware` → `2` — cluster is in AD-less (Local Identity) mode

<Tabs groupId="deployment-method">
<TabItem value="direct" label="Direct (On Node)" default>

Run directly on a cluster node via RDP or console session.

**Script:** `scripts/deploy/04-cluster-deployment/phase-05-cluster-deployment/local-identity/task-02-verify-deployment-completion/powershell/Test-LocalIdentityConfig.ps1`

```powershell title="Test-LocalIdentityConfig.ps1 — run directly on node"
# Check 1: Node must NOT be domain-joined — expected result: WORKGROUP
$domain = (Get-WmiObject Win32_ComputerSystem).Domain
Write-Host "Domain membership: $domain" -ForegroundColor $(if ($domain -eq 'WORKGROUP') { 'Green' } else { 'Red' })
if ($domain -ne 'WORKGROUP') {
 Write-Warning "Node is domain-joined ('$domain'). Expected WORKGROUP for Local Identity."
}

# Check 2: Cluster must be in AD-less mode — expected result: 2
$adAware = Get-ClusterResource "Cluster Name" | Get-ClusterParameter ADAware
Write-Host "ADAware value: $($adAware.Value)" -ForegroundColor $(if ($adAware.Value -eq 2) { 'Green' } else { 'Red' })
if ($adAware.Value -ne 2) {
 Write-Warning "ADAware is $($adAware.Value). Expected 2 for Local Identity (AD-less) mode."
}
```

## Troubleshooting

| Issue | Cause | Resolution |
|-------|-------|------------|
| Authentication fails | Password mismatch | Ensure IDENTICAL password on all nodes |
| Deployment fails | Key Vault access | Verify Key Vault permissions |
| Remote access denied | WinRM not configured | Run `Enable-PSRemoting -Force` |
| Validation timeout | Network issues | Check Azure endpoint connectivity |
| Arc extension fails | Agent issue | Reinstall Azure Connected Machine agent |
