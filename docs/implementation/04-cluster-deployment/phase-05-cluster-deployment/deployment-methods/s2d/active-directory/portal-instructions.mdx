## Overview

Active Directory deployment is the **Azure Local Cloud standard** for Azure Local clusters. Authentication is managed through domain accounts, with the Life Cycle Manager (LCM) service account pre-created in AD. Nodes are either left in a **workgroup** (the default: the wizard joins them to the domain automatically during deployment) or, starting with Azure Local 2604, **domain joined before deployment** as an optional path (see [Optional: domain join before deployment](../../../../phase-02-os-installation/manual-installation/task-03-manual-os-installation.mdx#optional-domain-join-before-deployment)).

:::info Azure Local Cloud Standard Deployment
Active Directory authentication is the recommended and fully supported Azure Local Cloud deployment method for Azure Local. All AD object prerequisites were completed in Phase 02 (Active Directory Configuration). If that work is not done, stop and complete Phase 02 first.
:::

## Prerequisites

All items below must be complete before starting the portal wizard. These were completed in earlier phases — this is a verification checklist only.

### AD Prerequisites (Phase 02)

| Requirement | Description | Validation |
|-------------|-------------|------------|
| AD objects pre-created | `New-HciAdObjectsPreCreation` run successfully | Objects visible in `OU=AzureLocal` |
| LCM service account | `svc-azl-deploy@<DOMAIN>` exists, password ≥14 chars | `Get-ADUser svc-azl-deploy` |
| Computer accounts | Pre-created computer objects for each node in designated OU | `Get-ADComputer -SearchBase <OU>` |
| Group memberships | LCM account in all required AD groups | `Get-ADGroupMember` |

### Node Prerequisites (Phase 04)

| Requirement | Description | Validation |
|-------------|-------------|------------|
| **Domain membership** | Default: nodes are in a workgroup and the wizard joins them to the domain during deployment. Optional (2604 or later): nodes already domain joined, with the deployment user in the local Administrators group on each node | `(Get-CimInstance Win32_ComputerSystem).PartOfDomain` is `False` (default) or `True` (optional pre-join); then `Get-LocalGroupMember -Group Administrators` shows the deployment user if pre-joined |
| Arc registered | All nodes visible in Azure Arc > Servers | Portal: Arc > Servers |
| DNS resolves domain | All nodes can resolve the AD domain FQDN | `Resolve-DnsName corp.azurelocal.cloud` |
| DC accessible | Domain controller reachable on port 389 from node management IPs | `Test-NetConnection <DC_IP> -Port 389` |
| WinRM enabled | Remote management enabled on all nodes | `Test-WSMan <NODE_IP>` |

:::info Workgroup (default) or domain joined (optional, 2604 or later)
Microsoft Learn 2610 states: "Starting with version 2604, domain joining before deployment is supported. If you choose to domain join, you must add the deployment user to the local Administrators group. If you don't domain join beforehand, the machines are automatically joined to a domain during the Deployment via Azure portal."

- **Default path:** leave the nodes in a workgroup. The wizard performs the domain join.
- **Pre-join path:** follow [Optional: domain join before deployment](../../../../phase-02-os-installation/manual-installation/task-03-manual-os-installation.mdx#optional-domain-join-before-deployment) on every node. Mixing is not documented by Learn: use the same path on all nodes.
- The Environment Checker software validator is run with `-Exclude Test-IsNotPartofDomain` so a pre-joined node does not fail that check.
:::

:::note Authentication and Key Vault changes (software 12.2512 and later)
Per Microsoft Learn 2610, starting with software version 12.2512 new deployments no longer create a Microsoft Entra ID application (service principal) for the cluster. The cluster uses a system-assigned managed identity to authenticate with Azure. For earlier deployments the Entra application is no longer used and can be deleted after you confirm event ID 609 in the `Microsoft-AzureStack-HCI/Admin` log on the machines (registration context v4). Azure Local does not support deploying with an existing Azure Key Vault that has Private Endpoints enabled.
:::

### Azure Prerequisites

| Requirement | Description | Validation |
|-------------|-------------|------------|
| Subscription | Active subscription; the deploying user is a User Access Administrator and a Contributor on the subscription | `Get-AzSubscription` |
| Resource group roles | On the Arc resource group the deploying user has Azure Stack HCI Administrator, Reader, Key Vault Data Access Administrator, Key Vault Secrets Officer, Key Vault Contributor and Storage Account Contributor, plus Azure Connected Machine Onboarding and Azure Connected Machine Resource Administrator | Resource group > Access control (IAM) |
| Resource group | Dedicated RG for the cluster | Created in Azure Portal |
| Arc registration | All nodes Arc-registered (Phase 04) | Azure Portal > Arc > Servers |

## Portal Deployment

### Task 1: Navigate to Azure Local

1. Open [Azure Portal](https://portal.azure.com)
2. Search for **"Azure Local"**
3. Select **Azure Local** from results
4. Click **+ Create**

### Task 2: Basics Configuration

| Field | Value | Source |
|-------|-------|--------|
| **Subscription** | Select subscription | User Access Administrator and Contributor on the subscription |
| **Resource group** | Select or create | Dedicated RG for cluster |
| **Cluster name** | `<CLUSTER_NAME>` | `cluster.name` |
| **Region** | `<AZURE_REGION>` | `azure.location` |

**Add Arc-registered machines:**

1. Click **Add machines**
2. Select all Arc-registered nodes from Phase 04
3. Click **Add**
4. Allow time for Arc extension installation to complete before proceeding

**Authentication selection:**

Under the **Identity** section of the Basics tab, select **Active Directory** as the authentication type. Domain credentials are entered in [Task 4](#task-4-basics--domain-credentials) below.

- Select **New configuration** (manual configuration)
- Do NOT use an existing template unless one has been explicitly reviewed and approved for this environment

### Task 4: Basics — Domain Credentials

The domain credential fields appear in the **Basics tab** after selecting Active Directory authentication. There is no separate Identity tab.

| Field | Value | Source |
|-------|-------|--------|
| **Authentication type** | **Active Directory** | |
| **Domain FQDN** | `corp.azurelocal.cloud` | `identity.active_directory.domain_fqdn` |
| **Computer OU** | `OU=AzureLocal,OU=Servers,DC=corp,DC=azurelocal,DC=cloud` | `identity.active_directory.ou_path` |
| **Deployment user** | `svc-azl-deploy@corp.azurelocal.cloud` | `identity.active_directory.lcm_user.username` |
| **Deployment password** | [Enter service account password] | `identity.active_directory.lcm_user.password` (keyvault ref) |

:::warning LCM account password requirements
The deployment account password must be **at least 14 characters**. This is a Microsoft hard requirement for the LCM service account. A password shorter than 14 characters will fail portal validation with no clear error message.

**Source**: [MS Learn — AD Deployment Prerequisites](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deployment-prerequisites?view=azloc-2610)
:::

:::info Computer OU distinguished name
The OU path entered here must exactly match the OU used by `New-HciAdObjectsPreCreation` in Phase 02. The pre-created computer account objects for each node must reside in this OU at the time the wizard runs. Verify with `Get-ADComputer -SearchBase "<OU>"` before proceeding.
:::

### Task 5: Networking Configuration

**Storage connectivity:**

| Option | When to use |
|--------|-------------|
| **Network switch for storage traffic** | 3+ node clusters (recommended) |
| **No switch for storage** | 1–2 node clusters only (switchless) |

**Network intents:**

:::info Network intents are defined by your planning design
The number of intents, traffic type assignments, and adapter bindings configured here must match the design from your planning and discovery sessions, as captured in `infrastructure.yml` under `networking.intents[]`. Do not assume a specific number of intents or a fixed layout.

Typical layouts:

| Layout | Intent | Traffic types |
|--------|--------|---------------|
| 2-intent | Management + Compute | Management, Compute |
| 2-intent | Storage | Storage |
| 3-intent | Management | Management |
| 3-intent | Compute | Compute |
| 3-intent | Storage | Storage |

For adapter assignments for each intent, refer to `networking.intents[].adapters` in your `infrastructure.yml`.
:::

**IP allocation:**

| Setting | Value | Source |
|---------|-------|--------|
| Starting IP | First available management IP | `networking.management.infrastructure_pool.start` |
| Ending IP | Last available management IP | `networking.management.infrastructure_pool.end` |
| Subnet mask | e.g., `255.255.255.0` | `networking.management.subnet` |
| Default gateway | Gateway IP | `networking.management.gateway` |
| DNS servers | Primary, Secondary | `networking.management.dns_servers` |

:::warning IP pool requirement
A minimum of **6 consecutive IPs** are required for cluster infrastructure (cluster IP, Arc Resource Bridge IP, etc.). Individual node management IPs are separate — do not include them in this pool.
:::

**Customize network settings (adapter property overrides):**

For each network intent you can select **Customize network settings**. Microsoft Learn 2610 lists these portal options:

| Setting | Options |
|---------|---------|
| Storage traffic priority | Priority Flow Control priority where Data Center Bridging (DCB) is used |
| System traffic priority | 5, 6 or 7 |
| Storage traffic bandwidth reservation | Percentage allocated to storage traffic |
| Jumbo frame size (bytes) | 1514, 4088 or 9014 |
| RDMA protocol | iWARP, RoCE, RoCEv2, or disabled |

Learn does not state per-intent defaults for these values (for example RDMA off and jumbo 1514 on management and compute, RDMA and jumbo only on storage). Treat any such default as **lab-verified only** and confirm it on a 2610 deployment with `Get-NetIntent`, `Get-NetAdapterAdvancedProperty -RegistryKeyword *JumboPacket` and `Get-NetAdapterRdma`. Change adapter properties only on OEM guidance. Guest RDMA is not supported on Azure Local. These settings do not apply to low capacity class devices. Portal deployment does not let you specify your own storage intent IPs; use ARM template deployment for custom storage IPs.

:::info DNS must resolve the AD domain FQDN
For AD deployments, the DNS servers entered here must be able to resolve `identity.active_directory.domain_fqdn`. Nodes query these DNS servers during the domain join step of deployment. If DNS cannot resolve the domain, deployment will fail at domain join.
:::

### Task 9: Validation

1. Click **Start validation**
2. Wait approximately 15–20 minutes for all checks to complete
3. **Do NOT click "Try again"** while validation is running — wait for it to complete or fail before taking any action

:::tip Run the validation monitor
While validation runs, watch it with [Azure Local Sonar](../../../deployment-monitoring/index.mdx).
:::

**Validation checks:**

| Check | Description | Action if failed |
|-------|-------------|-----------------|
| Connectivity | All nodes reachable | Verify network connectivity |
| Arc registration | Nodes registered with Arc | Verify Phase 04 completion |
| Domain accessibility | DC reachable from nodes | `Test-NetConnection <DC_IP> -Port 389` |
| Storage | Disks available and healthy | Check physical disk health |
| Network | NICs available and configured | Verify NIC drivers and connectivity |
| Azure endpoints | Required endpoints accessible | Check firewall and proxy rules |

Resolve all errors before proceeding to Task 10. Warnings may be acknowledged but should be documented.

---

### Task 10: Review + Create

1. Review all configuration settings on the summary page
2. Confirm:
 - All Arc-registered nodes are listed
 - Authentication type shows **Active Directory**
 - Domain FQDN and OU path are correct
 - Management IP pool has 6+ IPs
 - Storage adapters are configured
3. Click **Create**

## Deployment Progress

**Estimated duration:**

| Cluster size | Estimated time |
|-------------|----------------|
| Single machine | 1.5–2 hours |
| Two-node cluster | ~2.5 hours |
| Three+ node cluster | ~3 hours |

**Deployment stages:**

1. Begin cloud deployment (45–60 min)
2. Install Arc extensions
3. Join nodes to domain
4. Configure network intents
5. Create storage pools and volumes
6. Deploy Arc Resource Bridge
7. Provision custom location

### Verify cluster health

<Tabs groupId="post-deployment-ad">
<TabItem value="manual" label="Manual" default>

```powershell title="Run on any cluster node or from a management host with network access"
# Verify nodes are domain-joined after deployment
Invoke-Command -ComputerName @("iic-01-n01","iic-01-n02","iic-01-n03") -ScriptBlock {
 $cs = Get-WmiObject Win32_ComputerSystem
 [PSCustomObject]@{
 Node = $env:COMPUTERNAME
 Domain = $cs.Domain
 DomainJoined = $cs.PartOfDomain
 }
} | Format-Table -AutoSize

# Verify cluster status
Get-Cluster | Format-List Name, QuorumType, QuorumResourceName

# Verify all nodes online
Get-ClusterNode | Format-Table Name, State, NodeWeight

# Verify Storage Spaces Direct health
Get-StoragePool | Format-Table FriendlyName, HealthStatus, OperationalStatus

# Verify volumes
Get-Volume |
 Where-Object FileSystemLabel -match 'ClusterPerf|UserStorage' |
 Format-Table FileSystemLabel, HealthStatus, OperationalStatus, Size
```

</TabItem>

### PowerShell

> **When to use**: Verify the domain join and the cluster health on all nodes after the deployment.

#### Script

| Script | What it does |
|---|---|
| `scripts/deploy/04-cluster-deployment/phase-06-post-deployment/task-09-post-deployment-verification/powershell/Invoke-VerifyPostDeployment.ps1` | Verifies the deployed instance against `infrastructure.yml`. Read only. It checks, in order: every node is a cluster node and Up; the identity (with Active Directory every node is joined to `identity.active_directory.domain_fqdn` and its secure channel works; with local identity every node is in a workgroup); the quorum; the security groups; SSH; storage; the VM images and the logical networks in Azure. Supports `-WhatIf`. |

The earlier verification scripts of this task folder (`Test-ClusterHealth.ps1`, `Invoke-VerifyClusterHealth-Orchestrated.ps1` and the `-Standalone` copies) are removed. The other scripts in the folder are placeholders: they print `NOT IMPLEMENTED`, change nothing and exit with code 3. See [Task 09: Post-deployment verification](../../../../phase-06-post-deployment/task-09-post-deployment-verification.mdx).

The login is `-Credential`, else the account the file names: the LCM user (`identity.active_directory.lcm_user`) with Active Directory, the local administrator (`identity.local_admin`) with local identity. The password is a secret reference. The script never prompts: with neither it stops with exit code 2.

#### Run

```powershell
./Invoke-VerifyPostDeployment.ps1 -InfrastructureFile ./infrastructure.yml -WhatIf
./Invoke-VerifyPostDeployment.ps1 -InfrastructureFile ./infrastructure.yml
./Invoke-VerifyPostDeployment.ps1 -InfrastructureFile ./infrastructure.yml -TargetNode iic-azl-n01
```

## Troubleshooting

| Issue | Cause | Resolution |
|-------|-------|------------|
| Domain join fails | DC unreachable or wrong credentials | `Test-NetConnection <DC_IP> -Port 389` + verify LCM account password |
| LCM password rejected by portal | Password < 14 characters | Reset service account password to ≥14 chars, retry wizard |
| Computer account conflict | Stale pre-existing account in OU | Delete stale computer object from OU, re-run validation |
| Node not domain-joined after deployment | DNS issue during join | Check DNS server setting in Task 5 resolves the AD domain |
| Validation timeout | Azure endpoint connectivity | Check firewall rules for required Azure endpoints |
| Arc extension install fails | Arc agent issue on node | Reinstall Azure Connected Machine agent on affected node |
| Storage configuration fails | Unhealthy physical disk | `Get-PhysicalDisk` on the affected node |

**Collect deployment logs:**

```powershell title="Run on a cluster node — retrieves most recent log files"
Get-ChildItem "C:\CloudDeployment\Logs" -Recurse |
 Sort-Object LastWriteTime -Descending |
 Select-Object -First 10 Name, LastWriteTime, Length |
 Format-Table -AutoSize
```
