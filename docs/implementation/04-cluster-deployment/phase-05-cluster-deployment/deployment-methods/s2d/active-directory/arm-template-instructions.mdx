# Active Directory Authentication - ARM Template Deployment

[![Runbook](https://img.shields.io/badge/Type-Runbook-blue?style=flat-square)](../../../index.mdx)
[![Azure](https://img.shields.io/badge/Platform-Azure_Local-0078D4?style=flat-square&logo=microsoftazure)](https://learn.microsoft.com/en-us/azure/azure-local/)

> **DOCUMENT CATEGORY**: Runbook  
> **SCOPE**: ARM template-based cluster deployment with Active Directory  
> **PURPOSE**: Automated and repeatable deployment via infrastructure-as-code  
> **MASTER REFERENCE**: [Microsoft Learn - Deploy via ARM Template](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deployment-azure-resource-manager-template?view=azloc-2610)

**Status**: Active

## Overview

This guide walks through deploying an Azure Local cluster with **Active Directory** authentication using ARM templates. It is structured as a sequential runbook — complete each task in order from start to finish.

AD authentication requires:
- A pre-existing Active Directory domain accessible from the cluster nodes
- An organizational unit (OU) for Azure Local computer objects
- A deployment service account with the delegated OU permissions that Microsoft Learn lists (list contents, read all properties, read permissions, create and delete computer objects; see [AD-Specific Parameters](#active-directory-authentication))

Per Microsoft Learn 2610, for Azure Local 2503 and later you select the quickstart template `azurestackhci/create-cluster`. The ARM template reference below follows the parameter table that Learn publishes for that template. Learn does not state an API version or a total parameter count, so this runbook does not quote either: treat the exact `apiVersion` and parameter count as **lab-verified only** and diff your parameter file against the current `azuredeploy.parameters.json` in the quickstart template before each deployment. Azure Local Cloud provides parameter template files and a generation script that populate the parameter file from `infrastructure.yml`. See the [Reference](#reference) section at the bottom for the parameter reference.

Learn also states that all parameters in the JSON file must be filled out, including array placeholders such as `[""]`, or validation fails. ARM template deployment is intended for deployments at scale: Learn recommends deploying one system through the Azure portal first.

## Before You Begin

### Prerequisites

| Requirement | Description | Validation |
|-------------|-------------|------------|
| Azure CLI or PowerShell | Az module installed | `Get-Module -Name Az` |
| Subscription access | User Access Administrator and Contributor on the subscription | Verify in IAM |
| Resource group roles | On the Arc resource group: Azure Stack HCI Administrator, Reader, Key Vault Data Access Administrator, Key Vault Secrets Officer, Key Vault Contributor, Storage Account Contributor, plus Azure Connected Machine Onboarding and Azure Connected Machine Resource Administrator | Verify in IAM |
| Resource group | Created for cluster deployment | `Get-AzResourceGroup` |
| Platform Key Vault | Stores deployment credentials (local admin, LCM passwords) | Secrets populated in prior phases |
| Arc-registered nodes | All nodes registered in Azure Arc | Verify in Azure Portal |
| Identical local credentials | Same admin password on all nodes | Verify login via WinRM |
| Active Directory | Domain reachable from all nodes | `Test-ComputerSecureChannel` |
| OU for Azure Local | Dedicated OU in AD | `Get-ADOrganizationalUnit` |
| LCM service account | Domain account (deployment user) with the delegated OU rights from Learn: list contents, read all properties, read permissions, create and delete computer objects (`New-HciAdObjectsPreCreation` assigns these) | Verify delegation |

### What You Need Ready

Before starting the deployment procedure, confirm each item:

1. **`infrastructure.yml` fully populated** — all 13 sections complete, including `cluster_arm_deployment`, `accounts`, `network_intents`, and `compute.cluster_nodes`
2. **Authenticated to Azure** — run `Connect-AzAccount` (PowerShell) or `az login` (CLI) on the machine where you will execute commands
3. **`powershell-yaml` module installed** — required by the generation script: `Install-Module powershell-yaml -Scope CurrentUser`
4. **Arc nodes registered** — Phase 04 complete; `arc_node_resource_ids` populated in `infrastructure.yml`
5. **Platform Key Vault secrets stored** — `local-admin-password` and `lcm-deployment-password` secrets exist in the platform Key Vault (from prior phases)
6. **AD infrastructure ready** — domain reachable, OU created, LCM service account has the delegated OU permissions (created by `New-HciAdObjectsPreCreation`)
7. **Domain membership decided** — the nodes are either in a workgroup (default; the deployment joins them to the domain) or, with Azure Local 2604 or later, already domain joined with the deployment user in the local Administrators group. See [Optional: domain join before deployment](../../../../phase-02-os-installation/manual-installation/task-03-manual-os-installation.mdx#optional-domain-join-before-deployment)

:::info Where to Run From
All commands in this runbook run from the **azurelocal-toolkit repository root** on a management/jump box authenticated to Azure. The toolkit scripts expect `infrastructure.yml` at `infrastructure.yml` relative to the repo root.
:::

:::info Key Vault Architecture
Two Key Vaults are involved in Azure Local deployment:

- **Platform Key Vault** — Already exists from prior phases. Stores deployment credentials (local admin password, LCM domain service account password). Referenced in the parameter file via Key Vault references. **No action needed here.**
- **Cluster Key Vault** — Created by the ARM template deployment (`keyVaultName`, `softDeleteRetentionDays`, `diagnosticStorageAccountName`, `logsRetentionInDays` are defined in `infrastructure.yml`). Azure Local does not support deploying with an existing Key Vault that has Private Endpoints enabled.

Per Microsoft Learn, starting with software version 12.2512 new deployments do not create a Microsoft Entra ID application (service principal) for the cluster; the cluster uses a system-assigned managed identity. Do not create an ARB service principal or client secret for this template (the `arbDeploymentAppID` family of parameters applies only to Azure Local 2411.3 and earlier).
:::

## Deployment Procedure

### Task 1: Verify Active Directory Prerequisites

Confirm that each cluster node can reach the domain, the OU exists, and the LCM service account has the required delegation.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Manual Commands" default>

**When to use**: You want to verify each check individually using standard AD PowerShell commands.

```powershell title="Step 1 — Define variables from infrastructure.yml"
# Replace placeholders with values from your infrastructure.yml
$nodeIPs = @("<NODE_IP_1>", "<NODE_IP_2>") # nodes[].network_adapters[].ip_address
$ouPath = "<DOMAIN_OU_PATH>" # identity.active_directory.ou_path
$lcmUser = "<LCM_USERNAME>" # identity.active_directory.lcm_user.username
```

```powershell title="Step 2 — Verify domain connectivity from each node"
# Expected: True for every node
Invoke-Command -ComputerName $nodeIPs -ScriptBlock {
 [pscustomobject]@{
 Node = $env:COMPUTERNAME
 SecureChannel = (Test-ComputerSecureChannel)
 }
}
```

**Expected output** — every node returns `SecureChannel = True`:
```
Node SecureChannel
---- -------------
iic-01-n01 True
iic-01-n02 True
```

```powershell title="Step 3 — Verify OU exists"
# Expected: Returns the OU object without error
Get-ADOrganizationalUnit -Identity $ouPath | Format-List Name, DistinguishedName
```

```powershell title="Step 4 — Verify the LCM account has the delegated rights on the OU"
# Microsoft Learn (custom AD configuration): deployment user over the OU and descendants =
# list contents, read all properties, read permissions, create computer objects, delete computer objects.
# Full control applies only to descendant msFVE-RecoveryInformation objects.
$acl = Get-Acl "AD:\$ouPath"
$aces = @($acl.Access | Where-Object { $_.IdentityReference -like "*$lcmUser*" })
$rights = ($aces.ActiveDirectoryRights | ForEach-Object { $_.ToString() }) -join ', '

$required = 'ListChildren', 'ReadProperty', 'ReadControl', 'CreateChild', 'DeleteChild'
$missing = $required | Where-Object { $rights -notmatch $_ }

if ($aces.Count -gt 0 -and -not $missing) {
 Write-Host "PASS: $lcmUser has the delegated rights on $ouPath" -ForegroundColor Green
 $aces | Format-Table IdentityReference, ActiveDirectoryRights, InheritanceType
} else {
 Write-Host "FAIL: $lcmUser is missing: $($missing -join ', ') on $ouPath" -ForegroundColor Red
 Write-Host "Re-run New-HciAdObjectsPreCreation or follow the Microsoft Learn custom Active Directory configuration article." -ForegroundColor Yellow
}
```

### Task 2: Get HCI Resource Provider Object ID

The `hciResourceProviderObjectID` parameter requires the tenant-specific Object ID of the `Microsoft.AzureStackHCI` resource provider service principal. This GUID is unique per Entra ID tenant and must be looked up once, then stored in `infrastructure.yml` at `azure.hci_resource_provider_object_id`.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Manual Commands" default>

**When to use**: Quick one-time lookup.

```powershell title="PowerShell — look up the Object ID"
(Get-AzADServicePrincipal -ApplicationId "1412d89f-b8a8-4111-b4fd-e82905cbd85d").Id
```

```bash title="Azure CLI alternative"
az ad sp list --filter "appId eq '1412d89f-b8a8-4111-b4fd-e82905cbd85d'" --query "[0].id" -o tsv
```

The application ID `1412d89f-b8a8-4111-b4fd-e82905cbd85d` is the Azure Local resource provider application ID published on Microsoft Learn; looking it up by application ID is the documented method.

**Expected output**: A single GUID, e.g. `ab12cd34-ef56-7890-ab12-cd34ef567890`

**Next**: Open `infrastructure.yml`, find `azure.hci_resource_provider_object_id`, and paste the GUID as the value.

### Task 3: Generate Parameter File

Create the deployment-ready JSON parameter file for the `create-cluster` template. This step produces the file used by Tasks 4 and 5.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Manual Commands" default>

**When to use**: You want to build the parameter file by hand or use a pre-built example as a starting point.

1. Copy the template: `configs/azure/arm-templates/04-cluster-deployment/azuredeploy.parameters.ad.json`
2. Replace all `{{VARIABLE}}` placeholders with values from your `infrastructure.yml`

**Key placeholders to replace** (most common errors come from these):

| Placeholder | YAML Source Path | Description |
|-------------|-----------------|-------------|
| `{{CLUSTER_NAME}}` | `cluster.name` | Cluster resource name |
| `{{RESOURCE_GROUP}}` | `azure.resource_group` | Target resource group |
| `{{LOCATION}}` | `azure.location` | Azure region |
| `{{KEY_VAULT_NAME}}` | `cluster.key_vault.name` | Cluster KV (created by ARM) |
| `{{DIAGNOSTIC_STORAGE}}` | `cluster.diagnostics.storage_account` | KV diagnostics storage |
| `{{WITNESS_STORAGE}}` | `cluster.witness.storage_account` | Cloud witness storage |
| `{{LOCAL_ADMIN_USER}}` | `identity.local_admin.username` | Local admin on all nodes |
| `{{LCM_ADMIN_USER}}` | `identity.active_directory.lcm_user.username` | LCM sAMAccountName (no `@domain`) |
| `{{HCI_RP_OBJECT_ID}}` | `azure.hci_resource_provider_object_id` | From Task 2 |
| `{{DOMAIN_FQDN}}` | `identity.active_directory.domain_fqdn` | AD domain FQDN |
| `{{ADOU_PATH}}` | `identity.active_directory.ou_path` | OU distinguished name |
| `{{NAMING_PREFIX}}` | `cluster.naming_prefix` | Resource prefix |

For `localAdminPassword` and `AzureStackLCMAdminPassword`, use Key Vault references (not plain text):

```json title="Key Vault reference format (points to platform Key Vault)"
"localAdminPassword": {
 "reference": {
 "keyVault": {
 "id": "/subscriptions/<SUB_ID>/resourceGroups/<RG>/providers/Microsoft.KeyVault/vaults/<PLATFORM_KV_NAME>"
 },
 "secretName": "local-admin-password"
 }
}
```

3. Verify all `{{` placeholders are replaced: search the file for `{{` — there should be zero matches
4. Save as `azuredeploy.parameters.ad.json` in your working directory

:::tip Use an Example as Reference
Validated IIC examples exist for each networking pattern in `config/azure/arm-templates/examples/`. Compare your file against the matching pattern — see the **Example Parameter Files** collapsible in the [Reference](#reference) section below.
:::

### Task 4: Validate Deployment

Run the ARM template in **Validate** mode first. Validation executes the full deployment pipeline — environment checks, connectivity tests, credential validation — but stops before provisioning. Fix all errors before proceeding to Deploy.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Manual Commands" default>

**When to use**: You built the parameter file manually in Task 3 and want to run validation directly.

```powershell title="Define deployment variables"
# Values from infrastructure.yml
$subscriptionId = "<SUB_ID>" # azure.subscription_id
$resourceGroup = "<RESOURCE_GROUP>" # azure.resource_group
$parametersFile = ".\azuredeploy.parameters.ad.json" # File from Task 3
$templateUri = "https://raw.githubusercontent.com/Azure/azure-quickstart-templates/master/quickstarts/microsoft.azurestackhci/create-cluster/azuredeploy.json"

# Set subscription context
Set-AzContext -SubscriptionId $subscriptionId
```

```powershell title="Ensure deploymentMode is set to Validate"
# Check current mode in the parameters file
$json = Get-Content $parametersFile | ConvertFrom-Json
$currentMode = $json.parameters.deploymentMode.value
Write-Host "Current deploymentMode: $currentMode"

# If not "Validate", update it:
if ($currentMode -ne "Validate") {
 $json.parameters.deploymentMode.value = "Validate"
 $json | ConvertTo-Json -Depth 20 | Set-Content $parametersFile
 Write-Host "Updated deploymentMode to Validate" -ForegroundColor Yellow
}
```

```powershell title="Run validation"
$validateResult = New-AzResourceGroupDeployment `
 -Name "azl-validate-$(Get-Date -Format 'yyyyMMddHHmmss')" `
 -ResourceGroupName $resourceGroup `
 -TemplateUri $templateUri `
 -TemplateParameterFile $parametersFile `
 -Verbose

$validateResult | Select-Object DeploymentName, ProvisioningState, Timestamp
```

**Expected output** for a successful validation:
```
DeploymentName ProvisioningState Timestamp
-------------- ----------------- ---------
azl-validate-20260309142055 Succeeded 3/9/2026 2:45:30 PM
```

If validation fails, check the error output against the [Troubleshooting](#troubleshooting) table.

</TabItem>

### Task 5: Deploy Cluster

After validation passes, switch to **Deploy** mode and run the deployment. This provisions the cluster — the process takes 1.5–3 hours depending on node count.

<Tabs groupId="deployment-method">
<TabItem value="manual" label="Manual Commands" default>

**When to use**: You ran validation manually in Task 4 and want to continue with direct commands.

```powershell title="Step 1 — Switch deploymentMode to Deploy"
$parametersFile = ".\azuredeploy.parameters.ad.json"

$json = Get-Content $parametersFile | ConvertFrom-Json
$json.parameters.deploymentMode.value = "Deploy"
$json | ConvertTo-Json -Depth 20 | Set-Content $parametersFile
Write-Host "Updated deploymentMode to Deploy" -ForegroundColor Green
```

```powershell title="Step 2 — Run deployment"
$templateUri = "https://raw.githubusercontent.com/Azure/azure-quickstart-templates/master/quickstarts/microsoft.azurestackhci/create-cluster/azuredeploy.json"
$resourceGroup = "<RESOURCE_GROUP>" # azure.resource_group
$deploymentName = "azl-deploy-$(Get-Date -Format 'yyyyMMddHHmmss')"

$deployment = New-AzResourceGroupDeployment `
 -Name $deploymentName `
 -ResourceGroupName $resourceGroup `
 -TemplateUri $templateUri `
 -TemplateParameterFile $parametersFile `
 -Verbose

$deployment | Select-Object DeploymentName, ProvisioningState, Timestamp
```

:::danger This is a Long-Running Operation
The `New-AzResourceGroupDeployment` command blocks until deployment completes (1.5–3 hours). Do not close the terminal. Use the monitoring script in a separate terminal to track progress.

Invoke-Command -ComputerName $nodeIP -Credential $cred -ScriptBlock {
 Write-Host "=== Cluster Status ===" -ForegroundColor Cyan

 Write-Host "`n=== Node Status ===" -ForegroundColor Cyan

 Node = $_.Name
 Domain = (Get-WmiObject -ComputerName $_.Name Win32_ComputerSystem).Domain
 Secure = (Test-ComputerSecureChannel -Server $_.Name -ErrorAction SilentlyContinue)

}

## Troubleshooting

| Issue | Cause | Resolution |
|-------|-------|------------|
| Key Vault access denied | Missing RBAC on platform KV | Grant `Key Vault Secrets User` to deployment identity on the **platform** Key Vault |
| Domain join fails | LCM account lacks OU permissions | Verify the delegated rights on the OU (create/delete computer objects, list, read) and that the deployment user is in the local Administrators group if the nodes were pre-joined |
| Credential mismatch | Different local passwords across nodes | Reset to identical password on all nodes |
| `adouPath` format error | Incorrect DN syntax | Must be full DN: `OU=...,DC=...,DC=...` |
| Validation fails on `hciResourceProviderObjectID` | Wrong Object ID | Re-run `Get-AzADServicePrincipal` (Task 2) |
| `networkingPattern` error | Intent layout doesn't match pattern | Verify intent count and traffic types match pattern |
| Deployment timeout | Network or Azure service issue | Check node Azure endpoint connectivity |
| Arc extension failed | Node not reachable from Azure | Verify WinRM/HTTPS and Arc agent status |
| `deploymentMode` stuck on `Validate` | Forgot to switch mode | Re-run the script with `-DeploymentMode Deploy` or edit the JSON |
| Parameter file has `{{` placeholders | Incomplete placeholder replacement | Search file for `{{` and replace all remaining |

### Deployment Logs

```powershell title="Check deployment logs on a cluster node"
# Azure-side deployment operations
Get-AzResourceGroupDeploymentOperation `
 -ResourceGroupName $resourceGroup `
 -DeploymentName $deploymentName |
 Where-Object { $_.ProvisioningState -ne "Succeeded" } |
 Select-Object OperationId, ProvisioningState, @{N="Error";E={$_.StatusMessage}} |
 Format-List

# Node-side logs
Invoke-Command -ComputerName $nodeIP -Credential $cred -ScriptBlock {
 Get-ChildItem "C:\CloudDeployment\Logs" -Recurse |
 Sort-Object LastWriteTime -Descending |
 Select-Object -First 10 FullName, LastWriteTime
}
```

### Network intent adapter property overrides

The `intentList` entries accept optional override blocks. Microsoft's `Microsoft.AzureStackHCI/clusters/deploymentSettings` reference describes the adapter overrides `jumboPacket`, `networkDirect` and `networkDirectTechnology` (expected technologies `iWARP`, `RoCEv2`, `RoCE`) and states for each: "This parameter should only be modified based on your OEM guidance. Do not modify this parameter without OEM validation." Leave the override flags `false` unless the hardware vendor tells you otherwise.

```json title="intentList entry shape (illustrative values; confirm against the template and OEM guidance)"
{
  "name": "Storage",
  "trafficType": ["Storage"],
  "adapter": ["SMB1", "SMB2"],
  "overrideVirtualSwitchConfiguration": false,
  "virtualSwitchConfigurationOverrides": {},
  "overrideQosPolicy": false,
  "qosPolicyOverrides": {},
  "overrideAdapterProperty": true,
  "adapterPropertyOverrides": {
    "jumboPacket": "9014",
    "networkDirect": "Enabled",
    "networkDirectTechnology": "RoCEv2"
  }
}
```

The portal equivalents (**Customize network settings**) are storage traffic priority, system traffic priority (5, 6 or 7), storage bandwidth reservation, jumbo frame size (1514, 4088 or 9014) and the RDMA protocol (iWARP, RoCE, RoCEv2 or disabled). Microsoft Learn does not publish per-intent defaults. The Azure Local Cloud design intent of "storage intent: RDMA on and jumbo frames; management and compute intents: RDMA off, jumbo at the default" is **owner policy, lab-verified only**: confirm it after deployment with `Get-NetIntent`, `Get-NetAdapterAdvancedProperty -RegistryKeyword *JumboPacket` and `Get-NetAdapterRdma`. Guest RDMA is not supported on Azure Local.

#### networkingPattern Values

:::note Only `hyperConverged` is shown by Microsoft Learn
Learn gives `hyperConverged` as the example value for `networkingPattern`. The other values below are the pattern names used by the Azure Local Cloud parameter templates; they are **not documented by Microsoft Learn 2610** and are lab-verified only. <details>
<summary><strong>Key Vault Reference Syntax</strong></summary>

Sensitive parameters (`localAdminPassword`, `AzureStackLCMAdminPassword`) use Key Vault references that point to the **platform Key Vault** — the vault provisioned in prior phases where deployment credentials are already stored:

```json title="Key Vault reference pointing to platform Key Vault"
"localAdminPassword": {
 "reference": {
 "keyVault": {
 "id": "/subscriptions/<SUB_ID>/resourceGroups/<RG>/providers/Microsoft.KeyVault/vaults/<PLATFORM_KV_NAME>"
 },
 "secretName": "local-admin-password"
 }
}
```

This is **not** the cluster Key Vault (`keyVaultName`) — that vault is created by the ARM template during deployment.

:::danger Never Store Passwords in Plain Text
Always use Key Vault references to the platform Key Vault for sensitive parameters.
:::

</details>
