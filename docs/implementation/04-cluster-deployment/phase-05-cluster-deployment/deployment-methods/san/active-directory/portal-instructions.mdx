## Overview

This runbook deploys a disaggregated Azure Local cluster using the Azure Portal wizard with:
- **Storage**: External SAN (Fibre Channel; iSCSI is selected in the wizard from 2610) — not Storage Spaces Direct
- **Identity**: Active Directory. The nodes are either in a workgroup (the wizard joins them to the domain) or domain-joined before deployment (supported from version 2604)

The portal wizard flow is similar to the [S2D AD portal deployment](../../s2d/active-directory/portal-instructions.mdx) but with key differences in storage and networking configuration.

## Prerequisites

Complete all items from the [SAN Prerequisites](../index.mdx#prerequisites) and the [AD Prerequisites](../../index.mdx#active-directory-deployment-s2d-and-san) sections.

Additionally:
- [ ] FC HBA drivers installed on all nodes
- [ ] MPIO verified on all nodes (enabled by default from 2604), the array registered with MSDSM **and claimed**, and the node restarted (see [SAN Configuration](../index.mdx#san-configuration-before-cluster-deployment-fibre-channel))
- [ ] FC zoning done and the two system LUNs unmasked to all nodes **before Arc registration** (disaggregated), so the LUNs are visible through `Get-PhysicalDisk`
- [ ] LUNs in RAW state — not initialized, partitioned, or formatted
- [ ] Infrastructure LUN ≥ 250 GB, performance history LUN ≥ 20 GB
- [ ] Local administrator credentials identical on all nodes (14+ characters, lowercase, uppercase, numeral, special character)

:::info Workgroup or domain-joined nodes
Learn 2610 states: "Starting with version 2604, domain joining before deployment is supported. If you choose to domain join, you must add the deployment user to the local Administrators group. If you don't domain join beforehand, the machines are automatically joined to a domain during the Deployment via Azure portal."

To domain join first, follow [Optional: domain join before deployment](../../../../phase-02-os-installation/manual-installation/task-03-manual-os-installation.mdx#optional-domain-join-before-deployment). Do not install Windows Updates through SConfig or Azure Update Manager before deployment (this causes a deployment failure).
:::

:::warning Rack aware is not selectable for disaggregated
In the wizard, you can't select the **Rack aware** cluster option for disaggregated deployments. Use **Standard**. Learn 2610 also publishes a separate preview procedure for a [disaggregated rack aware cluster with SAN storage](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deploy-rack-aware-cluster-storage-area-network?view=azloc-2610), which is outside this runbook.
:::

## Portal Wizard — Step-by-Step

### Step 1: Start the Wizard

1. In the Azure portal, navigate to **Azure Arc** → **Azure Local**
2. On the **Get started** tab, on the **Deploy Azure Local** tile, select **Create instance**

### Step 2: Basics

1. Select **Subscription** and **Resource group**
2. Enter the **Instance name** for this Azure Local cluster
3. Select the **Region** for Azure resources
4. **Cluster options**: Select **Standard** (Rack aware can't be selected for disaggregated)
5. **Storage options**: Select **Storage Area Network (SAN)**
6. **Identity provider**: Select **Active Directory**
7. Select **+ Add machines** and choose the Arc-registered machines
8. **Install extensions**: Arc extensions install automatically on the selected machines (this can take several minutes; refresh to check). If an installation fails, select the failed machines and retry
9. Select **Validate selected machines** and wait for the green check (each machine must run the same OS version, have the correct extensions and symmetric network adapters)
10. Select an existing **Key Vault** or create a new one (retention 7 to 90 days, which you can't change later)

:::warning Key Vault with Private Endpoints
Azure Local doesn't support deploying a cluster using an existing Key Vault that has Private Endpoints enabled.
:::

### Step 3: Model

Choose **New configuration** (or a **Template spec**). **Quickstart template** isn't available in this release.

### Step 4: Configuration

1. Enter the Active Directory **Domain**. It must be the same FQDN used when AD DS was prepared
2. Enter the **OU** path created for this deployment, for example `OU=Local001,DC=contoso,DC=com`. The OU can't be at the top level of the domain
3. Enter the **Deployment account** credentials (the domain user you created when you prepared AD)
4. Enter the **Local administrator** credentials (identical on all nodes)
5. **iSCSI Configuration** (Azure Local 2610 and later): leave it disabled for Fibre Channel. For iSCSI, select **Enable**, specify the authentication type and the iSCSI network details, and select **Configure**. Do not enable iSCSI manually on the machines first

### Step 5: Networking

The networking configuration for disaggregated deployments differs from S2D:

1. **Storage configuration**: Select **SAN based storage** (the only available option)
2. **Traffic types**: Configure **Management** and **Compute** traffic
   - Available patterns: **Group management and compute** or **Separate management and compute**
   - There are no storage traffic intents
3. For each network intent, select at least one unused adapter (preferably two matching adapters for redundancy)
4. For each cluster network, specify the cluster network name, adapter, VLAN ID and subnet. If you share adapters with iSCSI, select the already-configured iSCSI adapters
5. Choose IP allocation **Manual** or **Automatic** (DHCP). For static IPs, allocate a contiguous block of at least six addresses on the management subnet (not used by the machines), then provide subnet mask, default gateway and one or more DNS servers

:::info No Storage Network Intents
Unlike S2D deployments, SAN deployments do **not** configure a storage intent through Network ATC. Storage traffic flows over the FC fabric (or the dedicated iSCSI adapters), not over an Azure Local storage intent. Cluster networks (CSV, live migration, heartbeat) are defined separately in the wizard with their own adapter, VLAN and subnet. See [Disaggregated host networking](../index.mdx#disaggregated-host-networking).
:::

#### Customize network settings (optional)

Select **Customize network settings** for an intent to change:

| Setting | Learn 2610 |
|---------|-----------|
| Storage traffic priority | Priority Flow Control priority where DCB is used |
| System traffic priority | Choose 5, 6 or 7 |
| Storage traffic bandwidth reservation | Bandwidth allocation in percent for storage traffic |
| Jumbo frame size (bytes) | 1514, 4088 or 9014 |
| RDMA protocol | For disaggregated deployments, "The RDMA protocol is disabled for cluster networks" |

Learn's API reference says adapter overrides "should only be modified based on your OEM guidance." Learn 2610 does not state the default RDMA and jumbo values per intent. **Owner policy (not stated by Microsoft, lab-verify on 2610 with `Get-NetAdapterAdvancedProperty -RegistryKeyword *JumboPacket` and `Get-NetAdapterRdma`):** leave the management and compute intent at defaults unless the OEM says otherwise. Jumbo frames on the switch ports must be set manually to match.

### Step 6: Security

Accept the recommended security settings or customize as needed.

### Step 7: Advanced — SAN Storage Selection

1. Optionally edit the **Custom location name**
2. Select or create the **cloud witness** storage account
3. Select the **infrastructure LUN** (the field only shows volumes of at least 250 GB) and the **cluster performance history LUN** (at least 20 GB). Workload LUNs are configured after deployment

:::warning Do Not Delete Infrastructure Volumes
The infrastructure volumes created during deployment must **never** be deleted. They are critical for cluster operation.
:::

4. Optionally add **Tags** for governance

### Step 8: Validation and Deployment

1. Select **Start validation** — takes about 20 minutes for one to two machines and longer for bigger deployments
2. Monitor validation progress. Don't select **Try again** while validation tasks are running
3. After validation succeeds, review and select **Create** to begin deployment. If deployment fails, use **Resume deployment** on the instance's **Deployments** page

### Deployment notes (authentication)

Starting with software version 12.2512, new deployments no longer create a Microsoft Entra ID application (service principal); the cluster uses a system-assigned managed identity to authenticate with Azure. For existing deployments the cluster switches to the managed identity automatically, and the old Entra app can be deleted. Before deleting the app, confirm the registration context is v4 and that event ID 609 exists:

```powershell
Get-ClusterNode | % { Get-WinEvent -ComputerName $_ -LogName Microsoft-AzureStack-HCI/Admin | ? Id -eq 609 }
```

## Troubleshooting

| Issue | Resolution |
|-------|------------|
| "Rack aware" option greyed out | Expected for disaggregated deployments. Use Standard cluster option. |
| No SAN disks visible in advanced settings | Verify FC zoning and MPIO configuration (including the MSDSM claim and restart). Run `Get-PhysicalDisk` to confirm disks are visible on all nodes. |
| Each LUN shows once per path | The vendor is registered but not claimed by MSDSM. Claim it (lab-verified, see [SAN Configuration](../index.mdx#san-configuration-before-cluster-deployment-fibre-channel)) and restart. |
| Validation fails on storage | Ensure LUNs are in RAW state. Infrastructure LUN must be ≥ 250 GB. |
| Machine validation fails | Check that the array is from a [supported vendor](https://learn.microsoft.com/en-us/azure/azure-local/concepts/san-requirements?view=azloc-2610); validation fails for unsupported SAN vendors. |
| Deployment fails on networking | Verify network intents use Management+Compute only (no storage intent). Check VLAN IDs and subnet configuration. |
| Deployment fails after SConfig updates | Updates must not be installed through SConfig or Azure Update Manager before deployment; they are installed during deployment. |
