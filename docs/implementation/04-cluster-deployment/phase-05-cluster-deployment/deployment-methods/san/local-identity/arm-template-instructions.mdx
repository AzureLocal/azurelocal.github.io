## Overview

Azure Local Cloud earlier published a parameter set for "SAN plus Local Identity" that reused the SAN settings with `domainFqdn` and `adouPath` set to empty strings. **That recipe is not supported by Learn 2610 and has been removed.** It combined parameters from two different templates, one of which (`storageConfiguration`) does not exist.

:::warning Not documented by Microsoft
Learn 2610 publishes two separate ARM template families, and neither covers SAN plus Local Identity:

| Scenario | Template | Identity parameters | Storage parameters |
|----------|----------|--------------------|--------------------|
| Disaggregated, Fibre Channel | `azurestackhci/create-cluster-san` | `domainFqdn`, `adouPath`, `AzureStackLCMAdminUsername` and password (Active Directory) | `infraVolLunId`, `infraPerfLunId`, `sanNetworkList` |
| Disaggregated, iSCSI | `azurestackhci/create-cluster-san-iscsi` | Same as above | Same, plus `nodes` |
| Local identity (hyperconverged) | `azurestackhci/create-adless-cluster-external-dns-public-preview` | `identityProvider` = `LocalIdentity`, `dnsServerConfig` (`UseDnsServer`), `dnsZones` (for example `dnsZoneName`, `dnsForwarder`); **no** `domainFqdn`, `adouPath` or LCM admin parameters | `storageNetworkList` (Storage Spaces Direct); **no** SAN parameters |

Do not merge the two templates by hand and expect Microsoft support. Learn publishes no SAN template that takes `identityProvider` and no local identity template that takes `infraVolLunId` or `infraPerfLunId`.
:::

## What to Do Instead

| Need | Option |
|------|--------|
| SAN plus Active Directory with automation | [AD — ARM Template (SAN)](../active-directory/arm-template-instructions.mdx) |
| SAN plus Local Identity | [Local Identity — Portal (SAN)](./portal-instructions.mdx). Learn's disaggregated wizard offers the identity provider choice, but the combination has no dedicated Learn walkthrough, so **lab-verify it first**. |
| Local Identity plus automation | The local identity template is for hyperconverged (S2D) deployments: see [Local Identity — ARM Template (S2D)](../../s2d/local-identity/arm-template-instructions.mdx) |

If you intend to lab-test a SAN plus Local Identity ARM deployment anyway, treat everything as **lab-verified-only**:

1. Start from `create-cluster-san` (or the iSCSI variant), not from the local identity template, and ask Microsoft Support whether the combination is supported for your build
2. Record exactly which parameters the validation accepts; do not publish them as a standard until Learn documents them
3. Remember the object ID lookup uses the application ID, not a display name:
   ```powershell
   (Get-AzADServicePrincipal -ApplicationId "1412d89f-b8a8-4111-b4fd-e82905cbd85d").Id
   ```

## Local Identity Requirements That Still Apply

Whatever method you use, Local Identity on Azure Local requires:

- A non-built-in local administrator account with identical credentials on all nodes
- Static IP addresses (DHCP is not supported) and a DNS zone with Host A records (or the Internal DNS preview)
- Nodes in workgroup (confirm with `(Get-WmiObject Win32_ComputerSystem).Domain`)
- SSH enabled on each node, and one Key Vault per cluster

See [Local Identity Prerequisites](../../index.mdx#local-identity-deployment-s2d-and-san).

## Troubleshooting

| Issue | Resolution |
|-------|------------|
| Template validation fails after merging parameters | Expected. The two templates have different parameter sets. Use the portal path or the AD SAN template. |
| Key Vault access denied | Ensure the deploying identity has the Key Vault roles Learn lists (Key Vault Contributor, Key Vault Secrets Officer, Key Vault Data Access Administrator). |
| SAN disks not detected | Verify FC zoning, the MSDSM claim and MPIO on all nodes before deployment. |
