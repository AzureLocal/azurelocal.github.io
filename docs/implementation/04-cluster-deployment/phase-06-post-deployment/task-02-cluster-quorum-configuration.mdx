# Task 02: Cluster Quorum Configuration

[![Implementation](https://img.shields.io/badge/Type-Implementation-blue?style=flat-square)](../../../index.mdx)
[![Cluster Deployment](https://img.shields.io/badge/Stage-04%20Cluster%20Deployment-orange?style=flat-square)](../../index.mdx)

> **DOCUMENT CATEGORY**: Implementation Runbook  
> **SCOPE**: Azure Local, WSFC (S2D / SAN), and standalone Hyper-V clusters  
> **PURPOSE**: Validate the witness storage account exists (create if absent), then configure cluster quorum
> **MASTER REFERENCE**: [Cluster Quorum Configuration](https://learn.microsoft.com/en-us/windows-server/failover-clustering/manage-cluster-quorum)

**Status**: Active

Configure cluster quorum for high availability and split-brain prevention. Cloud Witness is the recommended type for all cluster scenarios. The deployment creates the witness from `cluster.witness` of `infrastructure.yml`; use this task to check it, or to change it after the deployment.

---

## Quorum Options

| Quorum Type | Best For | Requirements |
|-------------|----------|--------------|
| **Cloud Witness** | Azure Local, WSFC (S2D/SAN), Hyper-V — recommended | Azure Storage Account, internet access |
| **File Share Witness** | Air-gapped or on-premises environments | Domain-joined file server — not a cluster node |
| **Disk Witness** | Legacy WSFC/SAN only | Shared disk visible to all nodes; incompatible with S2D and Azure Local |

:::tip Recommended Configuration
**Cloud Witness** is the recommended quorum type for all cluster scenarios. It requires an Azure Storage Account (`cluster.witness.storage_account`). The deployment creates the witness; the steps below check it or change it.
:::

### Failover Cluster Manager

> **When to use**: Single cluster, prefer GUI-based configuration, or verifying an existing quorum setting

#### Step 1 — Verify or Create the Cloud Witness Storage Account

Before configuring quorum, ensure the storage account exists in Azure.

1. Open **Azure Portal** → search for **Storage accounts**
2. Verify `cluster.witness.storage_account` exists in the correct resource group
3. If absent, create it:
 | Field | Value | Source |
 |-------|-------|--------|
 | Subscription | _(deployment subscription)_ | `azure.subscription_id` |
 | Resource group | _(cluster resource group)_ | `azure.resource_group` |
 | Name | _(witness SA name)_ | `cluster.witness.storage_account` |
 | Region | _(cluster region)_ | `azure.location` |
 | Redundancy | Standard ZRS or LRS | no key (the script or Azure decides it) |

4. After creation, navigate to the storage account → **Security + networking** → **Access keys**
5. Copy **key1** — you will need it for the quorum configuration below

#### Step 2 — Configure Quorum via Failover Cluster Manager

**Cloud Witness (recommended):**

1. Open **Failover Cluster Manager** on a management server or cluster node
2. Connect to the cluster
3. Right-click the cluster name → **More Actions** → **Configure Cluster Quorum Settings...**
4. Click **Next** on the wizard welcome screen
5. Select **Select the quorum witness** → **Next**
6. Select **Configure a cloud witness** → **Next**
7. Enter:
 - **Azure storage account name**: `<cluster_witness.name from infrastructure.yml>`
 - **Azure storage account key**: _(key1 from Azure Portal)_
 - **Azure service endpoint**: leave default (`core.windows.net`)
8. Click **Next** → **Next** → **Finish**

**File Share Witness (air-gapped / alternative):**

1. On a domain-joined file server (**not** a cluster node), create a shared folder
2. Grant the **cluster computer account** Full Control on the share
3. In Failover Cluster Manager: **More Actions** → **Configure Cluster Quorum Settings...**
4. Select **Configure a file share witness**
5. Enter the UNC path: `\\<file-server>\<share-name>`
6. Click **Next** → **Finish**

#### Validation

- [ ] Quorum witness shown in Failover Cluster Manager under the cluster summary
- [ ] Cluster Events show no quorum-related warnings or errors
- [ ] `Get-ClusterQuorum` returns expected `QuorumType` and `QuorumResource`

### PowerShell

> **When to use**: Check the witness against `cluster.witness` of `infrastructure.yml`, or set it when it was added or changed after the deployment. The script runs from a management host; every cluster command runs on a node over PowerShell remoting, so the host needs neither the failover clustering tools nor domain membership. It is idempotent.

#### Script

| Script | What it does |
|---|---|
| `scripts/deploy/04-cluster-deployment/phase-06-post-deployment/task-02-cluster-quorum-configuration/powershell/Invoke-ConfigureClusterQuorum-Orchestrated.ps1` | Sets the quorum witness from `cluster.witness.type`. `cloud`: it checks the storage account (an existing one is checked and never changed; a missing one is created as `StorageV2` with `Standard_LRS`), then runs `Set-ClusterQuorum -CloudWitness` on a node unless the cluster already uses that account. `file_share`: `Set-ClusterQuorum -FileShareWitness` with `cluster.witness.path`; the share and its permissions are not created. `none`: `Set-ClusterQuorum -NoWitness`; refused on a two-machine instance. A disk witness is not supported with Storage Spaces Direct, so the script has no disk witness step. Supports `-WhatIf`. |
| `scripts/deploy/04-cluster-deployment/phase-06-post-deployment/task-09-post-deployment-verification/powershell/Invoke-VerifyPostDeployment.ps1` | Read only. Its quorum check: a quorum type is set and the quorum state is Normal. See [Task 09](./task-09-post-deployment-verification.mdx). |

Parameters: `-InfrastructureFile` (required), `-ComputerName` (the node the cluster commands run on; default: the first node of `nodes[]`, then the next one), `-Credential`, `-AccessKeyName` (`key1`, the default, or `key2`), `-UpdateAccessKey` (set the cloud witness again with the current key, after a key rotation) and `-LogPath`. The access key is never printed, logged or returned: it goes to the node as a SecureString. The script never prompts.

For a cloud witness, sign in to Azure first (`Connect-AzAccount -Tenant <azure.tenant_id>`); you need Storage Account Contributor on the resource group. The login for the nodes is `-Credential`, else the LCM user (`identity.active_directory.lcm_user`) with Active Directory or the local administrator (`identity.local_admin`) with local identity; the password is a secret reference. Exit 0: the witness is as the file says (set now, already so, or planned under `-WhatIf`). Exit 1: a call or a precondition failed. Exit 2: a value in the file is missing or there is no login; nothing is changed.

#### Run

```powershell
# Read Azure and the cluster, change nothing
./Invoke-ConfigureClusterQuorum-Orchestrated.ps1 -InfrastructureFile ./infrastructure.yml -WhatIf

# Set the witness
./Invoke-ConfigureClusterQuorum-Orchestrated.ps1 -InfrastructureFile ./infrastructure.yml

# Check the result (read only)
./Invoke-VerifyPostDeployment.ps1 -InfrastructureFile ./infrastructure.yml
```

### Azure CLI

> **When to use**: Run the task from a host that has the Azure CLI and not the Az PowerShell modules. The script is PowerShell 7 that calls `az`; it reads `infrastructure.yml` and carries no values of its own.

#### Script

| Script | What it does |
|---|---|
| `scripts/deploy/04-cluster-deployment/phase-06-post-deployment/task-02-cluster-quorum-configuration/azurecli/New-CloudWitnessStorageAccount.azcli.ps1` | Creates, or checks, the Azure storage account of the cloud witness that cluster.witness of infrastructure.yml names, with the Azure CLI. Supports `-WhatIf`. |

Requires: PowerShell 7 and the Azure CLI, signed in with `az login --tenant <azure.tenant_id>`.

Azure side only. An existing account is checked and never changed: a cloud witness supports only a Standard general-purpose v2 account with locally redundant storage, so an account of another kind or SKU is reported as `Failed`. A missing account is created (`StorageV2`, `Standard_LRS`) after the script checks that the name is free. It never reads, prints or stores an access key. Pointing the cluster at the account (`Set-ClusterQuorum -CloudWitness`) runs on a node and is not an Azure CLI task. For `cluster.witness.type` `none` or `file_share` it does nothing and exits 0. You need Storage Account Contributor (or Contributor) on the resource group.

#### Run

```powershell
./New-CloudWitnessStorageAccount.azcli.ps1 -InfrastructureFile ./infrastructure.yml -WhatIf
./New-CloudWitnessStorageAccount.azcli.ps1 -InfrastructureFile ./infrastructure.yml
```

## Validation Summary

| Check | Command | Expected Result |
|-------|---------|----------------|
| Quorum type | `Get-ClusterQuorum \| Select QuorumType` | `NodeAndCloudWitness` or `NodeAndFileShareMajority` |
| Quorum state | `(Get-Cluster).QuorumState` | `Normal` |
| Witness resource | `Get-ClusterResource \| Where-Object ResourceType -match "Witness"` | `State: Online` |
| Storage account | `Get-AzStorageAccount -Name <name> -ResourceGroupName <rg>` | `ProvisioningState: Succeeded` |

## Troubleshooting

| Issue | Cause | Resolution |
|-------|-------|------------|
| `Set-ClusterQuorum` fails with access denied | Insufficient permissions on cluster or storage account | Run as cluster administrator; verify SPN has `Storage Account Key Operator Service Role` on the witness storage account |
| Quorum state shows `NotConfigured` | Cloud witness storage account key is incorrect or rotated | Re-configure with fresh key: `Set-ClusterQuorum -CloudWitness -AccountName <name> -AccessKey <newkey>` |
| Witness resource shows `Failed` | Storage account firewall blocking cluster node IPs | Add cluster node public IPs to the storage account firewall allow list or enable `Allow trusted Microsoft services` |
