## 2. Hardware Prerequisites

:::warning Critical Assumption
**Hardware must be racked, powered, and cabled per vendor guidance before beginning provisioning stages.** This includes:
- All Dell AX servers physically installed in racks
- Power cables connected to redundant PDUs
- Network cables installed per cabling design specifications
- iDRAC/BMC interfaces accessible and configured
- Console access available for all servers

The provisioning runbook assumes physical infrastructure is complete and validated.
:::

### Server Requirements

**Hyperconverged (Storage Spaces Direct) deployments support 1 to 16 machines per instance. Disaggregated deployments (external SAN, no Storage Spaces Direct) support up to 64 machines.** A hybrid instance is a hyperconverged instance with an external SAN attached after deployment.

| Component | Minimum | Recommended | Notes |
|-----------|---------|-------------|-------|
| **CPU** | Intel Xeon Gold/Platinum or AMD EPYC 7000 series | Latest generation enterprise CPUs | Must support virtualization |
| **RAM** | 256GB per server | 512GB+ per server | ECC memory required |
| **Storage** | 1TB SSD/NVMe (OS boot) + 2TB+ across 2+ data drives | All-NVMe configuration | Controllers must be HBA/passthrough mode — RAID not supported |
| **Network** | 2x 10GbE NICs minimum | 2x 25GbE or higher | RDMA-capable adapters for the storage intent (see [Section 5](#5-network-prerequisites)) |

:::note Design standard versus Microsoft minimum
The Minimum column is this runbook's production design standard. Microsoft's published minimums in [System requirements for Azure Local](https://learn.microsoft.com/en-us/azure/azure-local/concepts/system-requirements-23h2?view=azloc-2610) are lower: ECC memory of at least 32 GB, a boot drive of at least 200 GB (400 GB or more for machines with more than 768 GB of memory), at least two data drives of at least 500 GB each, TPM 2.0 and Secure Boot turned on, and Intel VT or AMD-V turned on. Hardware must be in the [Azure Local catalog](https://aka.ms/azurelocalcatalog) for Microsoft Support. Storage controllers must pass drives through (HBA pass-through mode): RAID controllers and shared SAS enclosures are not supported for Storage Spaces Direct. External Fibre Channel or iSCSI SAN storage is supported only as the SAN configurations described in [Storage Planning](../planning/07-storage-planning.mdx).
:::

### Physical Infrastructure

- **Rack Mounting**: Servers properly racked per vendor specifications
- **Power**: Redundant power supplies connected to separate PDUs
- **Cooling**: Adequate rack cooling and environmental controls
- **Cable Management**: Clean cable routing with proper labeling
- **Access**: Physical security controls for server room/rack access

### Management Access

- **iDRAC/BMC**: All servers accessible via out-of-band management
- **Console Access**: Direct console access available for troubleshooting
- **Network Access**: Management interfaces reachable from administration workstations

### Hardware Vendor Solution Builder Extension (SBE) Package {#sbe-package}

:::warning The SBE package is a requirement
Download your hardware vendor's Solution Builder Extension package for your model and the Azure Local version you deploy, **before you start**. It is a requirement: you need it to update the cluster, and the automation reads it from a share and checks it before the cluster is created. To install it during the build, switch on the side-load in the file; it is off by default.
:::

Put the package on a share or folder that the automation can read. You need it either way. A vendor whose package has no automatic download for your cluster leaves the first update in the `AdditionalContentRequired` state until you import the files (Dell, for example, without support credentials on the cluster). The later update reuses the same share: `Add-SolutionUpdate` imports the files, then `Start-SolutionUpdate` installs them. See [Import and rediscover updates](https://learn.microsoft.com/en-us/azure/azure-local/update/update-via-powershell-23h2?view=azloc-2610#step-3-import-and-rediscover-updates) on Microsoft Learn and [Update management and Solution Builder Extension](../operations/update-management-and-sbe.mdx).

The share holds the three files as the vendor delivers them:

| File | Purpose |
|------|---------|
| `SBE_Discovery_<Vendor>.xml` | The discovery manifest |
| `SBE_<Vendor>_<Family>_<Version>.xml` | The payload manifest |
| `SBE_<Vendor>_<Family>_<Version>.zip` | The payload |

**What stays optional** is only the build-time side-load: `hardware.sbe.delivery` is off unless you set it, and the toolkit never side-loads a package you did not ask for.

#### What the automation checks

The pre-cluster verification gate checks the package on the share with six checks. Each one blocks the cluster creation when it fails.

| Check | What it verifies |
|-------|------------------|
| SB-001 | The package source is configured (or you declared it not applicable, with a reason) |
| SB-002 | The share is reachable (read only) |
| SB-003 | The three files are present |
| SB-004 | The files are unmodified: the hashes match the manifest and, when you set them, `package_sha256` and `package_size_bytes` |
| SB-005 | The hardware model of every node is listed in the package's own supported models. A package for the wrong hardware family fails: a 17G Intel package fails on AX-760 nodes, and the right one is `16G-45n0c-Intel` 5.0.2609.1611 |
| SB-006 | The package version is validated for the target solution version (for Dell on 2610, `12.2610.1004.x`) |

#### Keys in `infrastructure.yml`

| Key | Meaning |
|-----|---------|
| `hardware.sbe.requirement` | `required`, or `not_applicable` when the hardware has no SBE or the cluster downloads it with the vendor credential |
| `hardware.sbe.not_applicable_reason` | Required with `not_applicable`: why, in one sentence |
| `hardware.sbe.source_path` | The share or folder that holds the three files |
| `hardware.sbe.source_username` | Optional account that reads the share, if the account running the automation cannot |
| `hardware.sbe.source_password` | A Key Vault reference (`keyvault://<vault>/<secret>`) for that account. Never the password itself |
| `hardware.sbe.package_sha256`, `hardware.sbe.package_size_bytes` | Optional. The payload's SHA-256 and size as the vendor publishes them |
| `hardware.sbe.delivery` | The build-time side-load: `winrm_copy`, `node_pull` or `skip`. Default `skip` |

#### Vendors differ: check your vendor's page

The table is a summary from Microsoft Learn (release 2610) and vendor pages. It is **not yet verified cell by cell**, so check your vendor's own page, and do not assume "download first" applies in the same way to every vendor. See [Solution Builder Extension updates](https://learn.microsoft.com/en-us/azure/azure-local/update/solution-builder-extension?view=azloc-2610) on Microsoft Learn.

| Vendor | What to expect |
|--------|----------------|
| Dell (AX, MC) | An SBE package. The download is behind a login. You side-load it unless the cluster has Dell support credentials |
| HPE | A Standard SBE from HPE's licence portal on some Gen11 models. Other models use a Minimal SBE plus a Windows Admin Center extension |
| Lenovo ThinkAgile MX Premier | Automatic download and staging |
| DataON | An SBE on S2D6, S2D7, AZS6 and AZS7. Otherwise a Windows Admin Center extension |
| Older hardware, Validated Nodes | Hardware older than 2311.2, and Validated Nodes, may have no SBE |

Where your hardware has no SBE, or the cluster downloads it itself, set `hardware.sbe.requirement` to `not_applicable` and give the reason.

## 3. Software Prerequisites

### Operating System

- This runbook targets the Azure Local **12.x release train (OS build 26100)**. The latest release is **12.2610** (solution version 12.2610.1004.50, October 2026). In the 2610 release all new and existing deployments run OS version **26100.33650**, so network adapter and other drivers must be compatible with that OS version or with Windows Server 2025. See [Releases and Support Lifecycle](../planning/08-release-and-support-lifecycle.mdx). Azure Stack HCI 23H2 (OS build 25398) is out of support
- **Core installation** (no Desktop Experience available; management via Windows Admin Center or remote tools)
- **Identity**: Active Directory (the default; domain recommended for production) or local identity with Azure Key Vault. With Active Directory, the machines can either stay in a workgroup until the deployment joins them to the domain, or be joined to the domain before deployment (optional, supported starting with version 2604; add the deployment user to the local Administrators group). With local identity the machines stay in a workgroup
- **Inbox network drivers are not supported**: an adapter whose `DriverProvider` is Microsoft uses the inbox driver. Install the OEM driver first

### Management Tools

| Tool | Version | Purpose | Installation |
|------|---------|---------|--------------|
| **Windows Admin Center** | 2311+ | Dell hardware health telemetry (optional) | [Download](https://learn.microsoft.com/en-us/windows-server/manage/windows-admin-center/overview) |
| **Azure CLI** | 2.50+ | Azure resource management | `winget install Microsoft.AzureCLI` |
| **Azure PowerShell** | 10.0+ | Azure automation | `Install-Module -Name Az -Force` |
| **Azure Stack HCI PowerShell** | Latest | HCI-specific cmdlets (module names still use the Az.StackHCI and AzStackHci prefixes) | Included with Azure Local |

:::note[Windows Admin Center is Optional]
Windows Admin Center is **not required** for Azure Local deployment or day-to-day cluster management — Microsoft recommends the **Azure Portal** as the primary management interface.

If you are not using Dell hardware, or do not require hardware health telemetry in Azure Monitor, WAC can be skipped entirely.
:::

### IP and Subnet Planning

The following must be defined before deployment begins (from the [Microsoft Learn deployment checklist](https://learn.microsoft.com/en-us/azure/azure-local/deploy/deployment-prerequisites?view=azloc-2610) and [Network considerations for cloud deployments](https://learn.microsoft.com/en-us/azure/azure-local/plan/cloud-deployment-network-considerations?view=azloc-2610)):

| Requirement | Details |
|-------------|---------|
| **Management network subnet** | Minimum **6 contiguous IPs** for infrastructure services (first IP assigned to failover clustering) |
| **Storage VLAN IDs** | Two unique VLAN IDs for storage networks (Network ATC defaults: **711** and **712**; a third storage network, when present, uses 713). Custom storage IPs and VLANs are possible only with an ARM template deployment |
| **DNS server** | Must resolve the Active Directory domain and public endpoints. **Cannot be changed after deployment.** The same servers on every node and on the infrastructure IP range; at least one outside the instance; no public resolvers such as 8.8.8.8. See [DNS decisions](#dns-decisions-are-permanent) |
| **Reserved Kubernetes ranges** | No node IP, cluster IP, infrastructure IP pool, DNS server, proxy, gateway or VM logical network may fall in the Azure Resource Bridge ranges. Plan around `10.96.0.0/12` and `10.244.0.0/16`. New deployments created on 2610 or later (Arc resource bridge 1.8.0) use a smaller service range, `10.96.0.0/24`, but deployments created before 2610 (including after an update) keep `10.96.0.0/12`, and AKS on Azure Local keeps `10.96.0.0/12` and its pod range `10.244.0.0/16`. The wider range is the safe planning rule |
| **NTP source** | Time synchronization for all nodes (domain controllers or dedicated NTP appliance). The node must not use the local CMOS clock as its time source; once domain joined, a node synchronizes from the PDC emulator |
| **Node IP assignment** | Static or DHCP (with reservations) is supported for node and cluster IPs, and the management IP pool is needed either way. **This runbook's design standard is static management IPs.** Local identity deployments require static IPs and do not support DHCP. Use only one default gateway across the node's physical adapters; the portal fails network validation when more than one adapter has a default gateway |

### DNS decisions are permanent

DNS cannot be changed after the deployment completes, so settle these before the OS is configured (from [Network considerations for cloud deployments](https://learn.microsoft.com/en-us/azure/azure-local/plan/cloud-deployment-network-considerations?view=azloc-2610#dns-server-considerations)):

1. The same DNS servers on every node, and the same servers as the infrastructure IP address range (the Azure Resource Bridge and AKS control planes use them).
2. At least one configured DNS server runs outside the Azure Local instance. Running all of them as VMs on the instance is not supported.
3. Every configured server resolves the on-premises domains the infrastructure needs; public DNS servers such as 8.8.8.8 are not supported.
4. DNS server IPs do not overlap the Azure Resource Bridge ranges (see the table above).
5. When an ARM template lists several servers, each is a quoted string separated by commas.

### Network Architecture

Azure Local uses [Network ATC](https://learn.microsoft.com/en-us/azure/azure-local/concepts/network-atc-overview?view=azloc-2610) intents to define traffic types. Traffic types are management (to and from outside the system), compute (VM traffic) and storage (SMB, which includes Storage Spaces Direct and SMB-based live migration; layer 2, not routable). The following network segments are required:

| Network | Purpose | VLAN | RDMA |
|---------|---------|------|------|
| **Management** | Cluster management, Arc connectivity, DNS, AD | Customer-assigned | No. RDMA is for host storage traffic |
| **Storage 1** | Storage Spaces Direct replication (East-West) | 711 (default) | Yes (storage intent) |
| **Storage 2** | Storage Spaces Direct replication (East-West) | 712 (default) | Yes (storage intent) |
| **Compute/VM** | Tenant VM traffic | Customer-assigned | No. Guest RDMA is not supported on Azure Local |

RDMA, a jumbo MTU, and DCB priorities belong to the **storage** intent. Learn lists the following as overridable Network ATC settings: storage VLANs, jumbo packets (portal options 1514, 4088 or 9014), Network Direct (set `false` to disable RDMA), Network Direct technology (`RoCEv2` or `iWarp`) and DCB traffic priorities, and recommends the defaults. Learn does not publish the management and compute defaults. The toolkit's ARM parameter generation states them explicitly: storage intent RDMA on with jumbo frames, management and compute intents RDMA off with the 1514 default. Treat that as the runbook's policy, and confirm it on a 2610 instance after deployment (`Get-NetAdapterRdma`, `Get-NetAdapterAdvancedProperty -RegistryKeyword *JumboPacket`, `Get-NetIntent`). This is lab-verified only until Learn states it.

**Supported intent patterns (hyperconverged)** follow the number of network adapter ports per node (2, 4, 6 or 8), using at least two ports per intent for redundancy:

| Ports | Intents | Notes |
|-------|---------|-------|
| 2 | One intent for all traffic | Needs a network switch for storage; 10 Gb minimum, 25 GbE or higher recommended |
| 4 | Management and compute on Port 1 and Port 2 (SET); storage on Port 3 and Port 4 | The storage intent is not a SET team; it uses SMB Multichannel. Works switched or switchless |
| 6 | Management on Port 1 and Port 2 (SET); compute on Port 3 and Port 4 (SET); storage on Port 5 and Port 6 | Management and compute separated |
| 8 | As 6 ports, plus a second compute or backup intent on the remaining ports | Custom configuration, up to three intents, one of which includes management |

"Group compute and storage, separate management" is also available with a switch. Switchless storage needs at least two intents (management and compute, plus storage); the portal removes the all-traffic and compute-plus-storage options for switchless. On hyperconverged clusters the storage intent shares the same ToR switch pair as management and compute; a separate storage-only switch pair is not supported and can cause split-brain.

**Hybrid (Storage Spaces Direct plus SAN)**: the Storage Spaces Direct network stays as above. SAN connectivity uses separate fabrics and adapters (FC HBAs, or dedicated physical NICs for iSCSI) that Network ATC does not manage; plan those ports up front even though the SAN is attached after deployment.

**Disaggregated (SAN only, up to 64 machines)**: no Storage Spaces Direct and no RDMA storage intent. Two ports carry the management and compute intent (SET, Network ATC); a separate pair of standalone ports carries the cluster networks (default VLANs 1711 and 1712) and is not managed by Network ATC. Fibre Channel uses a 4-port layout (or 6 with a guest backup intent); iSCSI uses the 6-port dedicated-path pattern with two more standalone ports for iSCSI paths A and B. PFC, host ETS and lossless Ethernet are not required because all of this traffic runs over TCP. See [Storage Planning](../planning/07-storage-planning.mdx).

**Physical switch requirements** (per [Microsoft Learn — Physical network requirements](https://learn.microsoft.com/en-us/azure/azure-local/concepts/physical-network-requirements?view=azloc-2610) and the network considerations article):

- IEEE 802.1Q (VLANs): required for all traffic types
- IEEE 802.1Qbb (Priority Flow Control) and 802.1Qaz (Enhanced Transmission Selection): required for the storage traffic of switched hyperconverged deployments (RDMA). Disaggregated deployments do not require them
- IEEE 802.1AB (LLDP): required, with the Learn custom TLVs
- Jumbo frames: Learn recommends an MTU of **9216** bytes for RDMA storage traffic, configured the same on the physical switches (host portal options 1514, 4088 or 9014; Learn gives 9000 on the host with 9216 on the switch as a common pairing for disaggregated deployments). The range 1514 to 9174 in the physical network article is the SDN encapsulation requirement, not the storage MTU. For external SAN (iSCSI) networks use the MTU your storage vendor specifies, end to end
- ECN for RoCEv2 deployments, and MLAG for redundant ToR pairs
- Switchless (direct connect) storage: 1 to 4 nodes, a hard upper limit, with no scale-out. The portal supports switchless for 1 or 2 nodes; 3 and 4 node switchless clusters deploy only with an ARM template and need Storage Auto IP turned off with every storage IP defined explicitly

### Arc Gateway (Optional)

If cluster nodes cannot reach Azure endpoints directly, deploy an [Arc Gateway](https://learn.microsoft.com/en-us/azure/azure-arc/servers/arc-gateway) to proxy Arc traffic. Arc Gateway configuration is defined in `variables.yml` under `deployment.arc_gateway`.

## 7. Validation Checklist

Use this checklist to verify all prerequisites before proceeding to implementation.

### ☐ Planning Phase
- [ ] Discovery checklist completed and approved
- [ ] Site assessment completed and approved
- [ ] Naming standards documented and approved
- [ ] Landing zone strategy documented and approved
- [ ] `variables.yml` populated with environment values

### ☐ Hardware Validation
- [ ] All servers racked, powered, and cabled
- [ ] iDRAC/BMC accessible for all servers
- [ ] Network connectivity verified (management interfaces)
- [ ] Hardware specifications meet [Azure Local system requirements](https://learn.microsoft.com/en-us/azure/azure-local/concepts/system-requirements-23h2?view=azloc-2610)
- [ ] Firmware/BIOS versions current per OEM solution builder extension
- [ ] Hardware vendor Solution Builder Extension (SBE) package for your model and Azure Local version downloaded and available on a share the automation can read, or `hardware.sbe.requirement: not_applicable` with a reason (see [the SBE package](#sbe-package))
- [ ] Storage controllers in HBA/passthrough mode (RAID not supported)
- [ ] Minimum 2 data drives per node for Storage Spaces Direct

### ☐ Software Validation
- [ ] Azure CLI installed and authenticated
- [ ] Azure PowerShell modules installed
- [ ] GitLab access configured
- [ ] PowerShell execution policy allows scripts
- [ ] Windows Admin Center installed *(optional — required only for Dell OMIMSWAC hardware monitoring)*

### ☐ Azure Validation
- [ ] Subscription active with sufficient quota
- [ ] 10 required RBAC roles assigned to deployment account: 2 on the subscription and 8 on the resource group (see [Section 4](#4-azure-prerequisites))
- [ ] All 13 required resource providers registered, including `Microsoft.KeyVault` (see [Section 4](#4-azure-prerequisites))
- [ ] Azure Arc prerequisites met (TLS 1.2, Windows firewall disabled/configured, proxy configured if applicable)

### ☐ Network Validation
- [ ] Outbound HTTPS (443) access confirmed from all nodes
- [ ] DNS resolution working for all nodes
- [ ] NTP synchronization configured
- [ ] Firewall/proxy rules allow required Azure endpoints (see [Section 5](#5-network-prerequisites))
- [ ] HTTPS inspection disabled along the entire networking path
- [ ] Static IPs allocated: management, storage VLANs, and 6+ contiguous management IPs for Azure services
- [ ] Physical switches configured (VLANs, jumbo MTU 9216 on the storage ports or the storage vendor's MTU for SAN, IEEE 802.1Q/Qbb/Qaz for RDMA storage)
- [ ] DNS servers final: same on all nodes, at least one outside the instance, none public, none in the Azure Resource Bridge ranges

### ☐ Security & Identity Validation
- [ ] Microsoft Entra ID tenant active and associated with the Azure subscription
- [ ] Active Directory domain functional with DNS resolution
- [ ] LCM deployment user account created with required permissions
- [ ] Local administrator credentials set identically across all cluster nodes
- [ ] MFA enabled for administrative accounts *(customer responsibility)*
