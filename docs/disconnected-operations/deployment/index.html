Deployment

This page summarizes the order of work. The exact commands, parameters and screenshots are in the Microsoft Learn articles linked from each step, and they change between releases, so follow Learn for the version you deploy.

Before you start​

  1. Read the known issues for your release.
  2. Confirm the eligibility criteria and that your subscription is approved. If a subscription is not approved, any create action in the acquire flow fails.
  3. Finish the network, identity, PKI and management cluster planning.

The flow​

StepWhat you doWhere you workLearn article
1. AcquireCreate the virtual appliance resource in the Azure portal, download the manifest and appliance files, and download the Azure Local ISOAzure portalAcquire disconnected operations
2. Prepare nodesInstall the OS, network, certificates and environment settings on every management cluster nodeEach node, with local administrator rightsPrepare Azure Local for disconnected deployments
3. Deploy the control planeInstall the appliance on the first node (the seed node) with the OperationsModuleSeed node, with local administrator rightsDeploy Azure Local with disconnected operations

Acquire​

  • You need an active Azure subscription, an approval for disconnected operations, and an Azure account with RBAC rights to create a disconnected operations instance.
  • Azure CLI is not supported for this step. Use the REST API if you need automation.
  • On the Basics tab you choose the subscription, resource group, appliance name, the region (used for billing and support metadata only; there is no metadata from the on-premises installation), the outbound connectivity option (limited connectivity or air-gapped) and the pricing model. The pricing model is either a limited two-month free trial (you cannot create more trials afterwards) or a capacity-based annual term billed monthly on the number of physical Azure Local cores you manage with disconnected operations.
  • After the resource is created you download a manifest file (under 1 KB) and the appliance files (250 GB or more, which can take several hours). Learn suggests the portal's download script. Put the files on a share or portable media for deployment.
  • Download the Azure Local ISO from Download software in the Azure portal, and pick the software version that is compatible with your disconnected operations build.

Version compatibility​

Azure Local can never be on a newer version than your disconnected operations build (the control plane). Learn publishes a table that maps each disconnected operations build to the Azure Local build and target solution version. Check it before you download. If nodes come with an OEM golden image on a lower version, update the image to the target solution version.

Prepare the nodes​

The preparation article covers, for every node in the management cluster:

  1. Download the Azure Local ISO that matches your control plane version, install the OS, and apply OEM firmware and drivers.
  2. Use the same adapter names on every node, and create the virtual switches that match your network plan (for a single converged intent, ConvergedSwitch(ManagementComputeStorage)). Set VLANs if you use them.
  3. Rename each node to your naming convention.
  4. Management cluster only: keep at least 600 GB of free space on the deployment drive, or initialize a data disk on every node.
  5. Copy the root certificate public key to each node, place it in the AzureLocal folder in APPDATA, and import it into the local root store.
  6. Set the machine-level environment variable DISCONNECTED_OPS_SUPPORT.
  7. Domain join each node before deployment (recommended), add the deployment user to the local Administrators group, and place the computer in the correct OU.
  8. Pick the first node (sorted by name) as the seed node. It deploys the control plane.

For fully air-gapped sites also:

  • Point each node's time source at a local server such as your domain controller.
  • Install the Microsoft Code Signing PCA 2011 certificate on each node. Without it, cloud deployment of the cluster fails.

Deploy the control plane and the management cluster​

  • Deploy on the seed node. Copy the appliance files into one base folder, extract the zip, and use the OperationsModule it contains. Install the appliance with Install-Appliance. Learn says the setup takes a few hours and must finish successfully before you move on. If it fails because of incorrect network, identity or observability settings, fix the configuration object and run it again; the -clean switch starts from scratch.
  • After installation the portal can show a "System not configured" page for 2 to 3 hours while configuration runs. Check Get-ApplianceHealthState; open a support ticket if no errors show and all services report 100 but the portal does not appear.
  • Add the disconnected operations cloud environment to the nodes so they can bootstrap against the control plane (Add-AzLocalEnvironment for release 2607 and later).
  • Place the dedicated management cluster in the operator subscription (recommended) and limit access to that subscription to the people who need it.
  • Register the required resource providers from a client machine, not from the nodes, and wait until they all show Registered.
  • If the nodes have a preinstalled OEM image, Learn describes a zero-day update step. Run Invoke-AzStackHciArcInitialization with the cloud set to Azure.local (any other value makes the node try to register with public Azure) and a target solution version that matches the appliance version.
  • Configure observability for a first deployment if you run with limited connectivity. It does not apply to air-gapped sites, because system-generated logs and diagnostics need connectivity.
  • Create the Azure Key Vault before you deploy Azure Local, to avoid long delays caused by a known issue. Learn tells you to wait 5 minutes in the deployment article and up to 20 minutes for RBAC permissions to propagate in the known issues article, so allow the longer time.

Register​

Registration is a self-attestation. From a machine with internet access you submit the hardware details of the management cluster to your disconnected operations resource: total cores and nodes, disk and memory, OEM, hardware SKU, the version at registration, the Solution Builder Extension version and the device ID (from Get-ApplianceInstanceConfiguration). When it succeeds, the portal banner disappears and the hardware properties are populated.

Deploy workload clusters​

Deploy workload clusters and manage them from the local control plane. Learn lists these related articles: Azure CLI for disconnected operations, Azure Local VMs, AKS, Azure Container Registry and Azure Policy. For the general cluster deployment procedure on this site, see Cluster deployment, and note that a disconnected deployment uses the local control plane instead of Azure.
