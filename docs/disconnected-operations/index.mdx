# Disconnected Operations on Azure Local

Disconnected operations let you deploy and manage Azure Local instances without a connection to the Azure public cloud. A local control plane gives you a familiar Azure portal and Azure CLI experience for virtual machines and containerized applications, with data, operations and control inside your own boundary.

:::note Not the same as a short loss of connectivity
A standard, cloud-connected Azure Local cluster keeps running workloads when the link to Azure is down for a while. Disconnected operations is a different deployment model with its own local control plane (a virtual appliance on a dedicated management cluster), its own hardware requirements and an approval process. Plan it from the start. Microsoft Learn states that the minimum hardware to deploy and operate Azure Local this way is higher than for a standard deployment, because you host a local control plane.
:::

## Why use it

Microsoft Learn lists three scenarios:

- **Sovereign requirements and compliance.** In sectors such as government, healthcare and finance, data residency and sovereignty requirements can be hard to meet with public sovereign cloud controls. Running disconnected keeps data, operations and control inside your organization's boundary.
- **Remote or isolated locations.** Where network infrastructure is limited, such as oil rigs and manufacturing sites, you can use Azure Arc services and run workloads without relying on internet connectivity.
- **Security.** Not exposing systems to external networks reduces the attack surface for industries with strict security requirements.

## What the local control plane supports

| Service | What you get |
|---------|--------------|
| Azure portal | An Azure portal experience similar to Azure public |
| Azure Resource Manager | Subscriptions, resource groups, ARM templates and CLI |
| Role-based access control | RBAC for subscriptions and resource groups |
| Managed identity | System-assigned managed identity for resource types that support it |
| Arc-enabled servers | Manage VM guests for Azure Local VMs |
| Azure Local VMs | Create and manage Windows or Linux VMs |
| Arc-enabled Kubernetes clusters | Connect and manage CNCF Kubernetes clusters deployed on Azure Local VMs |
| AKS on Azure Local | Set up and manage AKS clusters. See [AKS on Azure Local](../azure-services/aks-on-azure-local.md) |
| Azure Local device management | Create and manage instances, including adding and removing nodes |
| Azure Container Registry | Create and manage container registries |
| Azure Key Vault | Create and manage key vaults |
| Azure Policy | Enforce standards when you create new resources |

Only these services are available in the local control plane. Check the [limits](./limits.mdx) page before you design a workload around a service that is not listed.

## Two connectivity options

When you create the virtual appliance resource in Azure, you choose how the appliance is deployed.

| Option | Behavior |
|--------|----------|
| **Limited connectivity** | The appliance can optionally connect to Azure, which simplifies support and updating the appliance. All Azure Local node traffic and Azure Arc agent traffic stays on your network. |
| **Air-gapped** | The appliance never connects to Azure. You import and export data in both directions, such as update packages and support logs, across your datacenter boundary yourself. |

Learn notes that both modes let you operate the control plane and the surrounding Azure Local nodes fully disconnected.
