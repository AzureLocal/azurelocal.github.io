Storage Architecture Planning

DOCUMENT CATEGORY: Reference SCOPE: Storage architecture planning PURPOSE: Guide storage architecture decisions and document SAN requirements MASTER REFERENCE: Microsoft Learn — Storage overview for Azure Local

Status: Active Validated against: Microsoft Learn, view azloc-2610 (solution 12.2610.1004.50)

Overview​

Azure Local supports three storage topologies:

  • Hyperconverged (Storage Spaces Direct, S2D): Storage is provided by NVMe and SSD drives local to each node. S2D pools these drives into a distributed volume namespace managed by Cluster Shared Volumes. No external storage hardware is required. 1 to 16 machines.
  • Hybrid (S2D plus an external SAN): A standard hyperconverged instance is deployed first, then Fibre Channel or iSCSI SAN volumes are attached as a day-2 operation and run side by side with S2D. You choose S2D or SAN volumes per workload for VMs, AKS and Azure Virtual Desktop. You cannot deploy a hybrid configuration from the start.
  • Disaggregated (SAN only): There is no Storage Spaces Direct. The cluster uses an external SAN over Fibre Channel or iSCSI, and compute and storage scale independently, up to 64 machines. LUNs for the infrastructure volume and performance history must be presented before deployment.

Supported SAN connectivity is Fibre Channel (FC) and iSCSI; Dell PowerFlex is supported through a software initiator. iSCSI was in preview from 2605 and is generally available from 2607 for both hybrid and disaggregated deployments. Fibre Channel hybrid requires version 2604 or later. FCoE is not among the supported SAN protocols.

This page covers the decision criteria between the topologies, the LUN layout for SAN deployments, the network and hardware planning each one needs, and the commercial effect of choosing a SAN.

Use this matrix during discovery and planning to inform the storage topology recommendation.

When to Use Each Topology​

Storage Spaces Direct (S2D)​

S2D is the default and, for most deployments, the right choice.

Select S2D when:

  • There is no existing SAN investment to leverage
  • The deployment is greenfield with no legacy storage dependencies
  • The team prefers software-defined storage administration over FC fabric management
  • Capacity and performance requirements can be met by local NVMe or SSD drives
  • The deployment does not need to share storage with other platforms

It reduces hardware dependencies, simplifies cabling, and aligns with the Azure Local hyperconverged reference architecture.

Hybrid (S2D plus SAN)​

Select hybrid when you need S2D as the base and an existing certified SAN for particular workloads.

Plan for hybrid when:

  • An existing certified FC or iSCSI SAN array holds data or services that should sit beside Azure Local workloads
  • Some workloads fit the SAN's data services better than S2D
  • You accept that the SAN is attached after the cluster is deployed and running

Planning rules from Microsoft:

  • The SAN is always a day-2 operation on a hyperconverged cluster at version 2604 or later. You can't deploy hybrid from the start, so plan the fabric and adapters up front even though you connect them afterwards.
  • Fibre Channel: install Windows Server 2025 certified HBAs and drivers on all nodes, but do not zone HBA World Wide Names until after the Azure Local deployment. Zoning earlier can confuse the deployment for FC LUNs.
  • iSCSI: dedicated physical ports for iSCSI are required. vNICs are not supported. NIC firmware and drivers must match the Azure Local hardware catalog and all nodes must use identical NIC configurations.
  • SAN connectivity uses separate adapters and fabrics that Network ATC does not manage. The S2D storage network stays as designed for switched or switchless.
  • MPIO is enabled by default from 2604. Volumes are presented as NTFS Cluster Shared Volumes, each appearing as a folder path you map to a storage path.
  • Rack aware clusters are not supported with external SAN storage on hyperconverged deployments.

The day-2 procedure is Phase 06 Task 10: Enable external storage (hybrid).

Disaggregated SAN​

Select the SAN-only topology only when specific conditions apply.

Select disaggregated SAN when:

  • The customer already has a certified FC or iSCSI SAN that is actively maintained
  • Storage must be shared with other workloads (physical servers, other hypervisors) on the same array
  • Compute and storage must scale independently, or the cluster needs more than 16 machines
  • IOPS or latency needs are best met by the on-site certified array and cannot be met by local NVMe in the node design
  • SAN administration capability is present and the ongoing overhead is accepted
Operational overhead

Disaggregated SAN adds ongoing complexity: fabric management (FC zoning or iSCSI paths), LUN masking, array firmware lifecycle, and MPIO currency across all nodes. Confirm this is accepted before recommending the topology.

SAN LUN Layout (Disaggregated deployments)​

At deployment time the system needs two LUNs, and they must be RAW: no partition table, no file system, no drive letter. Initializing either of them before the deployment runs makes it fail.

LUNPurposeMinimum SizePartition State at deploymentNotes
Infrastructure volumeAzure Local system volume250 GBRAWThe deployment claims and formats this LUN
Performance historyCluster metrics collection20 GBRAWMust stay RAW until deployment
Workload CSVsVM workload dataPer capacity planNot needed at deploymentLearn lists only the two system LUNs as deployment prerequisites and the deployment runbooks here add workload CSVs after the cluster is up. Presenting workload LUNs earlier is not prohibited, but the Azure Local Cloud recommendation is to present them after deployment, which avoids the risk that someone initializes them by accident

Every LUN must be presented to all cluster nodes with the same LUN ID (no partial presentation), and all nodes must have identical HBA configuration and zoning. Only NTFS volumes are supported for SAN-backed CSVs, and each LUN is dedicated to one CSV.

Critical: do not initialize the LUNs before deployment

The infrastructure and performance history LUNs must stay RAW. Initializing either with Disk Management, diskpart or an array tool before the deployment runs causes the deployment to fail. Present them to the nodes and leave them untouched. This also means a local-disk wipe must never touch SAN disks (see Phase 03 Task 11).

When the LUNs must be visible​

For a disaggregated deployment the machines must see the LUNs before Azure Arc registration: install the HBA driver, retrieve the WWPNs, have the SAN administrator unmask the LUNs to the HBAs, configure MPIO, then confirm the LUNs appear in Get-PhysicalDisk before you register with Arc. That means FC zoning for a disaggregated cluster is done before Arc registration, in Phase 03. Hybrid is the opposite: do not zone FC until after the cluster is deployed. Don't mix the two rules.

For iSCSI, starting with version 2610 (connected and disconnected deployments) don't manually enable iSCSI on the machines before deployment; the deployment wizard includes the iSCSI configuration, including per-node iSCSI settings. For versions 2604 to 2609, configure iSCSI manually first. Only dedicated adapters are supported for iSCSI, and the inbox driver must not be used.

Host Networking for SAN​

Microsoft publishes three disaggregated reference patterns. There is no FCoE pattern.

PatternEthernet ports per nodeNotes
Fibre Channel, no backup network4: management and compute on ports 1 and 2 (SET, Network ATC), cluster networks on standalone ports 3 and 4Plus dual-port FC HBAs (port A to switch A, port B to switch B)
Fibre Channel, with backup network6: as above plus a guest backup compute intent on ports 5 and 6 (SET)
iSCSI, 6 network adapters6: management and compute (SET), two standalone cluster ports (VLANs 1711 and 1712), two standalone dedicated iSCSI ports (path A VLAN 300, path B VLAN 400)Optional in-guest backup network added after deployment; dedicated adapters only

Rules common to disaggregated deployments:

  • There is no S2D and no RDMA storage intent. RDMA and jumbo-frame storage settings are an S2D storage-intent concern, not a disaggregated one.
  • Network ATC manages only the management and compute intent. The cluster networks (CSV, Live Migration, heartbeat over SMB Multichannel) run on standalone ports that Network ATC does not manage. The default cluster VLANs are 1711 and 1712.
  • All of this traffic is TCP, so PFC and lossless Ethernet are not required. Learn also says host-side DCB or ETS isn't needed on a routed multi-rack fabric because 802.1p CoS is discarded when a leaf routes the frame; engineer the fabric for capacity instead. Learn's FC pattern pages still list CoS and ETS reservations for a single-rack L2 design (priority 0 about 78 to 79 percent, priority 3 CSV and Live Migration 20 percent, priority 7 heartbeat 1 to 2 percent, PFC off). Pick the approach that fits the fabric; this difference between two Learn pages is an open question for the design review.
  • Jumbo frames still help the cluster ports. Azure Local applies the MTU you set in the portal or template to the host adapters; you set the same MTU on the switch ports yourself (a common pairing is 9000 on the host and 9216 on the switch). For IP-based SAN use the MTU your storage vendor specifies, end to end.
  • iSCSI hosts need a persistent /32 route per target IP bound to the storage adapter, with the iSCSI adapters on static IPs and no default gateway, plus MPIO. Only the management interface has a default gateway.
  • Minimum four Ethernet ports per node. iSCSI adapters at least 10 GbE.

Fibre Channel Requirements (SAN deployments)​

FC HBA Requirements​

  • Minimum 2 HBA ports per node, one to each independent fabric. Single-fabric designs are not recommended for production.
  • Use Windows Server 2025 certified HBAs and drivers that are supported for the node model, and check the SAN vendor's host support matrix for the HBA and driver combination. The Azure Local catalog governs Microsoft Support.
  • Dual-fabric zoning is strongly recommended: two independent FC switches, each carrying one fabric. A single switch failure must not interrupt storage access.
  • Redundant single-initiator zoning following the fabric and array vendor design (this is the wording Microsoft uses in its rack aware SAN article). Many designs also use one initiator to one target; that tighter pattern is the Azure Local Cloud standard here, not a Microsoft requirement. Each HBA port is zoned only to the array target ports it needs.
  • Use the inbox Microsoft DSM (MSDSM) with the array's vendor and product IDs registered. There is no vendor DSM package to stage. Vendor IDs and tuning are in Phase 03 Task 13.

FC Switch Port Planning​

Per-fabric port count = (Node count × 2 HBA ports) + Array target ports per fabric

Example: 4-node cluster, 2 HBA ports per node, 4 array target ports per fabric: (4 × 2) + 4 = 12 FC switch ports per fabric. Plan at least 20 percent headroom.

Supported arrays​

Supported vendors and models are listed in Supported SAN solutions on Azure Local: Dell PowerStore T/Q (OS 3.0 or later), Everpure FlashArray, Hitachi VSP, HPE Alletra MP 10000, NetApp ONTAP (AFF, ASA), and Lenovo ThinkSystem DS, DM and DG. Machine validation fails for disaggregated deployments that use SANs from unsupported vendors, and the wizard prevents selecting unsupported vendor LUNs.

Licensing and Billing​

Choosing a SAN changes the Azure Local meter (from Azure Local billing and payment):

TopologyTierTrial
Hyperconverged with local storage, up to 16 nodesAzure Local (L1)The standard 60-day free trial
Adding external storage to an existing hyperconverged deploymentAzure Local (L2) after the trialA 30-day trial starts when external storage is added. Billing stays on the current pricing during the trial, and continues at L1 if the cluster's own free trial ends first
New SAN-only disaggregated deploymentAzure Local (L2)60-day free trial after registration

Billing updates automatically when external storage is added or removed. L2 requires cloud-connected management. Azure Hybrid Benefit for Azure Local supports only hyperconverged deployments with cloud-connected management and no external storage (L1); L2 and L3 aren't supported. Factor this into the business case before recommending a SAN.

Pre-Deployment Storage Checklist​

Complete before the hardware provisioning phase.

  • Storage topology decision confirmed (S2D, hybrid, or disaggregated SAN) and documented in the project planning record
  • If SAN: protocol decided (FC or iSCSI) and the matching network pattern chosen (FC 4 or 6 port, iSCSI 6 port)
  • If SAN: array model, firmware and Azure Local support status documented against the supported-SAN list
  • If FC: FC switch model and firmware documented for both fabrics
  • If SAN: billing impact (L2, trial period, no Azure Hybrid Benefit) agreed with the customer
  • If disaggregated: LUN layout planned (infrastructure 250 GB or more, performance history 20 GB or more; workload LUNs sized for after deployment)
  • If disaggregated FC: zoning policy agreed (redundant single-initiator; deviations documented) and WWPNs collected during Phase 03 OS configuration; zoning done before Arc registration
  • If disaggregated: infrastructure and performance-history LUNs presented to all nodes and left RAW
  • If hybrid FC: HBAs installed and certified, no zoning until after the S2D cluster is deployed
  • If hybrid iSCSI: dedicated physical ports reserved (no vNICs) and kept outside Network ATC
  • If SAN: MSDSM vendor and product IDs confirmed for the array (no vendor DSM package)
  • If rack aware is wanted: confirm it is the disaggregated FC preview; hyperconverged rack aware does not support external SAN
