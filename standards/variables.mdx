# Variable Management

> **Last Updated:** 2026-11-13  
> **Applies to:** All AzureLocal repositories  
> **Master Registry:** [`azurelocal-toolkit/config/variables/schema/master-registry.yaml`](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/schema/master-registry.yaml)

---

## How The Variable System Works

One master, one file, one template per tool.

- **The registry is the only master.** `config/variables/schema/master-registry.yaml` defines every variable: the keys of `infrastructure.yml`, the parameters and settings of each tool, the secret names and the environment variables. Nothing else defines a variable. A variable that exists only in a script, a file, a hand-edited schema or a document is drift, and the tests fail on it.
- **One `infrastructure.yml` feeds every tool.** It describes one Azure Local instance. It follows schema 5 (the current version is 5.6.26). The toolkit scripts, azurelocal-ztp, azurelocal-sonar, Trailwright, the ARM deployment, Terraform and Ansible all read this file.
- **One generated template per tool.** Each tool gets a template with only the keys it reads, under `config/variables/templates/tools`.
- **Secrets are references, never values.** One resolver reads them, through four providers (Azure Key Vault is the default). No script names a vault.
- **Every script parameter is registered.** A generator reads each script and writes its parameters into the registry.
- **An enforcement test stops hard-coded values.** A script cannot carry an address, a name, an ID or a region that a deployment chooses.

```text
                 master-registry.yaml   (THE MASTER: edit this)
                          |
                          | generated by New-InfrastructureArtifacts.ps1
        +-----------------+---------------------------+
        v                 v                           v
 infrastructure.schema.json   templates/infrastructure.master.yml   templates/tools/<tool>.yml
 (the contract)               (every key)                            (only the keys that tool reads)

 infrastructure.yml  (one per environment, validated by the schema)
        |
        +--> read by every tool through Import-AzlInfrastructure
        +--> cut for one tool with New-InfrastructureArtifacts.ps1 -Cut <tool>
```

## Quick Start

### 1. Start a file

Copy `config/variables/templates/infrastructure.master.yml` (every key), a scenario template under `config/variables/templates/scenarios/`, or the nearest worked example under `config/variables/examples/` to your environment repository as `infrastructure.yml`. Or let Trailwright write it from a guided design.

### 2. Set the scenario first

Set `scenario` before anything else. Each choice there makes its section required. For example, `identity: active_directory` needs `identity.active_directory`.

### 3. Fill in the values

Replace the example-company values with your own. Put each secret in a secret store and write a reference to it (see [Secrets](#secrets)).

### 4. Check the file

```powershell
# From the azurelocal-toolkit root
./scripts/common/infrastructure/Test-InfrastructureFile.ps1 -Path ./infrastructure.yml
```

It lists every problem at once and exits with code 1 when there are errors. Warnings do not fail it.

### 5. Run the automation

Every script takes the file as a parameter, for example `-InfrastructureFile ./infrastructure.yml`. Run it with `-WhatIf` first where the script supports it.

## The Master Registry

```text
azurelocal-toolkit/config/variables/schema/master-registry.yaml
```

For every variable the registry holds the type, the description, the default, the allowed values, an example, the schema version that added it (`since`) and the tools that read it (`used_by`). The registry version is 5.0.58 and it follows infrastructure schema 5.6.26.

### Layout

```text
config/variables/
  schema/
    master-registry.yaml          THE MASTER. Edit this.
    infrastructure.schema.json    GENERATED: the schema of infrastructure.yml
    tools/<tool>.schema.json      GENERATED: the part of the schema one tool reads
  templates/                      GENERATED
    infrastructure.master.yml     every variable, with comments and allowed values
    scenarios/                    the master for one scenario choice
    tools/<tool>.yml              one template per tool
  examples/                       hand-written worked examples, tested against the schema
  docs/
    infrastructure-file.md        what infrastructure.yml is and how to fill it in
    secret-references.md          secret references and the four providers
    MIGRATION.md                  where every key from the earlier files went
    VARIABLES.md                  GENERATED: every key, type, default, example, who reads it
    VARIABLE-MAP.md               GENERATED: what variable goes where, by phase, tool and ARM parameter
  tool-mappings/                  names of the variables of other tools mapped to registry paths
  scripts/                        validators, the reader (VariableRegistry.psm1) and the generators
```

A generated file carries a `GENERATED from master-registry.yaml` header. Never edit one. A test regenerates them and fails when one is stale.

### Registry first

A new or changed variable goes into the registry first. The script, the example and the document follow, and the generated files are regenerated.

1. Add the entry to the registry. The `example` is a documentation placeholder (RFC 5737 addresses such as `192.0.2.x`, the all-zero GUID, `example.com`), never a value from a real environment.
2. Bump the registry version and add a change log entry.
3. Run `./config/variables/scripts/New-InfrastructureArtifacts.ps1`. It rewrites the schema, the templates and `VARIABLES.md`.
4. Only then change the script, the example and the page that explains it.
5. Run the checks (see [Validation](#validation)).

## One Master File, One Template Per Tool

From the registry the generator writes one master file (`templates/infrastructure.master.yml`) and one template per tool (`templates/tools/<tool>.yml`), each with a matching JSON schema (`schema/tools/<tool>.schema.json`). Someone who fills in a file for one tool sees only that tool's keys.

| Tool id | Tool | Template |
|---------|------|----------|
| `ztp` | azurelocal-ztp | `templates/tools/ztp.yml` |
| `os_configuration` | OS configuration (toolkit) | `templates/tools/os-configuration.yml` |
| `deployment` | Pre-cluster verification and ARM deployment (toolkit) | `templates/tools/deployment.yml` |
| `cicd_infra` | CI/CD infrastructure (toolkit) | `templates/tools/cicd-infra.yml` |
| `monitoring` | azurelocal-sonar | `templates/tools/monitoring.yml` |
| `discovery` | Hardware discovery (toolkit) | `templates/tools/discovery.yml` |
| `trailwright` | azurelocal-trailwright, which writes the file | `templates/tools/trailwright.yml` |
| `ranger` | azurelocal-ranger, design comparison | `templates/tools/ranger.yml` |
| `terraform` | Terraform (toolkit), the other route for the Azure foundation and the CI/CD runners | `templates/tools/terraform.yml` |
| `ansible` | Ansible (toolkit), the other route for the on-premises steps | `templates/tools/ansible.yml` |

To give a tool its input from your master file, cut the file:

```powershell
./config/variables/scripts/New-InfrastructureArtifacts.ps1 -Cut ztp -From ./infrastructure.yml -Out ./infrastructure.ztp.yml
```

The cut is always a subset of the master file. The tool validates it against its own schema. The master file is validated by the full schema and the rules of `Test-InfrastructureFile.ps1`.

The own settings of a tool (a configuration key, a command parameter, an environment variable) are registered too, in the same registry, under `tools.<tool>.<kind>.<group>.<name>`. The names that azurelocal-ztp, azurelocal-sonar, azurelocal-ranger, azurelocal-loadtools and azurelocal-draftsman use are mapped to registry paths in `config/variables/tool-mappings/`.

## Naming Rules

| Rule | Standard | Example |
|------|----------|---------|
| Keys | `snake_case` at every level | `subscription_id`, `resource_group` |
| Enum values | `snake_case` | `active_directory`, `rack_aware` |
| Lists | A list of items, each with a `name` | `nodes[]`, `landing_zone.networks[]` |
| Secrets | A reference, never a value | `keyvault://kv-iic-mgmt-01/local-admin-password` |
| Your own keys | Under `extensions.<your-key>` | `extensions.iic-notes` |

Anything the schema does not define goes under `extensions`. Tools ignore keys they do not own.

## Secrets

A secret is never a value in `infrastructure.yml`, in a log, in an error message or in a report. A key that needs a secret holds a reference. One resolver reads it: `scripts/common/secrets/AzlSecret.psm1`. No script names a vault, a directory or a command. They all come from the master file.

### The four providers

A reference names its provider in its scheme. One file can mix providers.

| Form | Provider | What follows `://` |
|------|----------|--------------------|
| `keyvault://<vault>/<secret>` | Azure Key Vault (the default) | The vault, which must be listed under `key_vaults`, and the secret name |
| `env://<VARIABLE_NAME>` | Environment variable | The name of a variable of the process |
| `file://<name>` | File | The name of a file in `secrets.file.directory` |
| `command://<name>` | Custom command | The name passed to the command in `secrets.command` |

A text that is not one of these four forms is not a reference. The validator refuses it, and no tool uses it as a value. This is how a password written by mistake is caught.

### The `secrets` section

| Key | Default | Meaning |
|-----|---------|---------|
| `secrets.provider` | `keyvault` | The provider used to build a new reference when the caller does not name one |
| `secrets.file.directory` | none | The absolute path of the directory that holds the secret files (for `file://`) |
| `secrets.command.executable` | none | The program to start (for `command://`) |
| `secrets.command.arguments` | none | The arguments. At least one item must hold `{name}` |
| `secrets.command.timeout_seconds` | `30` | How long the command may run (1 to 300) |

```yaml
key_vaults:
  - name: kv-iic-mgmt-01
    subscription_id: 00000000-0000-0000-0000-000000000000
    resource_group: rg-iic-mgmt-01

identity:
  local_admin:
    username: iic-admin
    password: keyvault://kv-iic-mgmt-01/local-admin-password
```

The full rules are in the toolkit page [Secret references and providers](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/docs/secret-references.md).

## Reading Variables in Scripts

Scripts read the file through one module. It needs the `powershell-yaml` module.

```powershell
Import-Module ./scripts/common/infrastructure/AzlInfrastructure.psm1
$infra = Import-AzlInfrastructure -Path ./infrastructure.yml   # stops if the file has errors
$gateway = $infra.networking.management.gateway
$value = Get-AzlInfrastructureValue -Infrastructure $infra -Path 'provisioning.simplified.site_name'
```

Without `-Path`, `Import-AzlInfrastructure` looks for `$env:AZL_INFRASTRUCTURE_FILE`, then `./infrastructure.yml`, then `./config/infrastructure.yml`.

A script that a person calls takes `-InfrastructureFile`, and the parameter is mandatory. It never asks for a value: no `Read-Host` and no `Get-Credential`. A credential comes from a `-Credential` parameter or from a secret reference in `infrastructure.yml`. When neither gives one, the script stops with exit code 2.

## Script Parameters

Every parameter of every script a person calls is a registry variable. Nobody keeps that list by hand. `New-ScriptParameterRegistry.ps1` reads the `param()` block of each script with the PowerShell parser and writes one group per script and one entry per parameter into the registry (name, type, default, allowed values, mandatory, and the `.PARAMETER` help as the description).

```powershell
./config/variables/scripts/New-ScriptParameterRegistry.ps1           # write the block
./config/variables/scripts/New-ScriptParameterRegistry.ps1 -Check    # exit 1 if the registry is out of date
```

Run it when you add, remove or change a script parameter. A script parameter that is not registered fails the tests `tests/variables/ToolRegistry.Tests.ps1` and `tests/variables/ScriptParameterRegistry.Tests.ps1`.

## No Hard-Coded Values in Scripts

`tests/variables/Enforcement.Tests.ps1` fails the build when a script under `scripts/` carries a value that a deployment chooses, or reads a key that the registry does not have. The rules:

- **A:** a key path read from the infrastructure file that the registry does not have.
- **B:** a literal IPv4 address or CIDR, a GUID, a DNS name, an Azure region name, a Key Vault name, an Azure resource name, or a value given to a subscription, tenant, resource group or vault.
- **C:** a parameter whose default is such a value.
- **D:** `Read-Host`, `Get-Credential` or a console prompt in a script that has `-InfrastructureFile`.

Values that Microsoft or a protocol fixes are not violations (documentation addresses, loopback, the Azure platform address, Microsoft endpoints, the all-zero GUID and the built-in role and policy IDs). A reviewed exception goes in `tests/variables/enforcement-allowlist.psd1`. Known debt in older scripts that are not migrated yet is in `tests/variables/enforcement-baseline.psd1`, and the test fails on one more violation than the baseline lists.

A new violation is fixed in the script, by reading the value from the infrastructure file. It is not added to the baseline.

## Terraform and Ansible

The Terraform code (`src/terraform`) and the Ansible roles (`src/ansible`) do not define the facts of an environment a second time. `config/variables/scripts/New-IacVariableFiles.ps1` reads `infrastructure.yml` and writes `terraform.tfvars.json`, `backend.hcl`, `inventory/hosts.yml`, `group_vars/all.yml` and `host_vars/<node>.yml`. Every variable of the code says in the registry where it comes from. A secret is never written: the script tells you which environment variable the code reads at run time.

```powershell
./config/variables/scripts/New-IacVariableFiles.ps1 -InfrastructureFile ./infrastructure.yml -OutputDirectory D:\work\iac -WhatIf
```

Keep the output folder out of the repository.

## Validation

Run these from the toolkit root. All must pass.

```powershell
./config/variables/scripts/validate-registry.ps1                      # structure of the registry
./scripts/common/infrastructure/Test-InfrastructureFile.ps1 -Path ./config/variables/examples/infrastructure.example.yml   # the example against the schema and the rules
./config/variables/scripts/New-InfrastructureArtifacts.ps1 -Check    # generated files are current
./config/variables/scripts/New-ScriptParameterRegistry.ps1 -Check    # every script parameter is registered
Invoke-Pester ./tests/variables, ./tests/infrastructure
```

| Generator | Run it when |
|-----------|-------------|
| `New-InfrastructureArtifacts.ps1` | The registry's infrastructure keys changed. Rewrites the schema, the templates and `VARIABLES.md` |
| `New-ToolMapping.ps1` | A variable of ztp, sonar, ranger, loadtools or draftsman changed |
| `New-ScriptParameterRegistry.ps1` | A script parameter was added, removed or changed |
| `New-VariableMap.ps1` | Any of the above, or any script or test change. Rewrites the variable map |

The variable map (`config/variables/docs/VARIABLE-MAP.md`) answers "what variable goes where": for every key, who provides the value, which tool reads it and what it becomes downstream (an ARM template parameter, an OS configuration step, a Sonar setting).

## The Earlier Layout (Retired)

The earlier toolkit layout was a nested `variables.yml` (registry 4.0.0) read by loader helpers. Schema 5 replaces it, together with the environment file of azurelocal-ztp and the export of Trailwright 1.x. The earlier layout is gone from the toolkit (registry 5.0.58, schema 5.6.26):

- `config/variables/variables.example.yml`, `variables.schema.json`, `validate-variables.ps1`, `Test-VariablesFile.ps1` and `Test-VariableConfig.ps1` are removed. Use `config/variables/examples/infrastructure.example.yml` and `Test-InfrastructureFile.ps1`.
- `config-loader.ps1` and `keyvault-helper.ps1` are removed. Scripts use `Import-AzlInfrastructure` and `AzlSecret.psm1`.
- No script takes `-ConfigPath` or `-ConfigFile`. Every script takes `-InfrastructureFile`.
- The registry-only keys `environment.env_name`, `env_type`, `env_owner`, `env_description`, `site.env_name` and `identity.active_directory.security_groups_by_role` are removed. Use `environment.name`, `type`, `owner`, `description`, `site.name` and `identity.active_directory.security_groups[]`.

[MIGRATION.md](https://github.com/AzureLocal/azurelocal-toolkit/blob/main/config/variables/docs/MIGRATION.md) says where every old key and every removed script went.
